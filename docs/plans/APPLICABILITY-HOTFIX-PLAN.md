## 2. 확인한 원인과 범위

### 재현된 계단 증상

현재 명세와 원문 추출 p106-x0은 경사형 가설 계단의 높이 6m 이하·폭 0.9m 이하 기준을 나타낸다. 면적 18㎡·높이 8m·폭 1.5m 입력에서 다음을 실제 오프라인 경로로 재현했다. 검색은 모의 처리했으며 HTTP·브라우저·실제 모델 호출은 하지 않았다.

1. 남은 필수 질문이 있으면 적용 범위 검사를 미루어 높이 초과 뒤에도 폭 등을 질문한다.
2. 계산 도구는 BLOCKED와 높이 초과 사유를 항목에 저장한다.
3. 집계는 산정 가능한 항목이 없어 NO_RESULT를 만든다. 0원 견적을 만들지 않는 이 동작은 유지해야 한다.
4. 부모 대화의 마지막 상태가 NO_RESULT가 되고, 응답 변환은 개별 BLOCKED를 복구하지 못해 ANSWERED/result=null을 반환한다.
5. 고정 진행 문구가 표시된다. “안됐어”에는 종료된 항목을 건너뛰고 같은 문구를 반복한다.

### 전체 형식 조사 (핫픽스 기준선)

- 초안 파일 1,058개 중 차단 항목이 있는 파일 413개, 선언 752개.
- 실제 로드 명세 925개 중 차단 항목이 있는 명세 349개, 선언 663개.
- 로드된 선언은 단일 조건 407개, AND 복합 조건 191개, 실행 조건 없이 설명만 있는 항목 65개(49명세)다.
- 로드된 계산기 유형은 per_unit, adjusted_daily_crew, formula, lookup_only 모두 해당한다.
- 이는 정적 형식 조사다. 663개가 모두 공식 적용 제한이라는 뜻도, 모든 원문 규칙의 분모라는 뜻도 아니다. 별도 계상·정책 미확정·기능 미지원 등이 섞일 수 있다.
- 기존 `check_registered_blocked`는 승인 모듈이 처리하는 조건을 걸러낸다. 이를 무시하고 raw blocked를 안내하면 이미 지원되는 거푸집 높이 등을 다시 불가능하다고 안내할 수 있다.

## 3. 고정할 사용자 동작

### 공종 선택 직후

- 선택한 공종의 정확한 명칭·용도, 근거가 연결된 적용 범위, 별도 계상 범위를 첫 조건 질문과 함께 보여준다. 별도 확인 버튼을 매번 추가하지 않는다.
- 핵심 적용 조건은 요약하고 나머지는 펼쳐보기로 제공한다. 입력 대상 조건과 연결해 제시하며 전체 비고를 길게 나열하지 않는다.
- “가설”처럼 명칭에 명시된 용도를 숨기지 않는다. 다만 “철제 계단”이라는 말만으로 영구 계단이라고 단정하거나 자동으로 가설 계단에 확정하지 않는다. 기존 공종 선택 경로에서 선택 의미를 분명히 한다.
- 아직 값이 없거나 규칙을 평가하지 않은 상태를 “적용 가능 확인 완료”라고 표시하지 않는다.

### 조건 입력·수정 직후

- 질문 카드 답변, 대화에서 추출한 값, 초기 요청에 있는 값, 구조화된 조건 수정 등 공통 조건 저장 경로에서 재평가한다. 복원 시에도 현재 입력 revision에 맞는 안내를 제공한다.
- 높이 8m만으로 범위 초과가 확정되면 나머지 무관한 질문을 계속하지 않는다.
- 복합 조건에서 판단에 필요한 값이 부족하면 그 값만 확인한다. 이미 다른 조건이 거짓이면 그 AND 규칙은 위반이라고 하지 않는다.
- 실제 조건을 낮춰 입력하라고 유도하지 않는다. 잘못 입력했다면 정정할 수 있고, 실제 범위 밖이라면 공종 재선택·적용 근거 확인 경로를 제공한다.

### 차단·복구·다중 공종

- 사유, 해당 입력과 기준, 근거, 다음 행동을 텍스트와 카드에서 일관되게 표시한다. 데이터가 없으면 값을 만들어내지 않는다.
- “안됐어/왜 안 돼?”가 현재 차단 상태를 가리키면 해당 이유를 설명한다. 새 질문·새 공종·실제 조건 수정까지 이 응답으로 가로채지 않는다.
- 값이 수정되면 관련 판단·질문·품량·가격·집계를 무효화하고 재평가한다. 다른 공종 결과와 입력은 보존한다.
- 정상 항목+차단 항목은 부분 견적이며 누락 이유를 표시한다. 모든 항목이 차단되면 산정 결과 없음과 사유를 표시하고 0원 완료나 현재 견적 다운로드로 오인시키지 않는다.

## 4. 공통 규칙 처리 설계

### 안내와 판단은 같은 유효 규칙을 사용

새 LLM 분류기나 별도 계산 엔진을 만들지 않는다. 기존 명세·승인 모듈·입력 검증·차단 연산을 재사용한다. 필요한 최소 공통 유틸리티를 기존 계산 규칙 계층에 두어 안내와 조기 검사와 최종 계산이 동일한 유효 규칙 집합을 소비하게 한다.

- 승인 모듈의 handled_conditions, 추가 입력, 정책 적용 범위와 출처 검사를 존중한다. 원문 제한을 승인 정책이 해소한 경우 raw 제한을 현재 계산 불가로 재표시하지 않는다.
- 수치/선택 조건은 기존 비교 연산(>, >=, <, <=, ==, !=, in, not_in)과 정확한 수치 검증을 사용한다. 단위가 같더라도 높이·폭을 임의로 같은 필드에 배정하지 않는다.
- 규칙별 판정은 위반/위반 아님/입력 부족/규칙 평가 오류를 구분한다. “미검출”을 전체 적용 가능으로 해석하지 않는다.
- 문장만 있는 65개 선언은 자동 수식화하거나 일괄 차단하지 않는다. 근거가 있는 안내와 판단 불가를 구분하고, 실행 가능한 조건 누락은 진단 목록에 남긴다. 직접 영향을 받는 잘못된 선언을 고쳐야 한다면 원문 대조와 변경 근거를 별도로 기록한다.
- 최종 계산 시 기존 검사를 유지한다. 조기 검사만 통과한 것을 계산·금액 검증 완료로 간주하지 않는다.

### 상태 분류

| 사용자에게 구분할 상황 | 처리 |
|---|---|
| 필요한 조건이 부족함 | 필요한 질문 계속, 적용 가능 확정 금지 |
| 공식 적용 범위 밖 | 범위·값·근거 안내, 그 경로의 불필요한 질문 중단 |
| 지원 기능·정책이 미완료 | 원문에서 불가능하다고 단정하지 않고 현재 지원 한계를 설명 |
| 명세·출처·규칙 평가 오류 | 내부 기술정보를 그대로 노출하지 않고 근거를 확정하지 못한 상태로 안내·진단 기록 |
| 계산은 가능하지만 단가·별도 비용 누락 | PARTIAL 유지. 적용 불가와 혼동하지 않음 |

불명확한 사유 문자열만으로 공식 범위와 기능 미지원을 추정하지 않는다. 구조화된 근거가 부족하면 중립적인 확인 필요로 표시한다.

### 상태와 API 계약

항목별로 규칙 식별, 판정 종류, 관련 필드·입력값, 기준, 사유, 근거, 판단에 필요한 미입력 필드와 입력 revision을 보존한다. 기존 ID가 없으면 명세 ID·조건·출처에서 결정적으로 식별하고 명세 전체를 다시 쓰지 않는다.

기존 응답을 깨지 않는 선택 필드로 적용 범위 안내·문제 목록을 추가하는 방향을 우선한다. 기존 status/reason/result 변환도 함께 맞춘다. 원가·계산 결과에 오류 정보를 억지로 섞지 않는다. 과거 세션에 새 필드가 없으면 원래 조건에서 재구성하며 삭제·이전 대화 일괄 마이그레이션은 하지 않는다. BLOCKED/ERROR/UNSUPPORTED/NOT_FOUND/NO_RESULT가 모두 고정 성공 문구로 빠지지 않도록 응답 계약을 검사한다.

## 7. 실행 순서와 검토 지점

하나의 핫픽스와 PR로 처리한다. 순서는 의존 관계이며 날짜별 대기나 공종별 개별 패치 단계가 아니다.

1. 재현 사례와 응답 계약을 회귀 검사로 고정한다. 계단만 아니라 기존 계산기별 대표 숫자·선택·복합·정책 해소 규칙을 고른다.
2. 유효 규칙의 안내·부분 입력 판정과 공통 도구 호출 시점을 연결한다. 사용자에게 보이지 않는 새 기반 프레임워크부터 만들지 않는다.
3. 부모 대화·응답 변환·화면 표시와 복구 동작을 함께 연결한다. 여기까지를 한 사용자 흐름으로 완성한다.
4. 아래 행렬의 집중 검사와 기존 영향 회귀를 수행하고 같은 후보로 실제 브라우저를 확인한다.
5. 변경 내용·검사 결과·남은 데이터 결함·배포 영향을 정리해 PR 검토 대상으로 제시한다. 머지·배포는 자동 진행하지 않는다.

기본 한 묶음 45분 또는 같은 원인 수정 실패 2회 시 저장·보고한다. 이 시점에 미완료를 완료로 표시하거나 자동으로 무제한 후속 작업을 시작하지 않는다. 필요한 다음 실행 범위를 구체적으로 제시한다. 구현 일정의 완료 보증으로 해석하지 않는다. 이번 계획 조사에서는 외부 호출을 하지 않았다.

- [ ] 높이 6m·폭 0.9m 경계는 허용되고 초과는 차단된다. 기존 수량·금액 산식은 유지한다.
- [ ] 선택값 조건, AND 복합 조건, 미입력과 일부 거짓 조건이 있는 경우를 정확히 구분한다.
- [ ] 같은 단위의 높이·폭이 모호한 문장은 임의 배정하지 않고 확인한다.
- [ ] 승인 모듈이 해소한 거푸집 높이 제한을 과거 raw blocked 때문에 다시 차단하거나 잘못 안내하지 않는다.
- [ ] 설명만 있는 규칙·잘못된 비교식·누락된 근거를 적용 범위 밖으로 오판하지 않는다.
- [ ] per_unit, adjusted_daily_crew, formula, lookup_only 대표에서 동일 안내·상태 계약이 동작한다.
- [ ] 초기 요청·질문 카드·대화 답변·조건 수정·복원 경로에서 판단이 일관된다.
- [ ] “안됐어/왜 안 돼?”의 기존 문제 설명과 실제 값 수정·공종 변경·새 질문을 구분한다.
- [ ] 정상+차단 항목은 정상 결과·입력 revision을 보존하고 PARTIAL 및 차단 사유를 표시한다.
- [ ] 전체 차단은 결과 없음으로 표시하고 0원 견적·성공·무의미한 계속 진행을 만들지 않는다.
- [ ] 수정 전의 품량·금액·Excel을 최신 결과처럼 표시하거나 내려주지 않는다.
- [ ] 과거 세션에 새 선택 필드가 없어도 복원·수정이 가능하다.
- [ ] API에서 상태·사유·근거가 보존되고 실제 화면에서도 표시된다. 단위 테스트만으로 브라우저 통과를 선언하지 않는다.
- [ ] 기존 정상 상담·장비/높이 계산·부분 견적·다중 집계·Excel 영향 회귀와 프런트 빌드가 통과한다.
- [ ] 로드된 전체 규칙의 형식·의존 필드·지원 연산·안내 생성 여부를 한 번 정적으로 점검하고 미표현 선언을 결과에 남긴다. 전수 계산 정확성 검사로 집계하지 않는다.

브라우저는 운영과 분리된 기존 승인 로컬 환경을 우선한다. 환경이 준비되지 않으면 상태와 사유를 보고하고 브라우저 검증을 미실행으로 남긴다. 운영 DB 사용·비회원 제한 임의 해제·실제 모델 호출로 우회하지 않는다. 영향 검사 통과 뒤에는 변경 없는 전체 검사를 반복하지 않는다.

## 9. 검토 요청

승인 대상은 이 문서의 공통 안내·조기 검사·상태 전달·복구와 집중 검증 범위다. 계단을 위해 계산 기준을 바꾸거나 전체 계산 확대 작업을 섞는 승인이 아니다. 구현 결과는 이 문서의 체크 항목과 대응시켜 보고한다.
