## 이번 지시의 핵심과 최종 방향

최종 구조는 다음 네 기능을 함께 갖춘다. 서로 경쟁하는 후보가 아니다.

1. 표·단위·조건을 보존하는 구조 기반 청킹.
2. 검색된 내용의 부모 문맥과 필요한 주석을 함께 조회.
3. 공종 목록·규칙·표를 목적에 맞게 검색.
4. 원문에 명시된 참조 절을 조건과 함께 조회.

이번 실행은 **기존 파싱 출력에서 청킹과 근거 조립까지 이어지는 작은 시제품**으로 한정한다. 공종 목록·규칙·표의 검색용 레코드 예시는 만들되, 실제 검색 성능과 에이전트 답변 성능은 다음 단계에서 평가한다. API 금지를 유지하며 운영 코드에 연결하지 않는다.

이미 아래 작업을 수행한 결과가 있다면 먼저 결과와 완료 기준을 대조하고, 충족한 작업은 반복하지 않는다. 부족한 부분만 수행한다.

## 판단

ODL local + 기존 행 분리·조립을 다음 단계의 우선 후보로 선정한다. 운영 교체를 확정하는 지시가 아니다.

보고서에서 숫자 칸의 값과 행·열 조건 연결은 현행 187/425, 개선 시제품 247/425, ODL + 후처리 369/425였다. ODL 원본은 91/425이므로 개선 효과를 ODL 라이브러리 하나의 효과로 해석하면 안 된다. Docling은 대응 후처리 없이 추출만 평가했으므로 이 점수로 라이브러리의 일반적인 우열을 단정하지 않는다.

정답은 사람 검토 전 초안이고 전체 품셈 정확도가 아니다. 정상 표 회귀 0건도 비교한 정상 표 4개에 한정된다. 보고서 기준 ODL 후처리에는 잘못 연결된 숫자 칸 8개가 남아 있다. 금액 산출에서는 이 오류를 단순 누락과 구분해야 한다.

좋은 신호는 기존 후처리를 이번에 수정하지 않고 얻은 결과라는 점이다. 보고서에는 별도 평가 7표가 해당 후처리를 개발한 쪽과 겹치지 않는다고 적혀 있다. 다만 이제 이 표들도 확인했으므로 다음 수정의 최종 평가 자료로 재사용하지 않는다.

## 다음 작업의 목적

다시 파서를 폭넓게 비교하기보다, **ODL에서 얻은 표 구조를 잃지 않고 검색 조각과 답변 근거로 전달할 수 있는지** 확인한다.

## 1. 기존 출력으로 공통 보관 형식을 보여준다

| 문서 버전·연도·부문·절·소제목 | 같은 절 번호나 직종명이 다른 문서·부문과 섞이지 않게 함 |
| 표 식별자·쪽·원문 좌표 | 모든 숫자와 문장을 원문까지 추적 |

검색용 문자열과 원문 보관 구조를 분리한다. 보기 좋게 반복한 숫자를 원문의 독립 값으로 취급하지 않는다. 정보를 찾을 수 없으면 미확정으로 표시하고 추측해서 채우지 않는다.

## 3. 검색 표현을 만들고 근거 묶음을 단계별로 비교한다

같은 보관 구조에서 공종 목록용, 규칙 설명용, 표·작업 조건용 검색 레코드 예시를 만든다. 각각 원문 식별자로 돌아갈 수 있어야 한다. 세 종류가 별도 데이터베이스를 뜻하지 않으며, 공종별 수작업 설정을 새로 만들지 않는다.

부모 관계는 `이 내용이 어느 절·표에 속하는가`, 참조 관계는 `어떤 조건에서 어느 절을 더 읽는가`로 구분한다. 원문 문장과 위치를 관계에 연결한다. 관계 유형이나 적용 범위가 불확실하면 명시적으로 남긴다.

같은 원문 보관 구조를 입력으로 사용한다.

| 안 | 검색 시작점 이후 가져오는 내용 |
|---|---|
| 가 | 표 또는 작업 조건별 행 묶음 |
| 나 | 가 + 해당 표의 머리글·단위·기준·필수 주석 |
| 다 | 나 + 원문에 명시된 다른 절의 참조 근거 |

이는 기능을 하나씩 더했을 때 무엇이 달라지는지 확인하는 비교다. 최종적으로 하나만 고르는 투표가 아니다. 작은 절은 절 전체를 부모로 가져오는 방식을 먼저 확인한다. 참조는 같은 문서 버전·부문을 기준으로 찾고, 순환 참조를 반복 조회하지 않는다. 이번 시제품은 시작 절에서 직접 참조한 대상까지 조회하며, 그 너머 참조는 미조회 목록에 남긴다.

작은 표는 통째로 유지한다. 큰 표는 공동 작업량과 작업 조건이 완결되는 행 묶음을 우선한다. 직종 한 행이나 숫자 한 칸을 무조건 독립 청크로 만들지 않는다.

이번에는 동일한 검색 시작점을 직접 지정해 근거 조립을 비교한다. 이 결과를 벡터 검색 성능이라고 부르지 않는다. 검색용 추가 문맥의 효과는 별도 검색 비교에서 확인한다.

필수 조건 문장을 길이 제한 때문에 중간에서 자르지 않는다. 묶음이 너무 크면 추가 조회가 필요하다는 상태를 표시한다. 가져온 근거마다 가져온 이유와 원문 위치를 남긴다.

## 4. 반복 문장 제거는 효과를 분리해서 확인한다

기준 코드 `pipeline/assemble.py:314-318`은 원문 위치와 무관하게 동일 문자열을 제거한다. 같은 기준 문장이 다른 표에서 반복되는 경우, 원문 보관에서는 각각의 위치와 연결을 남겨야 한다.

관련 원본 출력이 있으면 반복 문장 보존 전후를 메모리에서 비교한다. 이 변화와 부모·자식 확장의 효과를 한 점수에 섞지 않는다. 출력에 필요한 원문 위치가 없으면 한계로 기록한다.

## 5. 작은 별도 확인으로 마무리한다

표현과 검사 방법을 고정한 다음, 이번 수정에 사용하지 않은 기존 출력 표본을 최대 5개 확인한다. 처음 비교한 12표를 새로운 확인 자료라고 부르지 않는다.

기존 출력 중 적합한 별도 표본이 없으면 새 파싱이나 설치로 범위를 늘리지 말고, 그 제한을 기록한다. 이번 작업을 위해 큰 평가 정답 묶음을 다시 만들지 않는다.

확인 항목은 값·단위·머리글·공동 값 범위·필수 주석·참조 연결·불확실 표시·원문 추적이다. 정답 초안과 원문을 구분하고, 원문 대조만으로 확정할 수 없는 실무 해석은 미확정으로 남긴다.

## 제출 형식과 이후 순서

보고서는 먼저 사용자가 읽을 수 있는 185쪽 예시를 보여준다. `찾은 표 → 함께 붙은 기준·주석 → 참조 대상 원문 또는 미확보 표시` 순서로, 기술 설명 없이도 무엇이 보완됐는지 알 수 있게 한다. 뒤에 보관 형식, 검색 레코드 예시, 검사 결과와 한계를 붙인다. 결과 문서의 절대 경로를 보고한다.

이번 결과를 확인한 다음에만 다음 순서로 진행한다.

1. 고정한 보관 형식과 근거 조립 방식으로 제한된 범위의 공종 목록·규칙·표 검색을 비교한다. API 금지 상태에서는 오프라인 키워드 검색까지만 가능하며 임베딩 품질을 검증했다고 주장하지 않는다.
2. 서로 다른 표 형태의 소규모 표본에서 오류와 누락을 확인한 뒤 데이터 처리 범위를 넓힌다. 실패한 표를 계산 가능한 자료로 승격하지 않는다.
3. 검증된 조회 결과를 에이전트 도구에 연결하고 목록·설명·품·견적의 동작을 나눠 평가한다. 계산 명세의 정확성 검증은 별도로 유지한다.

전체 문서 재파싱·재임베딩이나 운영 에이전트 개편은 이 지시서의 실행 범위가 아니다.
