# 품셈 서비스 개선 전체 인계 문서

> 이 문서는 2026-10-10 당시의 기록이다. 이후 파싱 개발 순서와 최신 결과는 [파싱 개발 이력](PARSING-DEVELOPMENT-HISTORY-2026-10-11.md), 현재 실행 위치는 `experiments/parsing-final`을 확인한다. 과거의 실행 금지 범위를 최신 사용자 승인보다 우선하지 않는다.

작성일: 2026-10-10. 대상: 대화 이력이 전혀 없는 새 Codex 세션.

이 문서는 사용자의 요청에 따라 이전 대화, 기획 문서, 실험 결과, 현재 작업 폴더 상태를 종합했다. **이 문서를 먼저 읽는다.** 이전 `codex-session-handoff-2026-10-10.md`보다 최신이며, 그 문서의 “실제 수정 결과가 아직 없다”는 내용은 더 이상 현재 상태가 아니다.

## 1. 새 세션이 먼저 이해할 세 문장

1. 최종 목표는 **한국 건설 표준품셈 전체로 확장 가능한, 근거와 가정을 보여 주는 견적 서비스와 실무용 Excel**이다. 파싱 파일 하나를 고치는 것이 최종 목표가 아니다.
2. 개선 방향은 **원문 데이터 품질 → 청킹·검색·필수 근거 연결 → 계산 지식 검증 → 대화·다공종 견적·Excel**이며, 각 단계의 책임을 구분한다. 기존 구조 유지와 교체 중 더 나은 쪽을 증거로 선택한다.
3. 현재는 그 과정에서 발견한 **표 앞 산출 기준 누락**을 별도 작업 폴더의 `pipeline/parse.py`에서 수정했다. 제한된 검사 결과가 있고, 전체 데이터·벡터·운영은 아직 갱신하지 않았다.

처음 답변부터 미세한 정규식이나 줄 번호 이야기만 하지 말고 이 세 문장으로 현재 위치를 설명한다.

## 2. 이 대화의 역할과 사용자와 일하는 방식

- 사용자는 여기서 기획, 운영 전반의 판단, 설계 검토, 결과 평가를 진행한다. 실제 구현은 사용자가 별도로 운영하는 Claude Sonnet 세션에 맡긴다.
- Codex는 코드와 결과물을 읽고 검토할 수 있고, 소넷에게 전달할 마크다운 지시서를 작성한다. 사용자 요청 없이 직접 구현자로 역할을 바꾸거나 다른 세션에 메시지를 보내지 않는다.
- 사용자는 한국어 답변을 원하며 **한자를 사용하지 말라고 명시했다**. 작업 설명과 보고서도 한국어로 작성한다.
- 사용자는 작업의 목적과 전체 흐름을 자주 놓쳤다. 설명은 먼저 “지금 무엇을 왜 하는지”를 말하고 다음 한 가지 행동을 제시한다.
- “구조화”, “스키마”, “부모 청크”, “검증 통과” 같은 말을 쓸 때 실제 예를 붙인다. 예: “0.34만 남기지 않고, 미장공·인·100㎡당이라는 조건과 원문 위치를 함께 보관한다.”
- 짧은 보고서가 올 때마다 새 실험을 하나씩 끝없이 붙이지 않는다. 이미 답이 난 질문은 닫고, 남은 위험이 실제 다음 결정에 영향을 주는지 설명한다.
- 동시에 큰 작업 여러 개를 실행시키지 않는다. 전체 계획은 자세히 보존하되 실행 지시서는 한 번에 한 가지 목적과 완료 기준을 갖춘다.
- 이전에 승인한 범위를 다시 물어보지 않는다. 더 넓은 실행이 필요하면 무엇이 늘어나는지 구체적으로 정리한다.
- 초반 사용자는 독립적인 구조 의견을 원했고 다른 설계 문서를 읽지 말라고 했다. 이후 일부 문서를 직접 제공하고 비교를 요청했다. 이것이 저장소 `tmp/` 전체를 자유롭게 읽어도 된다는 뜻은 아니다.

## 3. 서비스와 반드시 지원하고 싶은 사용자 요청

서비스는 한국 건설 국가 표준품셈 2026년판 PDF 982쪽을 근거로 품과 공사비를 산출하는 챗봇이다. 표가 대부분이며 연도마다 개정된다. 이미 운영 중이고 홍보 전 단계라고 사용자가 설명했다.

주 사용자는 현장 실무자와 견적 담당자다. 짧고 불완전한 자연어, 현장 용어, “루베”, “펌프카” 같은 표현을 사용한다.

| 실제 요청 예 | 원하는 결과 |
|---|---|
| 콘크리트 관련 품셈 기준 있어? | 관련 기준과 공종 목록 |
| 펌프차 할증 기준이 뭐야? | 적용 조건을 포함한 원문 근거 설명 |
| 콘크리트 타설 1㎥ 품 알려줘 | 선택한 공법과 조건에 맞는 인력·장비 투입량 |
| 철근콘크리트 펌프카 타설 100루베 견적 | 원가계산서와 Excel |
| 교량 견적: 콘크리트 타설 300㎥, 거푸집 500㎡, 철근 가공조립 20톤 | 여러 항목을 합친 견적서 하나와 Excel 한 권 |

목록 질문에 계산 명세가 없다는 오류를 내면 안 된다. 설명에는 계산을 강요하지 않아야 한다. 품과 금액도 구분해야 한다. 품을 계산할 수 있다고 단가까지 확보한 것은 아니다.

## 4. 사용자가 밝힌 사업·제품 조건

- 금액이 나오는 서비스이므로 숫자 정확성, 근거 제시, 재현성이 최우선이다.
- 응답 시간은 중요하다. LLM API 비용은 설계의 주된 제약으로 삼지 않아도 된다고 했다. 다만 **현재 실험에서 API 호출을 금지한 제약은 별개로 유지**된다.
- 개발자는 한 명이며 코딩 에이전트의 도움을 받는다. 운용할 구성 요소와 수작업 유지보수 부담을 줄여야 한다.
- 공종은 천 개 이상이고 앞으로 더 늘 수 있다. 사용자는 “만 개라면 명세를 다 수작업으로 찾을 것이냐”고 강하게 문제를 제기했다.
- 목표는 품셈 내 모든 견적 경우의수를 다루는 것이다. 이것은 장기 제품 목표이며 현재 모든 경우를 안전하게 지원한다는 뜻이 아니다.
- 결과물은 **가정이 표시된 초안**이다. 초안이라는 이유로 원문 오류나 임의의 숫자를 허용하는 것은 아니다.
- Excel은 사용자가 최소한의 수정으로 바로 업무에 활용할 수 있는 품질을 원한다. 단순 채팅 요약을 표로 옮기는 수준으로 목표를 낮추지 않는다.
- 아버지가 실무자여서 피드백을 부탁하고 있다. 그러나 지금 당장 검토를 받을 수 없다고 했다. 모든 진행을 실무자 승인 대기로 막지 않는다.
- 자재 거래단가와 장비가격을 공공데이터포털에서 확보하는 방안을 고민 중이다. 실제 물가정보·물가자료 등 회사 발행 자료는 이용이 어려울 것으로 보았다. 특정 데이터셋의 사용 가능성, 권리, 단위·지역·시점·갱신 주기, 품셈 자원명과의 대응은 아직 확정하지 않았다.
- 초기 답변 중 번호만 있고 원래 질문이 현재 문맥에 없는 “어려울 것 같다”, “잘 모르겠다”는 답변은 특정 사업 제약으로 임의 해석하지 않는다.

## 5. 시작 시점의 문제와 해석 수준

아래는 처음 사용자가 직접 확인했다고 전달한 문제다. 이 인계 작성에서 각 운영 현상을 새로 재현한 것은 아니다.

| 문제 | 설계상 분리해서 봐야 할 원인 |
|---|---|
| 목록 질문에 “기계설비 9-3-2의 계산 명세 없음” 등 엉뚱한 답 | 잘못된 공종 검색과, 목록·설명을 계산 준비 흐름에 종속시키는 문제가 겹칠 수 있음 |
| 콘크리트 타설 노무비에 도로 포장 공종 검색 | 검색 표현, 용어 정규화, 순위 결합, 문맥 및 공종 범위 문제 |
| 펌프차 조건을 아홉 개나 물음 | 입력 필드가 있다는 이유만으로 모두 묻는 방식과 질문·가정 정책 부재 |
| 여러 공종 견적이 안 됨 | 항목별 상태·선택·조건 변경·계산과 전체 합산의 대화 조정 문제 |
| LLM이 자동 생성한 계산 명세 중 약 절반만 검사 통과, 사람 검토 없음 | 형식 검증과 원문 의미·단위·계산 정확성 검증이 같지 않음 |
| 질문별 운영 기록이 부족함 | 검색, 조건 추출, 계산 명세, 단가 중 어디서 틀렸는지 분리하기 어려움 |

실험에서 파싱 손실도 확인했다. 따라서 “에이전트 프롬프트만 고치면 된다” 또는 “파싱만 바꾸면 끝난다”는 설명은 둘 다 부정확하다.

## 6. 전체 권장 구조와 책임

아래는 대화와 기획 문서에서 이어 온 권장 방향이다. 모두 운영에 구현됐다는 뜻은 아니다. 구체적 인터페이스와 저장소 선택은 후속 설계 대상이다.

```text
원문 PDF와 문서 버전
  → 파서와 후처리: 표·글·위치를 추출
  → 원문 구조 보관: 셀·기준·주석·소속·참조·불확실 상태
  → 검색 표현: 공종 목록, 규칙 문장, 표와 작업 조건
  → 검색 후보와 선택: 관련 공종과 근거를 찾음
  → 근거 조립: 필수 주석·부모 문맥·필요한 참조 원문
  → 대화와 견적 상태: 의도, 항목, 조건, 가정, 질문
  → 검증된 계산 지식 + 서버 계산기 + 버전이 있는 단가
  → 항목별 결과와 합산 → 견적서와 Excel

모든 단계에 원문 추적, 버전, 상태, 평가와 실행 기록을 연결
```

### 6.1 원문 구조와 검색 표현을 분리하는 이유

원문 표의 셀과 병합 범위는 원본의 뜻을 보존하기 위한 것이다. 검색용 글은 사용자의 표현과 원문을 잘 연결하기 위한 것이다. 용도가 다르므로 하나의 문자열을 두 목적의 유일한 원본으로 쓰지 않는 방향이다.

예를 들어 63/55가 세 직종 행에 걸친 공동 시공량이면 원문에는 값이 하나씩 있다. 검색용 글에는 이해를 위해 각 행에 반복할 수 있지만, 계산이 세 개의 독립 시공량으로 합산하면 안 된다. 원문 셀 식별자와 적용 행을 보존하면 이 차이를 설명할 수 있다.

이것이 곧 데이터베이스 제품을 바꾼다는 뜻은 아니다. 처음에는 파일이나 기존 저장소로도 실험할 수 있다.

### 6.2 부모·자식, 공종 목록, 규칙 검색, 참조 조회는 함께 쓸 수 있다

사용자가 “네 개를 다 하면 안 되나”라고 물었다. **서로 다른 책임이므로 함께 쓰는 방향**이다.

- 공종 목록은 무엇을 찾을지 돕는다.
- 규칙 검색은 표 숫자보다 할증·제외·적용 조건 같은 문장을 찾는다.
- 부모 문맥과 필수 주석은 짧은 검색 결과의 의미를 보완한다.
- 참조 조회는 같은 절 밖의 필요한 규칙을 가져온다.

짧은 절은 절 전체를 부모로 먼저 비교할 수 있다. 큰 절과 표는 공법·조건·공동 값이 완결되는 묶음으로 나눈다. 모든 셀과 직종 행을 무조건 독립 청크로 만들지 않는다. “철근공”이라는 단어가 반복된다는 이유로 서로 다른 공종을 연결하지 않는다.

관계에는 문서 버전, 부문, 절, 위치, 연결 종류, 조건 원문, 확정 여부를 남긴다. 그래프처럼 연결을 표현할 수 있지만 GraphRAG 전체 구성이나 그래프 전용 데이터베이스 도입이 필수라는 결론은 아니다.

### 6.3 LLM의 역할과 서버의 역할

LLM은 짧은 문장의 의도, 작업 항목, 공법 후보, 사용자 조건과 변경 의도, 근거에 따른 설명을 돕는다. 오프라인 지식 생성 단계에서 계산 명세 후보를 만드는 역할도 가능하다.

서버는 허용된 행동과 입력 형식, 항목과 조건의 연결, 단위, 계산 사용 가능 상태, 상태 변경과 실제 계산을 관리한다. 대화에서 LLM이 산식을 즉석 생성해 금액을 확정하는 구조를 기본으로 삼지 않는다.

서버 검증도 모든 자연어 의미를 보장하는 마법 장치는 아니다. 형식·단위 검사로 잡을 수 있는 오류와 문맥 해석이 필요한 오류를 구분하고 불확실한 변경은 확인 가능한 상태로 남긴다.

### 6.4 무엇을 묻고 무엇을 가정하는가

공종별로 질문 아홉 개를 수작업으로 따로 정하는 대신, 입력마다 결과에 미치는 역할을 보관하고 일반 정책으로 질문을 고르는 방향이다. 아래는 권장 설계이며 이미 구현된 정책이 아니다.

- 공법·적용 가능 범위·단위·물량처럼 선택이나 계산 자체를 바꾸는 정보는 우선 확인한다.
- 사용자가 이미 말한 조건을 다시 묻지 않는다.
- 근거가 있거나 서비스 정책으로 허용한 기본 가정은 가정임을 표시하고 사용자가 쉽게 수정하게 한다.
- 특정 보정이 영향을 주지 않는 조건은 선행 답변에 따라 생략할 수 있다.
- 손상된 표, 누락된 단위, 모르는 참조 조건을 “일반적인 현장”이라는 가정으로 덮지 않는다.
- 질문할 조건은 적용 여부와 결과 영향에 따라 우선순위를 매긴다. 모든 조합을 전수 계산하거나 공종마다 수작업 규칙을 만들겠다고 약속하지 않는다.

정확한 기본값과 질문 우선순위 수치는 아직 결정되지 않았다.

### 6.5 다공종 견적과 Excel

여러 공종은 견적 하나 아래 여러 항목으로 관리한다. 각 항목은 자신의 공종 선택, 물량, 조건, 가정, 근거, 명세 버전, 단가와 계산 결과를 가진다. 공통 현장 조건은 항목별 적용 여부를 확인하며 공유한다.

“거푸집만 700㎡로” 같은 변경이 다른 항목을 덮어쓰면 안 된다. 항목을 모르면 활성 항목이라고 무조건 추정하지 않는다. 포함·제외·별도 계상을 확인해 같은 작업이 자동 중복 합산되지 않게 한다.

Excel은 동일한 구조화된 견적 결과에서 만든다. 총괄과 항목별 산출 근거, 물량·단가·가정, 출처와 수정 가능한 항목을 연결하는 방향이다. 구체적 시트 구성과 수식·서식 요구는 아직 확정하지 않았다.

### 6.6 계산 명세를 만 개 수작업으로 만드는가

그 방향이 아니다. 목표는 **자동 추출·생성 → 기계 검증 → 불확실성 구분 → 재사용 가능한 계산 방식 → 예외 검토**다. 동일한 계산 패턴과 단위 규칙을 재사용하고, 공종마다 코드 도구를 수작업으로 늘리는 부담을 줄인다.

다만 “LLM이 만든 JSON이 스키마를 통과했다”는 이유로 실행 가능 판정을 하지 않는다. 원문 값, 기준량, 단위 차원, 식의 입력과 출력, 조건 범위, 참조, 대표 사례의 계산을 확인해야 한다. 계산 가능한 범위와 읽기·설명만 가능한 범위를 구분한다.

최종 계산 명세 형식을 유지·수정·교체할지, 어떤 범용 계산 패턴을 둘지는 확정되지 않았다. 원문을 잘 파싱하면 계산 의미까지 자동으로 모두 맞는다는 보장은 없다.

## 8. 실제 진행 흐름: 왜 파싱 파일 하나까지 왔는가

1. 처음에는 전체 서비스 구조와 다섯 질문 유형을 검토했다.
2. 공종별 계산 명세의 확장성과 신뢰성 문제가 제기됐다.
3. 원문 표의 값과 조건 자체가 제대로 전달되는지 살폈다.
4. 사용자도 PDF와 기존 결과를 육안 비교했다. 중첩 표가 깨지고 장비사용 타설의 63/55가 빠진 점, 다른 절 참조가 중요한 점을 지적했다.
5. 기존 파서와 개선 후처리, ODL, Docling 등을 비교하는 외부 실험을 진행했다.
6. ODL 출력과 기존 후처리로 185쪽을 다시 보여 줬고 사용자는 많이 나아졌다고 평가했다.
7. 숫자를 잘 뽑는 것 외에 저장 구조와 청킹, 부모 문맥과 참조 조회가 필요하다는 논의를 진행했다.
8. 실무 검색 사례를 조사하고 185쪽·555쪽을 중심으로 근거 묶음 시제품을 만들었다.
9. 실제 6-1-1 → 6-1-3 참조 조회를 확인했다.
10. 공종 목록·규칙·표 표현의 오프라인 검색을 비교했으나 전체 순위 개선은 확인하지 못했다.
11. 이때 6-1-3의 `(100㎡당)` 등 원문 기준이 기존 청크에 없음을 확인했다.
12. 문제를 작은 단위로 좁혀 186쪽, 195쪽, 645쪽의 누락 원인을 기존 글자 필터까지 추적했다.
13. 줄별 필터와 반복 기준 보존 수정안을 메모리에서 시험하고 기존 청킹으로 연결했다.
14. 실제 PDF 세 개발 쪽과 신규 여섯 쪽에서 제한된 회귀 검사를 했다.
15. 사용자가 별도 작업 폴더에서 파싱 파일 하나의 실제 수정을 허용했다.
16. 실제 적용 뒤 승인 범위를 벗어난 구간별 머리글 필터를 추가 확인하고 두 줄을 제거했다. 이것이 현재 최종 코드 상태다.

작은 파싱 수정은 큰 계획을 폐기한 결과가 아니다. 비교 실험을 진행하다 발견한 기초 데이터 결함을 닫는 과정이다. 다만 이 수정이 끝나면 큰 계획에서 어느 결정을 진행할지 돌아봐야 한다.

## 9. 이전 조건 변경 검증 시제품도 잊지 말 것

사용자가 공유한 이전 소넷 보고에는 `set_conditions`와 구조화된 편집 검증기의 비교가 있었다. 지금 파싱 작업과는 다른 대화·상태 관리 과제다.

```json
{"item":"current","field":"vibrator_used","value":false,"unit":null,"evidence":"진동기 안 쓰는","negated":true}
```

항목·조건·값·단위·근거·부정 여부를 명시하고 서버가 확인한다는 시제품이다. 사용자 제공 보고 기준으로 직접 만든 추출 결과 47건에서 올바른 20건을 받고 잘못된 27건을 거부했다. 기존 방식은 올바른 13건을 받고 잘못된 9건을 통과시켰다고 보고됐다.

중요한 한계:

- LLM 추출 결과를 실제 API로 받은 검사가 아니다. 사람이 추출 구조를 직접 넣었다.
- 개발 과정에서 사례를 추가·조정했으며 독립된 새 평가 집합의 성능이 아니다.
- 조건 연결과 부정은 경험적 규칙에 의존했다.
- 세 명세만 검사했고 `current`가 가리키는 항목의 모호함은 해결하지 않았다.

방향의 근거로 보존하되 운영 도입 완료 또는 자연어 이해 완벽이라는 근거로 사용하지 않는다. 사용자 단위와 조건을 안전하게 바꾸는 과제는 여전히 남아 있다.

## 10. 파서·근거 조립 실험에서 얻은 사실

### 10.1 ODL과 기존 후처리

ODL은 OpenDataLoader를 가리킨다. “기존 후처리”는 추출된 표를 행·열 조건과 값의 레코드로 만드는 기존 파이프라인 로직이다. 공종별 수작업 입력을 새로 한다는 뜻이 아니다.

185쪽 확인 문서에서는 기존 ODL JSON에 `odl_tables.read_tables(split_rows=True)`, `table_guard.guard`, `assemble.table_to_records`를 적용했다. 장비사용 타설의 인력·장비와 63/55, 비고 안 작은 정의 표를 읽을 수 있었다.

이 결과에서 기준과 주석을 함께 보여 줬다는 것과 운영 청킹·계산에 자동 반영됐다는 것은 다르다. 라이브러리 비교의 과거 세부 점수를 새 의사결정에 사용할 때는 해당 원 보고와 후처리 조건을 다시 확인한다. 이 인계에서는 작은 표본의 우열을 전체 문서 정확도로 환산하지 않는다.

### 10.2 185쪽 근거 묶음

- 장비사용 타설: 콘크리트공 3인, 보통인부 1인, 굴착기 1대. 무근·철근 시공량 63/55는 각 한 셀의 공동 값이다.
- 표 안 비고, 작은 정의 표, 표 아래 주석, 상위 절 문장을 함께 보관했다.
- 상위 “본 품” 문장의 적용 범위와 표 아래 주석 소속은 모두 확정된 것이 아니다. 위치 기반 연결과 원문 명시 연결을 구분했다.
- 옛 보고의 “합산·곱셈 금지”는 지나치게 넓은 표현이다. 후속 보고에서 **같은 시공량을 여러 행에 표시했다고 중복 합산하지 않는다**로 수정했다. 정상적인 물량·작업일수·인력 계산을 금지한 것이 아니다.

### 10.3 555쪽과 표 보류

원문 13행이 뒤 단계 `assemble.py`의 `unstack`에서 23레코드로 갈라지는 문제를 확인했다. ODL 원본 칸이 정상인 부분도 후처리에서 망가질 수 있었다.

`영상지도 편집1`과 `.00`처럼 1.00의 글자 하나가 옆 칸으로 간 결함은 자동 수정하지 않고 표를 보류했다. 결함 칸이 없는 일부 묶음에도 표 전체 보류 상태를 전달하도록 시제품을 보완했다.

시제품 보고의 32표 중 18표 이상 없음, 13표 행 대응 확인 필요, 1표 보류는 구조 점검 상태다. 18표의 계산 의미가 모두 승인됐다는 뜻이 아니다. 글자·숫자가 보존됐다는 검사와 행·열 연결이 맞다는 검사를 구분한다.

### 10.4 실제 참조 조회

185쪽 주석은 “미장공에 의한 표면 마무리가 필요한 경우 [공통부문] 6-1-3 표면 마무리”를 따른다고 한다.

- 공통 186쪽의 6-1-3을 찾았다. 같은 번호가 있는 건축 659쪽, 기계설비 736쪽은 대상이 아니다.
- 대상: `(100㎡당)`, 미장공 / 인 / 0.34, 쇠흙손 마감에 관한 주석.
- 제목 발견, 자료 확보, 실제 내용 전달을 따로 기록했다.
- 조건 판정과 비용 자동 추가는 하지 않았다.
- 실제로 확정한 참조 종류가 제한돼 있어 복잡한 다단계 참조 일반화는 미검증이다.
- 근거 길이 한도 때문에 필수 근거가 빠지면 완료로 표시하지 않도록 보완했다. 같은 절의 다른 표가 계수 등 필수 근거일 수 있으므로 무조건 선택 자료로 취급하지 않는다.

## 11. 검색 실험의 결론과 잘못 이어받기 쉬운 표현

질문 20개를 고정하고 한 번 실행했다. 가는 기존 청크의 BM25, 나는 질문 의도별 목록·규칙·표 중 한 검색 표현, 다는 나의 같은 순위에 근거 조립을 더한 것이다.

- 기대 공종이 있는 18문에서 상위 1개 적중 14건, 상위 5개 17건으로 가·나가 같았다.
- 목록 등 일부 질문은 좋아졌으나 1㎥ 품, 노무비, 표면 마무리 등은 나빠진 부분이 있었다.
- 다는 근거 위치·필수 주석·조건부 참조와 미확정 상태를 전달했다. 잘못된 1위 공종 자체를 고치지는 않았다.
- 근거 글자 적중 11문은 가 10, 나 단위 8, 나+부모 9, 다 10으로, 다가 기존을 넘었다고 말할 수 없다.
- 숫자와 단위 붙여쓰기, 복합 명사와 현장 표현, 반복 문구, 짧은 청크의 순위 이점, 표 색인에 없는 주석, 답 없음 판별 부재 등이 실패 원인으로 보고됐다.

이 실험의 질문 의도와 다공종 작업 분리는 사람이 입력했다. 자동 에이전트가 성공한 결과가 아니다. 운영의 BM25+벡터 전체 검색과 실제 LLM 답변도 검사하지 않았다.

“1㎥ 품”을 묻는다고 자동으로 현장비빔타설이 정답인 것은 아니다. 원 보고의 “1㎥ 기준 대표 표” 표현을 공법 선택 규칙으로 가져오지 않는다. 공법을 먼저 구분하고 다른 기준량도 적절히 환산할 수 있어야 한다.

따라서 검색 표현과 후보 결합을 다시 비교할 여지는 있지만, 새 색인 구조가 우월하다고 이미 결론 났다는 전제로 다음 작업을 지시하지 않는다.

## 12. 현재 파싱 수정의 정확한 내용

기준 코드 `pipeline/parse.py`의 `read_text_blocks`는 PDF의 글자 블록 전체를 대상으로 제외 여부를 판정했다.

- 186쪽: `(100㎡당)`과 표 내부 글자가 같은 블록이고 블록 중심이 표 안이라 기준까지 제거됐다.
- 195쪽: `(개소당)`도 같은 유형이었다.
- 645쪽: 절 제목과 `(㎡당)`이 같은 블록이고 블록이 제목으로 시작해서 기준까지 제거됐다.

수정은 제목과 표 안 글자를 **줄별로 제외**한다. 제외할 줄이 없으면 원래 묶음과 위치를 유지하고, 일부가 제외되면 남은 연속 구간만 묶는다. 표 안 판정은 줄 중심과 표 경계 ±2pt를 사용한다.

독립된 기준 레코드 `(…당)`은 같은 절에서 여러 표 앞에 반복되더라도 문자열 중복 제거에서 보존한다. 일반 설명과 표 행의 중복 제거 정책은 이번에 바꾸지 않았다.

기존 청킹 함수는 같은 절·같은 쪽의 바로 앞 기준을 `pending_basis`로 기억해 다음 표의 `basis`에 연결한다. 확인한 사례에서는 파싱에서 기준을 살리면 청킹 수정 없이 연결됐다.

초기 구현에는 남은 구간마다 머리글 정규식을 다시 검사하는 조건문이 추가돼 있었다. 정수만 남은 본문 구간을 버릴 수 있어 가상 입력으로 확인했고 이후 두 줄을 제거했다. 현재는 기존처럼 블록 단위 머리글 판정만 남아 있다.

## 15. 데이터 갱신 전에 고려할 ID와 원문 추적 문제

추가 기준 레코드 때문에 뒤쪽 줄글 청크 ID가 바뀔 수 있다. 예를 들어 186쪽 `x4→x5`, `x16→x17` 같은 이동이 보고됐다. 글 내용이 같아도 위치 기반 순번은 달라진다.

- `record_ids`가 전체 파싱 레코드 순번이면 `parsed`와 `chunks`가 서로 같은 생성 결과를 가리켜야 한다.
- 벡터에는 ID와 글 해시를 이용한 누락·오래된 값 검사가 있다는 앞선 코드 검토가 있다. 이것이 모든 인용·캐시·명세 참조의 안전을 자동 보장하지는 않는다.
- `6-1-4_pump.json`의 `p186-x16` 설명, `adjustments.py`의 `p80-x0`, 숫자 ID 비교, 평가 자료와 초안의 인용 등 점검 대상이 기록돼 있다. 실제 영향은 갱신 전에 해당 기준 코드와 대조해야 한다.
- 향후에는 원문 문서와 버전·위치에 연결된 안정적인 식별 방식과 갱신 단위를 설계하는 것이 후보지만, 현재 패치에 ID 전면 개편을 끼워 넣기로 결정한 것은 아니다.

## 16. 평가와 실무자 검토의 기준

사용자는 LLM에게 PDF를 보고 골든셋을 만들게 한 것이냐고 물었고, 이미 관련 작업을 시켰다고 했다. 따라서 기존 기대값과 평가 초안을 버리고 처음부터 전부 다시 만들게 하지 않는다.

평가 데이터에는 최소한 다음 성격을 구분하는 방향을 유지한다.

- 원문에 실제로 인쇄된 값과 단위 및 위치.
- 원문에서 계산한 기대값과 계산 과정.
- 기존 코드가 낸 값.
- LLM이 추론하거나 작성한 초안.
- 실무 해석 확인이 필요한 조건.

LLM이 만든 정답을 같은 LLM과 같은 로직으로 검증했다고 독립된 정답으로 부르지 않는다. 개발에 사용한 표본은 다시 실행해도 새 평가 표본이 아니다. 사람이 검토할 수 없다는 이유로 모든 검사를 중단할 필요도 없다.

파싱 셀 정확성, 행·열 연결, 검색 적중, 필수 근거 전달, 조건 추출, 최종 상태, 숫자 계산, Excel 일치, 응답 시간을 각각 평가한다. 한 층의 성공을 다른 층의 성공으로 대신 보고하지 않는다.

목차에 대한 이전 조사에서는 저장된 청크에 PDF 목차 쪽이 없다고 확인한 기록이 있다. 파서 전체에 목차 자동 제외가 보장된다는 뜻은 아니다. 향후 전체 재생성에서는 목차를 탐색용 목록에 쓸지와 답변 근거로 쓸 본문을 구분한다. 현재 인계에서는 목차 검사를 다시 실행하지 않았다.

## 17. 앞으로의 큰 계획: 상위 다섯 단계

아래는 기존 기획과 지금까지의 결과를 묶은 진행 지도다. 새로 전부 실행하도록 승인한 목록이 아니다. 각 단계는 작은 검토 가능한 작업으로 나누되 큰 목표에서의 위치를 먼저 설명한다.

| 단계 | 목적과 주요 작업 | 완료 판단 |
|---|---|---|
| 1. 원문을 믿을 수 있게 보관 | 현재 기준 누락 패치를 정리하고, ODL+후처리 등 후보와 기존 방식의 채택 범위를 결정. 표·병합·기준·주석·원문 위치·불확실 상태 보관 | 확인된 오류 유형을 숨기지 않고, 구조와 값이 원문에 연결되며, 파서 선택과 검증 범위가 설명됨 |
| 2. 올바른 공종과 필요한 근거를 찾기 | 구조 기반 청킹, 목록·규칙·표 후보 결합, 부모·필수 주석·명시적 참조를 함께 비교 | 공종 후보 정확성과 근거 완성률을 별도로 제시. 잘못된 연결과 답 없음 사례도 포함 |
| 3. 계산 지식을 자동 생성하고 검증 | 반복 계산 패턴, 원문 값·단위·산식·조건·참조의 검증, 사용 가능 상태와 연도 개정 추적 | 실행 가능한 범위와 보류 범위가 분명하고 대표 계산을 입력·원문·명세 버전으로 재현 가능 |
| 4. 질문과 견적 상태를 개선 | 목록·설명·품·견적 의도, 구조화된 조건 편집, 질문·가정 정책, 여러 공종의 상태와 합산 | 다섯 요청 유형이 목적에 맞게 동작하고 다른 항목의 조건을 오염시키지 않음 |
| 5. 실무용 Excel과 운영 품질 정착 | 단가 데이터 정책, 견적 결과와 Excel 일치, 가정 수정, 기록·평가·갱신·복구 절차 | 사용자 검토에 필요한 근거와 가정이 보이고, 같은 버전으로 결과를 재현하며, 오류 원인을 추적 가능 |

평가와 기록은 마지막까지 미루는 별도 장식이 아니라 모든 단계에 붙인다. 데이터 전체가 완벽해질 때까지 목록·설명 개선을 무조건 막는 뜻도 아니다. 의존성을 지키면서 가치가 큰 작은 단위를 선택한다.

현재 위치는 **1단계 안의 기준 누락 패치가 실제 파일에 반영된 시점**이다. 2단계의 근거 조립과 검색 비교 시제품도 이미 일부 진행했다. 선형으로 아무것도 안 한 상태가 아니다.

## 18. 새 세션에서 지금 할 일과 하지 말아야 할 오해

처음에는 이 문서를 읽고 아래 내용을 짧게 설명한다.

> 대목표는 근거 있는 품·다공종 견적과 실무용 Excel이다. 파싱·청킹·검색·계산 지식·에이전트를 순서와 책임을 나눠 개선하고 있다. 지금은 기준 문구 누락 패치가 별도 폴더에 반영됐고 제한된 검사를 통과했다고 보고됐다. 운영 데이터는 아직 갱신하지 않았다.

그다음 사용자의 최신 요청을 따른다. 소넷의 최신 결과를 검토하는 것이 필요한 경우 `remove-parse-run-header-filter-result.md`가 현재 마지막 보고임을 알고 시작한다. 없는 결과를 기다리라고 하거나 최초 구현을 다시 시키지 않는다.

다음 실행을 제안할 때는 현재 패치를 완료된 범위로 묶을 수 있는지, 남은 위험 중 다음 파서·데이터 채택 결정을 실제로 바꿀 것이 무엇인지 먼저 정리한다. 이미 답이 난 아홉 쪽을 새 평가라고 반복하지 않는다. 전체 재처리가 필요하다면 범위, 출력 위치, 비교 기준, 시간·자원, 데이터와 ID의 일관성을 검토 가능한 지시서로 먼저 구체화한다.

새 세션이 피해야 할 오해:

1. “파싱 한 파일 수정”을 전체 목표로 받아들이지 않는다.
2. “소넷 결과 대기” 상태라고 잘못 시작하지 않는다. 최신 결과와 실제 수정이 있다.

4. 파싱이 좋아지면 청킹·검색·계산 명세·대화가 모두 자동 해결된다고 하지 않는다.
5. 공종마다 손으로 명세를 다 만들자는 계획을 기본값으로 되돌리지 않는다.
6. 벡터 DB와 LLM의 자유 판단으로 숫자 검증을 대체하지 않는다.
7. 다른 절 참조를 가져온 것만으로 비용을 더하지 않는다.
8. 실무자 검토를 지금 당장 필수 선행 조건으로 새로 걸지 않는다.
9. 시제품 통과 수치를 운영 정확도나 전체 품셈 정확도로 말하지 않는다.
10. 이 인계 문서를 읽으라는 요청을 구현·API·데이터 교체 승인으로 해석하지 않는다.
