## 6. 구현 요구

### 6.1 원래 칸과 해석 결과를 함께 남긴다

원문 PDF가 최종 근거다. ODL 출력도 틀릴 수 있으므로 ODL과 같다는 검사는 원문 정확성 검사와 구분한다.

최소한 아래 정보를 보존한다.

- 문서와 입력 버전, 처리 쪽, 추출 및 변환 기준
- 표 식별자·쪽·좌표·행·열·원래 병합 범위
- 원래 칸 식별자와 줄바꿈을 포함한 글
- 하위 행이나 조각을 만들었다면 원래 칸과의 연결, 분리 근거와 상태
- 공동 값이 적용되는 행 또는 작업 묶음
- 기준·주석의 원문과 위치, 기존 시제품에서 확보한 소속과 확정 여부
- 작은 표가 들어 있는 칸과 작은 표의 연결
- 추출 이상·행 대응·근거 연결의 불확실 사유

빈칸, `-`, `〃`, 숫자 0을 같은 값으로 만들지 않는다. 정리한 글이나 숫자 후보를 만들어도 원래 표기는 유지한다. 없는 단위나 좌표를 임의로 채우지 않는다. 문단 높이로 추정한 줄 좌표와 실제 원문 좌표를 구분한다.

### 6.2 잘못된 행 분리와 공동 값 복사를 막는다

555쪽에서 원문 작업명 안의 줄바꿈이 가짜 작업 행으로 늘어난 원인은 조립 단계의 `unstack` 규칙으로 보고됐다. 이번 수정에서는 이 오류가 새 전달 경로에 다시 들어오지 않게 한다.

원래 칸 구조를 먼저 보존하고 행 분리 판정은 명시적으로 한 번 관리한다. 어댑터가 이미 나눈 행을 조립 단계가 근거 없이 다시 나누지 않는다. 줄 수가 우연히 같다는 이유로 여러 작업이라고 확정하지 않는다.

기존에 실제 하위 행을 구분할 수 있던 표를 무조건 한 행으로 합치는 방식도 피한다. 이번 범위에서 행 대응을 확정할 근거가 없으면 칸과 대응 후보를 남기고 해당 표의 계산 사용을 보류한다. 다른 보류 표 13개를 모두 해결하는 작업으로 확대하지 않는다.

185쪽의 63/55는 원래 칸 하나씩과 세 직종의 연결로 보관한다. 검색용 글이나 전달 레코드에 반복 표기하더라도 같은 칸을 가리키게 한다. 값이 여러 번 보인다고 독립된 시공량으로 취급하지 않는다.

### 6.3 위치가 다른 반복 기준과 주석을 보존한다

글자만 같다는 이유로 원문 항목을 삭제하지 않는다. 807쪽에서 반복되는 기준과 주석이 각자의 위치와 기존에 확인한 소속 후보를 유지해야 한다.

기존 시제품의 소속 후보를 전달하되, 위치로 추정한 관계를 원문에 명시된 확정 관계로 바꾸지 않는다. 다음 쪽 주석이나 번호 없는 소제목의 새로운 연결 규칙은 이번에 구현하지 않는다.

### 6.4 기존 청킹에 전달 가능한 입력을 만든다

보관 결과에서 `kind`, `section`, `page`, `table_id`, `bbox`, `structure`, `text` 등 기존 `chunk.make_chunks`가 요구하는 입력 필드를 생성한다. 기존 청킹 함수를 변경 없이 호출해 결과까지 확인한다. 함수 호출로 기존 운영 결과를 덮어쓰지 않는다.

기존 레코드 형식에 없는 칸·공동 값·주석 관계는 원문 연결 정보로 함께 남긴다. 출력 레코드와 청크가 어떤 원문 항목을 가리키는지 식별자로 연결한다. `text` 문자열만 유일한 보관 원본으로 사용하지 않는다.

이번 결과 안의 ID는 충돌 없이 재현 가능하게 만들되, 기존 운영 ID와 같거나 파서가 바뀌어도 영구적으로 안정적이라고 주장하지 않는다. 변환 레코드·청크·연결 정보는 같은 생성 결과를 가리켜야 한다. 기존 운영 ID의 전체 대응 작업은 이번 범위에 넣지 않는다.

단순히 과거 `store_all_tables.json`을 읽어 출력한 것으로 끝내지 않는다. 기존 원시 ODL 입력 → 재사용한 보관 처리 → 수정된 정리·내보내기 → 기존 청킹 호출을 코드로 재현할 수 있어야 한다. 과거 보관 출력은 비교 자료로 사용한다.

### 6.5 훼손과 불확실성을 다음 단계까지 전달한다

555쪽의 `영상지도 편집1`과 `.00`을 추정해 수정하지 않는다. 해당 표의 문제 표시와 계산 보류가 결함 칸 없는 작업 묶음에도 전달돼야 한다.

구조를 판단하지 못한 결과를 `ok`로 바꾸지 않는다. 보관 결과의 상태를 기존 청킹의 불확실 상태로 옮기는 규칙을 문서화한다. 청킹의 구조 `ok`는 계산 명세 승인과 다르다.

이번에는 계산기나 계산 명세를 변경하지 않는다. 이 데이터의 후속 소비자가 구분할 수 있는 문제·보류 정보를 출력까지 남기는 것이 완료 범위다.

| 변경 범위 | 수정 파일과 생성 파일이 허용 범위 안에 있고 기존 원본·패치·시제품·데이터가 유지된다 |

원문 대조와 ODL 입력 보존 검사, 가상 입력 기능 검사를 각각 구분해 보고한다. 모든 확인 항목을 억지로 통과시키지 않는다. 중요한 항목을 충족하지 못하면 실패 또는 미완료로 기록하고 현재 범위에서 가능한 부분까지 마무리한다.

추가 회귀 확인에서 실패가 발견되면 이번 코드 변경의 영향인지 구분한다. 해결에 새로운 원문 처리나 다른 파일 변경이 필요하면 작업을 무한히 확대하지 말고 남은 문제로 제출한다.
