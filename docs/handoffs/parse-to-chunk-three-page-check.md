# 이번 작업 하나: 실제 PDF 세 쪽에서 파싱부터 청킹까지 확인

## 목적

지금까지 준비한 두 수정안을 합쳐 **실제 PDF 186·195·645쪽의 파싱 결과를 메모리에서 만들고, 기존 청킹 함수까지 전달**한다. 가상 입력으로만 확인했던 연결을 실제 파싱 레코드로 확인하는 단계다.

운영 파일에는 적용하지 않는다. 이번에는 외부 API 없는 로컬 읽기 전용 검사로, 기존 파서 함수를 메모리에서 실행하는 것을 허용한다. 앞선 작은 검사의 '새 파서 실행 금지' 범위는 이번 실제 흐름 검사에는 적용하지 않는다. 새 라이브러리 설치나 ODL·Docling 실행은 허용하지 않는다.

## 한 번의 비교 실행

1. 기준 코드를 메모리에 읽는다. 기준 코드 그대로인 경우와, 아래 두 수정안만 반영한 경우를 별도 메모리 모듈로 만든다.
   - `read_text_blocks`: 제목·표 안 글자를 줄별로 제외하되 일반 설명 묶음 유지.
   - `parse_pages` 중복 제거: 독립된 기준 레코드는 같은 글이어도 보존.
2. 각 경우에 PDF 186·195·645쪽을 각각 실제 `parse_pages`로 처리한다. 원본 PDF는 읽기 전용이며 `parsed` 파일을 쓰지 않는다. 페이지별로 실행했다는 범위와 이전 쪽 문맥의 한계를 기록한다.
3. 실제 생성된 레코드를 기존 `make_chunks`에 전달한다. 부문은 기존 기준 자료에서 명시적으로 넘겨 `page_map` 생성·설정 로더 실행을 피한다. 청킹 함수를 수정하거나 `basis`를 정답으로 직접 대입하지 않는다.
4. 다음 결과를 비교한다.

| 대상 | 확인할 기준 |
|---|---|
| 186쪽 6-1-3 표 | `(100㎡당)` |
| 195쪽 6-3-5 표 | `(개소당)` |
| 645쪽 4-1-1 표 | `(㎡당)` |
| 645쪽 4-1-3·4-1-4 표 | 각각의 `(일당)`이 남는지. 같은 절의 반복 기준 검사와 혼동하지 않음 |

표 순번이 기존 결과와 다르면 제목·좌표로 대응을 확인하고 이유를 기록한다. 기존 `p...-t...` 번호만 믿고 다른 표와 비교하지 않는다.

5. 같은 실행에서 표 값·제목·주변 주석의 변화도 확인한다. 기존 값·주석이 사라지거나 바뀌면 검사 실패로 보고한다. 청크 수와 줄글 ID의 변화는 기준 레코드 추가로 설명되는지 기록한다.

## 제약

- 저장소 코드·설정·데이터·루트 가상환경을 수정하지 않는다. 커밋·푸시·PR·배포는 금지한다.
- LLM·임베딩·네트워크 API, 운영 서버·DB, 비밀값 파일 읽기는 금지한다.
- 설치·다운로드·전체 문서 재파싱은 하지 않는다. 대상은 세 쪽뿐이다.
- 루트 `.venv/Scripts/python.exe`, `AGENT_OFFLINE=1`, `AGENT_LLM=off`, `PYTHONDONTWRITEBYTECODE=1`, `-B`로 검사한다. 기존 파서의 `main`을 실행하지 않고 함수만 호출해 출력 파일 생성을 막는다.
- 검사와 시제품은 메모리에서 수행한다. 결과 문서만 `docs/reviews/parse-to-chunk-three-page-check-result.md`에 작성한다.
- 실패 후 다른 규칙을 추가해 반복하지 않는다. 실패 내용과 원인을 보고하고 종료한다.

## 완료와 보고

첫 문장에 `실제 PDF 세 쪽에서 기준이 청크까지 전달됐다` 또는 실패한 대상을 적는다.

표에는 원문 기준, 기준 코드 청크의 `basis`, 수정안 청크의 `basis`, 표 값·주석 유지 여부를 보여준다. 기능 검사 입력이 아니라 실제 파싱 레코드를 사용했다는 점과, 세 개발 쪽만 검사했다는 점을 함께 적는다.

이번 검사로 전체 문서의 정확성·검색·계산 명세·운영 적용이 검증됐다고 하지 않는다. 알려진 제목 오인 가능성과 전체 적용 전 회귀 검사 필요성은 남긴다. 결과 문서의 절대 경로를 보고하고 종료한다.
