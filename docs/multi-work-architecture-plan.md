# 품셈이 복수 공종 견적 구조 설계

작성: 2026-10-07. 설계 문서이며 구현·배포 승인이 아니다.

## 1. 목표와 현재 상태

하나의 요청에 나온 최대 3개 공종을 빠짐없이 추적하고, 공종마다 올바른 물량·조건을 적용해 기존 계산기로 계산한다. 같은 공사의 직접비를 합쳐 하나의 원가계산서와 Excel을 제공한다. 계산하지 못한 항목과 금액에 포함되지 않은 범위를 명확하게 표시한다.

단일 공종도 동일한 구조에서 항목 하나인 견적으로 처리한다. 단일·복수마다 별도 계산 구현을 만들지 않는다.

비교 기준은 로컬 main 9a2af9f다. 현재 작업 브랜치는 claude/multi-work-estimate, 복수 공종 최초 커밋은 f412fa2이며 이후 변경은 작업 트리에 있다. 설계 검토 중 route.py와 신규 intent.py 변경도 관찰됐으므로, 구현자는 실제 변경 목록을 먼저 보존·확인해야 한다. 이 문서는 현재 작업을 자동으로 되돌리도록 지시하지 않는다.

main의 계산 흐름은 route → retrieve → select → fill → gate → compute → price → statement → compose다. 현재 브랜치는 split·collect·bundle을 추가해 이 흐름을 반복한다. compute·price·원가계산 함수는 main 대비 동일하다.

현재 문제는 다음과 같다.

- route·split·select가 질문 의도를 독립적으로 판단한다.
- 하나의 전역 query/inputs/result를 여러 공종으로 바꿔 끼운다.
- 장비 규격·실제 물량·공통 조건을 문장 규칙으로 분리하면서 예외가 늘었다.
- 분리 개선과 단일 공종 검색 개선을 함께 수정해 회귀 원인 구분이 어려워졌다.
- 체크 통과는 오프라인 검사 범위의 결과다. 실제 의미 검색·회원 저장·새로고침·화면 동작이 모두 검증됐다는 뜻이 아니다.

## 2. 선택한 구조

전체 견적을 관리하는 부모 그래프와 공종 한 개를 계산하는 작업 흐름을 분리한다. 초기에는 공종을 순차 처리하며, 별도 서버·큐·병렬 실행 시스템을 만들지 않는다.

```text
사용자 요청
  → interpret_request: 라우팅 + 공종 계획 생성
      ├─ 상담 → 기존 retrieve → answer
      ├─ 범위 밖 → 안내
      ├─ 불확실 → 확인 질문
      └─ 견적 → validate_plan
                   → run_items (공종별 독립 계산)
                       ├─ 확인 필요 → ask → apply_answers → run_items
                       └─ 처리가 끝남 → aggregate → compose → 응답/Excel
```

라우터의 역할은 유지한다. `interpret_request`는 그 역할과 공종 계획을 함께 관리하는 입구다. LLM을 사용하는 경우 분류와 계획을 하나의 구조화 호출로 생성해 분류용·분리용 모델 호출을 중복하지 않는다. split·select가 견적/상담을 다시 분류하지 않는다.

기존 compute·price·원가계산기를 재사용한다. 주로 재설계할 부분은 요청 해석, 상태의 소유권, 질문과 답의 연결, 반복 실행이다.

## 3. 요청 해석 정책

자유로운 한국어를 충분히 지원하려면 LLM 기반 구조화 해석기를 권장한다. LLM은 금액·품셈 계수·단가를 결정하거나 계산하지 않는다. 공종명, 사용자가 적은 물량과 단위, 조건, 조건의 대상만 추출한다. 품셈 검색과 실행 명세 확정은 서버가 담당한다.

LLM을 현재 켠다는 뜻은 아니다. 해석기 인터페이스를 다음 두 구현으로 분리한다.

- `RuleInterpreter`: 현재 LLM-off 모드. 명확한 입력만 해석하고 불확실하면 확인한다. 모든 자유 문장을 이해한다고 약속하지 않는다.
- `StructuredInterpreter`: LLM을 별도로 활성화했을 때 사용. 요청당 한 번의 정상 구조화 호출을 목표로 한다. 재시도는 상한을 둔다. 모델의 자체 확신도만으로 계산을 승인하지 않는다.

두 구현의 반환 형식과 서버 검증은 같다. LLM-off에서 임의로 유료 모델을 호출하지 않는다. 개발 검증은 모의 LLM 응답으로 한다. 실 API 평가와 비용 측정은 이후 별도 단계다.

서버 검증 규칙:

1. 모든 공종과 수량·조건은 원문 또는 사용자 답변의 출처를 가진다.
2. `100㎥`는 물량, `펌프차 32m`는 장비 규격으로 구분한다. 작업 단위와 규격 단위를 별도로 저장한다.
3. 생략된 물량·장비·자재 가격을 만들어내지 않는다.
4. 최대 3개를 넘으면 초과 항목을 버리지 않고 범위 조정을 요청한다.
5. 조건의 대상이 불명확하거나 값이 충돌하면 확인한다.
6. 모델 출력·사용자 입력은 스키마, 길이, 타입, 단위, 범위 검사를 거친다. 프롬프트의 지시를 실행 명령으로 취급하지 않는다.
7. 숫자나 필수 항목이 있는 작업을 무시한 불완전한 계획은 계산으로 넘기지 않는다. 추출 누락 여부를 확인할 수 없는 경우 사용자에게 해석 목록을 보여주고 수정할 수 있게 한다.
8. 견적과 상담이 섞이면 요청 유형을 명시해 확인한다. 첫 구현에서 둘을 조용히 한쪽으로 버리지 않는다.

## 4. 상태: 전체와 항목을 분리

전체 견적 상태는 다음을 가진다.

```text
EstimateSession
  schema_version, estimate_id, revision
  original_request, intent, basis_date
  common_conditions                 # 공사 종류·기간·업종·전체 규모 등
  items: {item_id: EstimateItem}     # 고정 ID, 표시 순서는 별도
  item_order
  pending_questions: {question_id: Question}
  aggregate_result, statement, diagnostics
```

공종 상태는 다음을 가진다.

```text
EstimateItem
  item_id, request_text, source_spans
  quantity: {value, unit, source} | null
  conditions: {field: {value, source, explicit}}
  selected_spec_id, candidates, citations
  status, reason
  computed_result, priced_result
  input_revision, result_revision
```

항목 상태의 소유자는 그 항목이다. 다른 항목의 inputs/result를 덮어쓰지 않는다. 원문은 불변으로 유지한다. 원문 텍스트를 공종별 조건 추출에 참고할 수는 있지만, 조건의 귀속을 문자열 복사로만 관리하지 않는다.

항목 상태는 `NEEDS_WORK`, `NEEDS_INPUT`, `READY`, `PRICED`, `UNSUPPORTED`, `NOT_FOUND`, `BLOCKED`, `ERROR`로 구분한다. 단가가 일부 없는 경우 PRICED 결과의 `partial`과 미산정 목록으로 표현한다. 상담 결과, 실행 불가, 부분 가격을 같은 result 형태로 캐스팅하지 않는다.

우선순위는 사용자 명시 수정 > 원래 요청의 명시 값 > 허용된 기본값이다. 기본값 적용 항목은 화면과 출력물에 표시한다. 공통 조건 충돌은 나중 값으로 조용히 덮어쓰지 않는다.

## 5. 공종 계산 흐름

```text
retrieve → select_work
                ├─ 불확실 → NEEDS_WORK 반환
                ├─ 실행 명세 없음 → UNSUPPORTED 반환
                ├─ 관련 후보 없음 → NOT_FOUND 반환
                └─ 확정 → resolve_inputs
                              ├─ 조건 부족/충돌 → NEEDS_INPUT 반환
                              └─ gate → compute → price → 항목 결과 반환
```

각 항목 작업은 자신의 상태를 받고, 변경된 자신의 상태만 반환한다. 검색·공종 선택·조건 확인은 기존 구현을 어댑터로 재사용하되, 선택 미확정 상태에서 후보 명세의 면적·규격을 먼저 묻는 동작은 제거한다.

공종별 작업은 `statement`를 실행하지 않는다. 부모가 통합 원가계산서를 만든다. 단일 공종은 항목 하나로 같은 경로를 타며, 기존 단일 공종과 수치·반올림·버림·세율이 같아야 한다.

처음부터 검색 품질 규칙을 새로 쓰지 않는다. 구조 이전과 검색 품질 변경은 별도 변경 단위로 진행한다. 검색 결과만으로 공종을 확정할 수 없으면 관련 후보를 제시하거나 작업 방법을 확인한다. 별칭·장 제목 개선은 고정 평가 세트로 검증한 뒤 추가한다.

## 6. 질문과 응답

사용자 질문은 부모 그래프의 ask에서만 중단·재개한다. 자식마다 중단 지점을 만들지 않는다. 항목 흐름은 필요한 질문을 데이터로 반환한다. 부모는 준비된 항목 결과를 저장하고, 필요한 질문을 적당한 묶음으로 보여준다. 공종 미확정 질문과 그 후보의 세부 조건을 동시에 묻지 않는다.

```text
Question
  question_id, estimate_id, revision
  scope: intent | common | item
  item_id (항목 질문일 때)
  field, kind, allowed_values, required, reason
```

응답은 question_id로 연결한다. `volume`처럼 필드명이 같아도 다른 공종 답이 섞이지 않는다. 표시 순서나 문자열로 답의 대상을 추정하지 않는다. 미응답·유효하지 않은 답은 질문으로 남긴다. 이미 저장한 유효한 답은 다음 요청에도 유지한다. 오래된 revision의 답은 현재 결과에 적용하지 않는다.

선택 응답에는 LLM을 호출할 필요가 없다. 자유 문장은 한 항목·한 질문의 문맥이 명확한 경우만 적용하며, 모호하면 대상을 묻는다. 자연어 답변의 LLM 해석도 활성화 정책과 호출 상한을 따른다.

## 7. 합산과 적용 범위

동일한 하나의 공사·계약 조건을 가진 항목만 통합 견적으로 묶는다. 공종별 직접 재료비·직접 노무비·직접 경비를 모으고 기존 원가계산 함수를 호출한다.

공사 종류·업종·규모 등 제비율 적용 기준이 충돌하거나 하나의 기존 계산 모델로 적용할 수 없으면, 조건 확인 또는 견적 분리를 요구한다. 서로 다른 계약의 금액을 합친 뒤 간접비를 무조건 한 번 적용하지 않는다. 복수 공종 지원은 자동 물량 산출이나 전체 공사 누락 검토 기능을 뜻하지 않는다.

미지원·보류·오류 항목은 합산에 넣지 않고 항목명·사유를 표시한다. 일부 항목이 미확인 상태라면 완료로 표시하지 않는다. 부분 결과를 미리 보여줄 경우 잠정 금액임을 명시한다. 처리 완료 후에도 미산정 항목이 있으면 부분 견적이다. 계산된 항목이 없으면 금액·완성 견적서로 제시하지 않는다.

버림·반올림은 main의 원칙을 보존한다. 항목 합계, 비목 합계, 통합 직접비 사이의 기존 자릿수 처리 차이를 명시하고 같은 원칙을 화면과 Excel에 적용한다. 표시 숫자를 맞추려고 임의 조정하지 않는다.

## 8. 수정·멀티턴

- 물량/장비/시공 조건 수정: 대상 항목의 작업 품·단가 결과를 무효화하고 재계산한 뒤 전체 합산.
- 공통 공사 조건 수정: 영향을 받는 제비율·통합 원가계산서를 다시 계산. 공종 직접비에 영향을 주는 필드이면 해당 항목도 재계산.
- 공종 변경: 그 항목만 후보·명세·조건을 재검증. 호환되지 않는 이전 조건은 유지하지 않음.
- “자동문만 5개로”: 항목을 식별해 수정하고 다른 항목은 보존.
- “수량을 5로”: 대상 항목이 여럿이면 확인. 전 항목에 적용하지 않음.
- 새로운 견적/재전송: 새 estimate_id 또는 revision 정책으로 시작하고 이전 대화 기록을 보존.

후속 수정에서 이미 저장된 계획을 사용한다. 매번 대화 전체를 다시 분리해 항목 ID가 바뀌도록 만들지 않는다. 기존 previous_context의 짧은 문자열만으로 복수 공종을 수정하지 않는다.

## 9. API·저장·운영

기존 인증·소유권 확인·회원 DB·게스트 저장 정책·대화 삭제·요청 중복 방지·요금 한도를 보존한다. 새 인프라나 Supabase 공종별 테이블은 첫 구현에 필요하지 않다. 계획과 항목 상태는 현재 체크포인트 저장소에 버전 있는 데이터로 저장한다.

회원의 부모 상태와 항목 결과는 기존 PostgresSaver/메시지 트랜잭션으로 저장한다. 자식은 별도 사용자 thread를 만들거나 단독으로 운영 DB에 저장하지 않는다. 게스트도 현재 메모리 정책을 유지하며, Cloud Run 재시작 이후 영구 보존을 약속하지 않는다.

서버는 request_id 기반 중복 응답 방지를 유지한다. 내부 공종 반복에서 usage_limits.consume을 추가 호출하지 않는다. 현재 사용량 차감 단위는 이번 구조 변경에서 조용히 바꾸지 않는다. 복수 공종으로 검색·임베딩 비용이 증가하는 것은 별도로 계측한다.

API에 estimate_id/revision/item_id/question_id를 추가하고, 프론트와 서버를 호환되게 이전한다. 기존 단일 공종 응답은 어댑터로 기존 필드를 제공한다. 과거 저장 답변은 그대로 읽을 수 있어야 한다.

진행 중인 구버전 대화는 마이그레이션 또는 제한된 legacy 재개 경로로 완료시킨다. 노드 이름 변경으로 대화가 사라지거나 다른 질문의 답으로 적용돼서는 안 된다. 새 견적부터 새 schema_version을 적용하고, 삭제 없이 이전 정책을 검사한다.

## 10. 화면

기존 랜딩·사이드바·색상·단일 공종 스타일을 보존한다.

1. 해석한 공종·물량과 기본 조건을 짧게 표시한다. 확실하면 매번 확인 버튼을 강제하지 않는다.
2. 필요한 확인 질문을 공종 이름과 함께 보여준다.
3. 전체 금액 또는 부분/잠정 금액, 포함 범위를 먼저 표시한다.
4. 현장 조건 반영과 Excel 다운로드를 유지한다.
5. 통합 원가계산서·내역서 아래에 공종별 상세를 접어서 제공한다.
6. 미지원·미산정·오류 사유를 공종별로 제공한다.

상세 표·Excel은 같은 항목 결과와 같은 합산 결과를 사용한다. 화면만 별도 재계산하지 않는다.

## 11. 구현 순서와 합격 기준

각 단계는 독립적으로 검증하고, 결과를 검토한 뒤 다음 단계로 간다. 코드가 없어진 전체 재작성이나 새로운 병렬 에이전트 시스템은 하지 않는다.

### A. 기준 고정

현재 커밋/미커밋 변경을 보존하고 main 기준 평가를 만든다. 명확한 단일 공종, 모호한 공종, 상담, 범위 밖, 원문 물량과 후속 수정, 기존 저장 대화를 포함한다. 계산 비교는 수치뿐 아니라 입력·단위·출처·후보도 비교한다. main 자체의 알려진 오동작은 보존해야 할 성공 사례와 구분한다.

### B. 독립 항목 계산과 부모 상태

자연어 없이 구조화된 두 공종 계획으로 먼저 검사한다. 공통 조건과 항목 조건을 분리하고, 같은 `volume` 질문 두 개에 각각 다른 답을 주었을 때 결과가 섞이지 않아야 한다. 순차 실행과 부모 ask/재개를 만든다. 기존 계산 함수를 유지한다.

### C. 합산·API·저장·수정

단일 항목이 main과 같은 금액을 내야 한다. 두 항목의 직접비 합산과 제비율 적용 범위, 부분 결과, 실패 항목, Excel, request_id 중복, 새로고침 복원, 구버전 대화 호환을 검사한다. 한 항목 수정은 다른 항목의 명시 값을 바꾸지 않아야 한다.

### D. 요청 해석 연결

일관된 단일 인터페이스로 라우팅과 계획을 생성한다. 규칙 해석은 보수적으로, LLM 해석은 모의 응답으로 검증한다. 말투 변형, 장비 규격, 물량 없는 공종, 동사 연결, 조건 충돌, 초과 공종, 혼합 질문을 포함한다. 공종 누락은 조용한 성공이 아니라 확인/명시 오류가 되어야 한다.

### E. 검색 품질·화면 검증

정답 후보 손실 7건을 고정 사례로 두고, 상담 경로에서도 기대 원문을 찾는지 검사한다. 새로운 관련성 판단과 별칭 개선은 구조 변경과 구분해 평가한다. 회원·게스트, 질문 응답, 부분 금액, 조건 수정, 새로고침, Excel을 실제 로컬 화면에서 확인한다.

처음에는 계획·최대 3개·순차 처리·기존 계산기·기존 DB로 제한한다. 도장 등 새로운 실행 명세, 전체 공사 자동 물량 산출, 무제한 공종, 병렬 실행, 결제, 배포 변경은 이 작업에 포함하지 않는다.

## 12. 구현자 전달 지시

이 문서를 읽고 먼저 단계 A/B의 구현 계획과 영향 파일을 보고한다. 사용자에게 확인받은 범위만 구현한다. 현재 작업 변경을 삭제하거나 main으로 덮어쓰지 않는다. 운영 DB·유료 AI API를 검사에 사용하지 않고 서버를 임의 종료하지 않는다. 배포·푸시·머지는 하지 않는다.

상태 분리는 자연어 인식률을 자동으로 높이지 않는다. 규칙 모드와 LLM 모드의 범위·한계, 실제 검사 범위와 미검증 범위를 구분해서 보고한다.
