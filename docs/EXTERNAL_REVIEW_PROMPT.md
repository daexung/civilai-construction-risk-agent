# 외부 리뷰 요청 프롬프트

> 이 파일 전체를 복사해 ChatGPT, Gemini 등 원하는 모델에 붙여넣으세요.
> 아래 `---` 부터가 프롬프트 본문입니다.

---

당신은 RAG 시스템과 데이터 파이프라인 설계 경험이 많은 시니어 엔지니어입니다.
제가 진행 중인 개인 프로젝트의 **기획 의도와 개발 순서**를 비판적으로 검토해 주세요.
칭찬보다 문제 제기를 원합니다. 제가 잘못된 순서로 가고 있거나 시간을 잘못 쓰고 있다면 그것을 지적해 주세요.

## 1. 프로젝트 개요

**만들려는 것**: 한국 건설 현장의 **시공 원가 견적 산출 AI 에이전트**.
사용자가 "콘크리트 타설 100㎥ 견적 뽑아줘" 같은 질문을 하면, **국가 표준품셈**(정부가 발간하는 공사비 산정 기준서), 정부가 제시하는 노임단가, 해당하는 자재들의 물가정보들을 근거로 자재비·인건비·장비비를 산출하고 근거 조항을 함께 제시하는 챗봇.

**나의 상황**
- 혼자 개발. 가용 기간 몇 주.
- 목적: 포트폴리오(RAG·에이전트·데이터 파이프라인 역량 증명) + 가능하면 무료 티어로 실제 배포.
- **건설 적산(積算, 공사비 산출) 도메인 지식이 부족함.** 학습하면서 개발 중.
- 이 프로젝트의 v1이 팀 프로젝트로 존재했고, 깊이가 부족하다고 판단해 주제만 유지한 채 재작성 중.

**대상 문서**
- 2026년 건설공사 표준품셈 원문 PDF, **982쪽**, 한국어.
- 내용의 대부분이 **표**. 예: "레디믹스트콘크리트 타설 / 인력운반 타설 / 콘크리트공 3인 / 시공량 무근구조물 23㎥, 철근구조물 20㎥".
- 표에 **병합 셀**이 많고, 한 칸에 여러 직종이 줄바꿈으로 쌓여 있는 경우가 흔함.
- 표 사이의 줄글(`[주] ④ 공구손료는 인력품의 2%로 계상한다` 등)이 **금액에 직접 영향**을 줌.
- **주기적으로 개정됨**(대략 연 1회). 새 판이 나오면 파이프라인을 다시 돌려야 함.

## 2. v1이 실패한 이유 (재작성 동기)

v1은 파싱·청킹·임베딩·DB 저장이 **파일 하나에 전부** 들어 있었습니다. 그래서:
- 청킹 전략만 바꿔 실험하려 해도 AWS 자격증명과 PostgreSQL이 떠 있어야 했음 → 실험을 안 하게 됨 → 처음 짠 휴리스틱이 그대로 굳음.
- 표를 단순 텍스트 추출로 읽어 행·열 관계가 사라짐. 그 결과 **철근콘크리트공사 챕터에서 '철근구조물' 열 전체가 누락된 채** 임베딩됨.
- **검증 수단이 전혀 없어서 아무도 이 누락을 몰랐음.** 에러도 안 났음.

## 3. 지금까지 한 것

**구조**
```
pipeline/   오프라인 배치: parse → chunk → embed → index   (단계 간 연결은 JSONL 파일)
backend/    상시 서빙: 검색·에이전트·API                     (아직 없음)
shared/     양쪽이 쓰는 스키마·설정                          (아직 없음)
data/       raw(원본 PDF) / processed(생성물)
evals/      골든셋과 채점기
```
단계를 파일로 끊은 이유: 청킹 전략을 바꿀 때 PDF 재파싱이나 임베딩 API 재호출 없이 중간 산출물부터 다시 돌리기 위함.

**파싱 (완료, 파일럿 범위)**
- 라이브러리: PyMuPDF. 줄글은 `get_text()`, 표는 `find_tables()`로 따로 읽고 좌표(y)로 순서를 맞춤.
- 표 한 행(구분+직종)을 레코드 하나로 만들고, 각 레코드에 **절 번호와 쪽수**를 붙임.
- 산출 예시:
  ```
  6-1-1 레디믹스트콘크리트 타설('24년 보완) | 인력운반 타설 | 콘크리트공 | 단위 인 | 수량 3 | 시공량(㎥) 무근구조물 23 | 시공량(㎥) 철근구조물 20
  ```
- 범위: 제6장 철근콘크리트공사 **185~214쪽(30쪽)**. 레코드 583건(표 297, 줄글 286), 절 45개.

**검증 (골든셋)**
- 원문을 눈으로 대조해 만든 정답 **23건**을 JSON에 저장하고, 스크립트가 채점.
- 방식: "이 페이지의 레코드 중 지정한 단어들을 전부 포함한 것이 정확히 N건 있어야 한다"는 문자열 포함 검사.
- 성과: 붙이자마자 **값이 조용히 사라지는 버그 2건**을 잡음.
  - 여러 행을 묶는 괄호 기호(`⌉ ⌋`)를 값으로 세어 `시너 0.2ℓ`가 통째로 소멸
  - 첫 칸이 라벨이 아니라 값인 표에서 `지하층 및 1∼3층`이 유실
- 현재 23/23 통과. **다만 검증 커버리지는 절 9/45, 페이지 5/30, 레코드의 16%뿐.**

**아직 안 한 것**: 청킹, 임베딩, 벡터 DB, 검색, 에이전트, API, 프론트엔드 전부.

## 4. 내가 지금 고민 중인 것

**(A) 스코프**
초기에 "대공종 1개(철근콘크리트공사)로 먼저 빠르게 만들고 확대하자"고 정했습니다.
그런데 최종 목표는 **표준품셈 전체(982쪽)** 를 다루는 것입니다.
지금 파일럿 30쪽에 맞춰 만든 파싱 로직과 골든셋이, 전체로 확대할 때 얼마나 재사용될지 확신이 없습니다.


**골든셋 확장 방식**
손으로 원문을 대조하는 방식은 982쪽에 적용할 수 없습니다. 그래서 2층 구조를 생각 중입니다.
1. **표본 검증**: 사람이 원문 대조한 정답 케이스 수십 건
2. **불변식 검증**: 정답을 몰라도 기계가 전수 판정하는 규칙
   - 원본 표 격자의 숫자 칸 개수와 레코드에 실린 숫자 개수가 일치하는가
   - 절 번호가 비어 있는 레코드가 있는가
   - 표가 있는데 레코드가 0건인 페이지가 있는가

**시간 배분**
지금까지 시간의 대부분을 **PDF 파싱**에 썼습니다. 청킹·임베딩·검색·에이전트는 아직 시작도 못 했습니다.
몇 주짜리 프로젝트에서 이 배분이 맞는지 확신이 없습니다.

## 5. 질문

아래 질문에 대해, 근거와 함께 답해 주세요. 제 판단에 동의하지 않는 부분이 있다면 그 이유를 구체적으로 지적해 주세요.

1. **스코프**: 파일럿 1개 대공종(30쪽)으로 시작한 판단이 옳습니까? 아니면 처음부터 982쪽 전체를 파싱해보고 실패 지점을 파악하는 편이 나았습니까? 지금 시점에서 전체로 확대하는 최적 타이밍은 언제입니까?

2. **개발 순서**: 파싱 → 청킹 → 임베딩 → 검색 → 에이전트 순서로 완성도를 높이는 방식이 맞습니까? 아니면 각 단계를 조악하게라도 먼저 관통해서 end-to-end를 만든 뒤 개선하는 편이 낫습니까? (후자라면 이미 실기한 것인지도 알려주세요.)

3. **시간 배분**: 몇 주짜리 개인 프로젝트에서 PDF 파싱 품질에 이만큼 투자하는 것이 합리적입니까? 파싱은 "적당히" 하고 검색·에이전트 쪽에 시간을 쓰는 편이 포트폴리오 가치가 높습니까? 견적이라는 도메인 특성(숫자가 틀리면 결과가 무의미)을 감안해서 답해 주세요.

4. **검증 전략**: 손으로 만든 골든셋 + 기계 불변식의 2층 구조가 982쪽으로 확장할 때 현실적입니까? 더 나은 접근이 있습니까? 불변식으로 검증 가능한 항목을 추가로 제안해 주세요.


6. **도메인 리스크**: 적산 도메인 실무 경험이 부족한 상태에서 만든 파이프라인이, 숫자는 정확하지만 실무적으로는 무의미한 결과를 낼 위험이 있습니까? 있다면 어떻게 완화합니까?

7. **놓치고 있는 것**: 위에서 언급하지 않았지만 이 프로젝트에서 중요한데 빠진 것이 있습니까? (예: 평가 방법론, 배포 제약, 법적·라이선스 이슈, 사용자 시나리오 정의 등)

가능하면 각 질문에 대해 **결론 → 근거 → 대안** 순으로, 실행 가능한 수준까지 구체적으로 답해 주세요.
