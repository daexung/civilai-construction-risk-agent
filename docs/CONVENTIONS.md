# 개발 컨벤션

## 브랜치

`main`에 직접 커밋하지 않고, 작업 브랜치를 만들어 PR로 합친다.

```
<타입>/<짧은-설명>
```

| 예시 | 설명 |
|---|---|
| `feat/pdf-parser` | 기능 추가 |
| `fix/table-merge-cell` | 버그 수정 |
| `chore/project-structure` | 설정·구조 등 기능 외 작업 |
| `docs/conventions` | 문서 |

- 영어 소문자와 하이픈만 사용한다.
- 브랜치 하나에 목적 하나. 길어지면 쪼갠다.

## 커밋 메시지

[Conventional Commits](https://www.conventionalcommits.org/) 형식을 따른다. 제목은 한국어로 쓴다.

```
<타입>: <무엇을 왜 했는지 한 줄>

- 상세 내용 (선택)
- 상세 내용 (선택)
```

### 타입

| 타입 | 사용 시점 |
|---|---|
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서만 변경 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 빌드·설정·의존성 등 그 외 |
| `perf` | 성능 개선 |

### 규칙

- 제목은 50자 이내, 마침표 없이.
- "무엇을"보다 **"왜"**를 남긴다. 무엇을 바꿨는지는 diff가 이미 보여준다.
- 한 커밋에 한 가지 변경. 리뷰가 어려워지면 쪼갠다.
- 예시
  ```
  feat: 표준품셈 표 파서 추가

  - 병합 셀 라벨이 유실되는 문제를 forward-fill로 보정
  - 185쪽 6-1-1 기준 무근/철근 두 열 모두 추출되는지 테스트 추가
  ```

## PR

- 제목은 커밋 메시지와 같은 형식을 쓴다. 예: `feat: 표준품셈 표 파서 추가`
- 본문은 `.github/pull_request_template.md` 양식을 채운다.
- **Squash merge**로 합치고, 머지 후 브랜치를 삭제한다. 커밋 이력이 한 줄로 정리된다.
- 리뷰어가 없어도(1인 개발) PR을 거친다. 변경 단위와 이유가 기록으로 남는다.

## 디렉터리

| 경로 | 역할 | 실행 시점 |
|---|---|---|
| `pipeline/` | PDF 파싱·청킹·임베딩·색인 | 오프라인 배치 |
| `backend/` | API·검색·에이전트 | 요청마다 (상시) |
| `shared/` | 양쪽이 함께 쓰는 스키마·설정 | - |
| `frontend/` | 웹 UI | - |
| `data/` | 원본(`raw`)과 가공 결과(`processed`) | - |
| `evals/` | 골든셋·평가 스크립트 | - |
| `docs/` | 기획·설계 문서 | - |

`data/raw`의 원본은 수정하지 않는다. 가공 결과는 `data/processed`에만 쓴다.
