# Constrained calculation modules

> **Current v1 contract:** JSON candidates support multiply_output, add_output, require_field, and apply_system_policy. Expressions are bounded data (number, quantity, input, arithmetic including pow/floor/ceil, and boolean comparisons). A registered policy reference invokes its versioned evaluator; a generated rule cannot restate that policy as a formula. The former global height_interval_deduction operation is retired. Registered Python modules are invoked through the isolated runner in `pipeline.python_sandbox`; local calls use Docker and configured production calls use the authenticated Cloud Run sandbox worker. `generated.py` does not evaluate source in the application process. Existing legacy ask_policy artifacts remain readable.

**Python executor status:** `--executor isolated_python` is a CLI generation mode. It emits a code candidate plus a v1 contract, runs isolated authoring cases and separate held-out evaluation, and stores artifacts only after both pass. `--register-candidate` is a separate explicit registration action. Local estimate runtime uses pinned Docker; deployed runtime can use the private Cloud Run sandbox worker when configured. The worker is implemented but not deployed or verified; see [python-calculation-execution.md](python-calculation-execution.md).

`backend/agent/tools/calc/generated.py` runs only registered, reviewed JSON modules. It never evaluates generated Python. This is a constrained data interpreter, **not an arbitrary-Python sandbox**. Generated rules can match input fields and apply exact-rational daily-output multiplication/addition, an automatically computed height-interval adjustment, or a source-backed field question. `when_expr` and `value_expr` support JSON trees for `number`, `input`, `add`, `sub`, `mul`, `div`, `floor`, `ceil`, comparisons, `and`, `or`, and `not`. Loops, imports, filesystem/network access, function calls, and arbitrary code are not part of this format. Its quantity scope today is daily production output; it does not extend the unit-price or indirect-cost formula languages.

The structured JSON authoring path gives the model only semantic fields: source conditions, target, units, rules, policy references, and explicit note-to-rule interpretations. Program code supplies the deterministic module identity/version, original PDF hash and PDF/printed page map, executor metadata, and trusted case IDs, then validates the complete v1 contract. The model must supply the source interpretation and note-to-rule mapping; missing mappings or exclusions are errors. JSON Schema validation is structural only; unit, policy, provenance, and execution checks remain separate. The candidate cases contain independent expected result fields only in the trusted evaluator, never in the generation prompt. Failed validation can be sent back for at most two repairs on the semantic path, and an identical semantic error suppresses another retry. Candidate IDs are slug-validated, existing files are never overwritten, and output directories overlapping the approved registry are refused. A successful artifact remains `candidate_unreviewed`; this code never copies a candidate into `approved/`.

Run `python -m pipeline.calculation_modules --source <source.pdf> --section-no <section> --cases <cases.json>` for offline preparation; this makes no model call. `--call-model` enables the existing Vertex AI Express Mode adapter using `VERTEX_API_KEY_BULK`. ## 6-3-1 height runtime policy

The published note says the daily output applies through 7 m and, above that, where lifting equipment is not used, reduces output by "up to 9% every 3 m". The note does not define the treatment of a partial 3 m interval, whether 9% is the exact rate, or whether successive reductions are additive or compounded. The official note on continuous crane use is a separate exception: add the equipment to the crew and do not reduce output. The roof note independently reduces output by 17%.

The 2026 source located for this rule states no upper height limit, and the official 2026 estimate publication and targeted public-source search did not yield a separate 6-3-1 clarification or Q&A defining a 40 m cutoff or a high-rise method. This leaves the official applicability and method above the text's stated 7 m base unresolved; the automatic recurrence below is the system's declared extrapolation for estimates, not an official ruling for arbitrary elevations.

For automatic estimates, the registered module makes these explicit system assumptions: every started 3 m interval above 7 m counts (`ceil((height - 7) / 3)`); use the maximum stated interval rate, 9%; apply each interval successively (`daily output × (1 - 0.09)^intervals`); then apply the separate roof factor of 83/100 in rule order. This avoids a negative multiplier at high elevations without clipping the rate or inventing a minimum output. It is a deterministic estimating policy, not a formula specified by the standard. The official source does not state the partial-interval convention, exact rate within “up to 9%”, or additive versus compounded accumulation. No height percentage, interval count, accumulation choice, or calculation-source document is requested from the user. The source table cell stays unchanged; modifiers affect daily output only, which drives work days and then labor/equipment quantities. Total work quantity is unchanged.

Source references: 2026 Standard Construction Estimate, common 6-3-1, PDF page 193 (printed page 137); [Construction Association of Korea 2026 Standard Estimate notice](https://info.cak.or.kr/lay1/bbs/S1T43C44/A/15/view.do?article_seq=153443&cpage=1&mode=view&rows=10); [CODIL official construction information excerpt](https://www.codil.or.kr/filebank/files/202601/helpdesk/FILE_000000000011032_3.PDF?atchFileId=FILE_000000000011032&fileSn=3). The public excerpts reproduce the note but do not add a partial-interval or accumulation formula.

It retains prose notes and referenced-section chunks separately. # Contract and executor notes (v1)

New authoring candidates use the additive contract in [calculation-contract-v1.md](calculation-contract-v1.md). Existing estimate-spec fields remain supported. The earlier `SPEC_FORMAT.md` note describing `per_unit` as unimplemented is stale: `backend/agent/tools/calc/per_unit.py` is an active runtime calculator reused by estimate flow.

The JSON interpreter is preferred when existing calculator operations can express a rule. `height_interval_deduction` is no longer a general operation; the 6-3-1 height convention is a scoped `system_policy_ref` plus a bounded expression with explicit `quantity` units. Legacy registered `ask_policy` remains readable; new candidates use `require_field` for site facts and cannot ask users to choose rates or calculation policies.

Python candidates are generated and tested only inside a pinned, no-network Docker image with resource limits. They remain unregistered. Runtime selection requires an explicit reviewed entry in `data/calculation_modules/approved/python-registry.json`; execution remains in the sandbox. Docker or image unavailability returns a closed error. AST validation alone never authorizes execution.

The authoring CLI requires the source PDF, section identifiers, parsed chunks, page map, and authoring cases. A separate final-evaluation case file is not sent to the model. All attempts and failures are appended to the candidate attempt log. Gemini calls are opt-in and use the configured Vertex adapter/model with call, token, and USD reservation limits.
