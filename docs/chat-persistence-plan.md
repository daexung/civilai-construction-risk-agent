# 회원별 대화 저장과 멀티턴 설계

## 관계와 경계

Supabase Auth 사용자 1명에 대화 N개, 대화 1개에 메시지 N개를 연결한다.
`conversations.id`를 회원 대화의 LangGraph `thread_id`로 사용한다.
같은 사용자의 서로 다른 대화도 문맥을 공유하지 않는다. 계정 전체 장기 기억은 구현 범위에서 제외한다.
Google 로그인 세션은 신원 확인에 쓰며, 대화 세션과 구분한다. 재로그인해도 같은 사용자 ID로 기록을 찾는다.

예시: A → A1(콘크리트), A2(도장); B → B1(콘크리트).
A1의 물량 변경은 A1 상태에만 반영한다. A2와 B1의 메시지·조건은 문맥에 포함하지 않는다.
공통 품셈 검색 색인은 공유하되 사용자의 질문과 견적 상태는 분리한다.

## 저장 구조

- `auth.users`: Supabase가 관리하는 신원. 이메일을 관계 키로 사용하지 않는다.
- `profiles`: 사용자 ID, 선택 표시 이름, 생성 시간. 요금제·결제는 추후 서버 전용 테이블로 분리한다.
- `conversations`: 소유자, 제목, 생성·갱신 시간. 새 대화는 첫 질문 때 생성한다.
- `messages`: 대화 ID, 순서, 요청 ID, 역할, 텍스트, JSON 응답. 요청 ID로 재시도 중복을 막는다.
- `agent_state`: 비공개 스키마. PostgresSaver가 체크포인트 테이블을 생성하도록 한다.
  화면용 메시지와 내부 상태는 목적이 달라 분리한다. 회원 요청에 PostgresSaver를 연결했다.

브라우저에는 본인 기록 조회와 표시 이름 변경만 허용한다. 메시지·대화 생성, 삭제, 제목 변경은
토큰을 검증한 API를 통해 처리한다. API는 사용자 입력의 user_id를 신뢰하지 않고 토큰에서 얻는다.
관리자 DB 연결은 RLS를 우회하므로 API의 대화 소유자 검증이 별도로 필수다.
채팅뿐 아니라 계산 조건 변경, 원문에 연결된 개인 결과, 엑셀 다운로드에도 소유자 검증을 적용한다.
대화 삭제 시 메시지와 체크포인트를 함께 정리한다. 체크포인트는 외래 키 자동 삭제 대상이 아니므로
API에서 체크포인터의 삭제 기능을 호출해야 한다. 사용자 탈퇴도 같은 정리를 수행한다.

## 멀티턴 처리

일반적으로 각 요청에 해당 대화의 최근 메시지와 상태를 제공한다. 모든 사용자의 기록을 합치지 않는다.
우리 서비스는 확인된 공종·입력 조건·기준일을 구조화한 상태를 계산의 기준으로 삼는다.
최근 대화는 대명사와 변경 의도를 해석하는 보조 문맥으로 사용한다.

1. 초기 질문: 공종과 물량 추출 → 필요한 조건 질문 → 계산.
2. 누락 조건 답변: 기존 interrupt에 답변하고 해당 대화의 상태를 이어간다.
3. 조건 변경: `물량을 200㎥로` → 기존 공종과 나머지 조건 유지 → 물량 검증 → 재계산.
4. 근거 질문: `그 할증 근거는?` → 같은 대화의 직전 견적과 적용 근거를 조회한다.
5. 다른 공종: 새 견적 상태로 전환하되 메시지 기록은 유지한다. 이전 공종의 전용 조건은 지운다.
6. 모호한 변경: 어떤 견적·항목인지 확인하고 임의로 덮어쓰지 않는다.

완료된 요청에서 `new_state`로 inputs 등을 초기화하는 현재 경로는 위 분기로 교체해야 한다.
DB에 기록을 넣는 것만으로 문맥 해석이 구현되지는 않는다.
문맥 길이는 최근 메시지·확정 조건 중심으로 제한하며, 원문 및 계산값을 모델이 임의로 변경하지 못하게 한다.
LLM이 생성한 변경 제안도 명세 타입·허용값으로 검증한 뒤 기존 계산 도구에 전달한다.

## 비회원과 로그인 전환

비회원은 DB에 메시지와 체크포인트를 저장하지 않는다. 브라우저 메모리와 만료되는 서버 메모리를 사용한다.
서버는 무작위 thread ID만으로 접근을 허용하지 않고 비회원 소유권을 입증하는 별도 세션 비밀값을 확인한다.
로그인 후 임시 대화 이전은 로그인 JWT와 비회원 세션 소유권을 모두 검증한다.
서버가 가진 메시지·상태를 새 회원 대화 ID로 옮기고 완료 후 임시 상태를 삭제한다.
이전 요청은 멱등 처리하며 실패 시 비회원 상태를 보존한다. 다른 사용자의 임시 대화를 가져올 수 없어야 한다.
팝업 로그인은 탭 메모리를 유지한다. 팝업을 사용할 수 없으면 대화가 사라질 수 있는 리디렉션을
자동 실행하지 않고 안내한다. localStorage에 비회원 대화는 저장하지 않는다.

## 구현과 검증 순서

1. 로컬 마이그레이션과 A/B/비회원 RLS 검증.
2. Google OAuth 설정, API JWT 검증, 회원·비회원 세션 경계 구현.
3. DB 저장소와 회원 전용 PostgresSaver 연결. 비회원 그래프는 임시 메모리 사용.
4. 로그인 상태에 따른 프런트 목록, 저장·복원, 로그아웃 시 회원 기록 제거.
5. 누락 답변·조건 변경·근거 질문의 멀티턴 구현과 로그인 전환 구현.
6. 서버 재시작 복원, 동일 대화 동시 요청 직렬화, 실패·재시도 복구 검증.
7. 공개 전 사용자별 횟수·전역 동시 처리·외부 API 비용 제한.

요청 처리 중에는 대화별 잠금을 사용한다. 메시지·체크포인트는 서로 다른 쓰기이므로
회원 API는 같은 PostgreSQL 연결과 트랜잭션에 메시지·체크포인트를 저장한다.
중간 실패 시 둘 다 롤백하며, 동일 request_id의 완료 응답은 다시 계산하지 않고 반환한다.
Google 팝업 로그인과 회원 저장·조회·새로고침 복원은 연결했다. 로그인 전 대화 이전은 후속 구현이다.
Auth 서버 검증·계정 격리·동시 재시도·롤백·계산 상태 복원은 로컬에서 검증했다.
실제 Google 사용자 계정의 브라우저 로그인부터 복원까지는 사용자 확인이 남아 있다.
