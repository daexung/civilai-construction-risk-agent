# 새 검색의 운영 연결

기준일: 2026-10-15, 한국 시간.

## 목표와 범위

로컬 시험에만 있던 파싱·청킹·임베딩·절 연결 조회와 4h/5b 근거 선택·위치 인용 검증을 실제 `/api/chat`에 연결한다. 기존 인증, 대화 저장, 이용 한도, 실행 로그, 계산기는 유지한다. 페인트 횟수와 방수 입력 결함을 이 검색 전환으로 고쳤다고 주장하지 않는다.

## 구조

```text
상담 화면 → Vercel 중계 → 기존 상담 API와 인증·이용 한도
  ├─ 품셈 상담 → 새 결합 검색 → 절·표·주석·참조 조회
  │             → 모델은 위치 선택 → 코드가 원문·상태·수치를 검증 → 답변과 원문 표시
  └─ 견적 → 새 청크로 공종 후보 검색 → 기존 계산 명세·계산기·단가·엑셀

운영 Supabase / rag_knowledge
  원문·절·청크·원문 연결·참조 연결·교정 장부
운영 이미지 / data/knowledge
  이미 생성한 벡터와 해시 목록, 서버 시작 때 입력·모델·차원·내용 검증
```

청킹 묶음: `cs-37f81b5cfb1b-46f4f035c0fa`.
원문 릴리스: `rk-complete-82c206c61e21-37f81b5cfb1b`.
문서 벡터는 `studio / gemini-embedding-2 / 3072`로 고정한다. 기존 문서 임베딩을 다시 호출하지 않는다. 질문 벡터만 요청 때 생성하고 제한된 프로세스 메모리 캐시를 쓴다.

## 운영 코드

- `backend/knowledge/`: 검증한 검색·선택 코드를 상대 경로로 가져오는 운영 패키지. 실험 CLI·저장 응답·시험 원장·전체 질문 파일 로그는 사용하지 않는다.
- `runtime.py`: 읽기 전용 DB 연결, 질문별 모델 호출 한도, 엔진 직렬화, 실제 상담 응답 연결.
- `response.py`: 5b 원문 위치 기반 답변 생성과 검증을 재사용한다. 모델이 원문 인용을 직접 작성하도록 하지 않는다.
- 기존 도구형 상담과 그래프형 상담 모두 새 경로로 연결했다. 도구형 상담은 검증한 답변을 추가 대화 모델이 다시 쓰거나 상태를 올리지 않도록 종료한다.
- 견적 계산은 새 청크에서 찾은 부문·절 번호를 기존 계산 명세에 대응한다. 새 검색의 성공이 계산 명세의 정확성을 보장하지는 않는다.
- `KnowledgeAnswer.tsx`: 답변 상태, 정상 근거, 검토용 원문, 번호 대안, 목록을 구별한다. 원문 이미지는 기존 `/api/source/p숫자.png`를 쓴다.
- 저장된 도구형 응답의 복원에도 새 근거와 상태를 유지한다. 과거 응답에는 선택 필드이므로 기존 표시를 유지한다.
- 실행 로그의 청킹 묶음·원문·벡터·검색 설정을 실제 운영 버전으로 기록한다.

## DB 적재

회원·대화 테이블과 분리한 `rag_knowledge`에 고정 릴리스만 복사했다.

| 자료 | 건수 |
|---|---:|
| 원문 노드 | 106,825 |
| 절·상위 묶음 | 1,362 |
| 원문 레코드 | 23,481 |
| 검색 입력 레코드 | 23,484 |
| 참조 연결 | 241 |
| 청크 | 5,764 |
| 청크와 원문 연결 | 25,147 |
| 청크와 칸 연결 | 63,318 |
| 청크 연결 | 18,977 |

18개 자료 테이블을 정렬된 PostgreSQL COPY 내용의 SHA-256으로 대조했다. 모두 일치해야 하나의 트랜잭션으로 반영한다. 첫 시도는 외래키 대기 검사 뒤 권한을 설정하는 순서 문제로 전부 롤백됐고, 검사 완료 후 권한을 설정하도록 순서를 수정한 재실행이 완료됐다. 기존 릴리스가 있으면 내용이 같은지 비교하며, 다르면 덮어쓰지 않는다.

모든 검색 테이블은 RLS를 켜고 `anon`, `authenticated`, `public`의 접근 권한을 제거했다. 회원·대화·평가·사용량을 복사하거나 직접 변경하지 않았다. SQL 이력과 `deploy/promote_knowledge.py`를 함께 보관한다.

벡터는 GitHub의 버전 고정 배포 자료 `retrieval-v1-20261015`에 보관한다. 빌드는 `deploy/knowledge-assets.json`의 파일 크기와 SHA-256을 확인한 파일만 이미지에 넣는다. 비밀값·대화·질문 캐시는 자료에 포함하지 않는다.

## 확인 결과

- 신규 연결·상태·로그 검사 16개 통과.
- 화면 79개 검사 통과. Windows 경로 때문에 기본 검사 패턴이 파일을 찾지 못해 같은 전체 검사 패턴을 명시해 실행했다.
- 기존 견적 도구 70개, 기존 실제 검색 흐름 7개 통과. 오프라인 회귀에서는 DB 로그 저장이 비활성 상태라는 경고가 있었으며 운영 DB 저장 실패를 뜻하지 않는다.
- 프런트 운영 빌드 성공. 기존 PostHog 의존성의 소스맵 경고가 있다.
- 운영 DB를 읽는 전용 엔진: 5,764개 청크·1,362개 절 준비, DB 읽기 전용 확인.
- 실제 모델 질문: 번호 `4-1-1`은 5개 부문 대안·확인 필요, 적산열량계 ø100mm 질문은 0.569인·답변 확인으로 전달됐다. 이 두 질문은 배포 연결 확인이며 새로운 독립 정확도 평가가 아니다.
- PC에서 운영 DB를 읽은 엔진 준비 약 9초, 번호 조회 약 5초, 첫 실제 답변 약 51초. 운영 서버 지연과 구별한다.

## 전환과 되돌리기

`KNOWLEDGE_RETRIEVAL=v1`이면 새 검색, 없거나 `legacy`이면 기존 검색이다. CI는 저장소 변수 값을 Cloud Run에 전달한다. 되돌릴 때는 변수를 `legacy`로 바꾸고 같은 백엔드 배포 절차를 실행한다. 지식 DB와 이전 파일은 삭제하지 않는다. 새 경로가 실패했는데 성공한 것처럼 기존 검색으로 몰래 대체하지 않는다.

## 남은 한계

- 원문에 없는 표현·활용형, 부정 조건, 모호한 목록 범위, 수식과 소속 미확정, 모델 변동은 기존 정책의 한계다.
- 미확정 원문은 자동 계산 근거로 올리지 않는다. `applicability`는 계속 `unknown`이다.
- 엔진은 한 인스턴스 안에서 공유 DB·선택기 상태를 잠금으로 보호한다. 동시 요청이 몰릴 때 지연은 별도 측정이 필요하다.
- 전체 서비스 정확도, 견적의 완전성, 신규 사용자 수요를 입증하는 작업은 아니다.
- 별도 공개 자료 점검에서 찾은 롤러칠 횟수 누락과 실내 방수 입력 결함은 그대로이며 후속 수정 대상이다.

## 배포 확인

배포 완료 후 실제 상담 API, 실행 로그 버전, 공종 검색, 화면과 원문 이동 확인 결과를 추가한다. 이 문서 작성 시점의 준비 결과를 배포 완료로 혼동하지 않는다.

### 실제 API에서 확인한 추가 연결

첫 배포의 실제 규격 포함 QA가 공종 선택으로 들어가면서 새 답변 필드가 없었다. 전용 엔진 성공을 공개 API 성공으로 세지 않았다. 새 견적이 확정되지 않은 품셈 상담은 규격 숫자와 관계없이 검증형 조회 도구로 먼저 보낸다. 운영의 모델 사용 설정도 CI에 명시하고, 새 검색인데 모델 사용이 꺼져 있으면 준비 완료로 표시하지 않는다. 견적 공종 검색은 실제 사용한 검색 메타데이터를 응답과 저장 상태로 전달한다.

되돌릴 때 모델 사용 설정까지 이전 오프라인 운영으로 돌리려면 저장소 변수 `AGENT_LLM=off`도 함께 지정한다.


### 운영 모델 공급자

기존 Secret Manager 등록 도구는 `GEMINI_API_KEY`를 사용한다. 운영 배포는 모델 사용 여부뿐 아니라 `LLM_PROVIDER=studio`를 명시해 해당 키로 호출한다. 문서 벡터와 질문 임베딩도 Studio의 기존 모델을 유지한다. 모델 이름은 기존 `gemini-3.5-flash-lite`이며 새 키나 권한을 만들지 않는다. 로컬 시험에서 사용한 Vertex 공급자와 동일하다고 주장하지 않는다. 운영 API 확인을 따로 남긴다.
