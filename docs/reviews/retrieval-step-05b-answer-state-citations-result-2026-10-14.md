범위: 로컬 답변 연결 계층과 화면만 보완했습니다. 검색 정책(4h)·`select_verified.py`·원문·청킹·문서 벡터·검증 DB·과거 결과·운영 상담·인증·회원·사용량·원격 연결은 바꾸지 않았고, 커밋·푸시·배포·새 검색 정책·독립 평가도 하지 않았습니다.

## 1. 한눈에 보기

- 검색 상태(`supported` 등)는 그대로 두고 **답변 상태(`answer_status`)와 이유를 따로 추가**했습니다. 주 배지는 답변 상태입니다. 검색이 `supported`여도 원문 검증을 통과한 설명이 있을 때만 "답변 확인"입니다.
- 모델은 **원문 위치(`S2.1` 같은 자료·줄 식별자)만 고르고**, 인용문·출처는 코드가 모델에 실제로 준 줄에서 가져옵니다. 모델이 글을 베끼다 실패하던 경로는 없어졌습니다.
- 값 답변은 인용한 **줄 안에 값이 있고, 질문의 치수 조건(㎜·ø 등)이 같은 열·열 묶음·순서 위치와 대응하는지** 코드가 따로 확인합니다. 다른 행·다른 열·다른 두께의 값은 통과하지 못합니다.
- 최종 구성의 실제 답변 생성 16회(G01 2, G03 7, G08 2, G10 2, 자유 질문 3): 답변 확인 11회, 질문 조건 확인 필요 4회(자유 질문 3회는 기대한 결과, G10 1회는 모델이 값을 못 찾았다고 응답), 원문 확인 필요(검증 실패) 1회, 전송 오류·시간 초과 0회(6절).
- 브라우저에서 5가지 상태 표시를 확인했습니다(원문 확인 필요는 강제 응답으로 표시만 확인, 5절).
- 새 유료 호출 **24회·약 $0.019**(상한 30회·$1 이내). 모델 단가는 공개값 기반 추정입니다.
- 이 결과는 **로컬 시험 연결의 표시·인용 보완**입니다. 검색 전체 정확도·견적 계산 승인·기존 운영 서비스 대비 우위를 뜻하지 않습니다. `applicability`는 모든 응답에서 `unknown`입니다.

## 3. 검색 상태와 답변 상태 대응

| 상황 | 검색 상태 | 답변 상태(주 배지) | 이유 코드 |
|---|---|---|---|
| 질문 조건에 대응한 설명이 원문 위치 검증 통과 | supported | **답변 확인** `confirmed` | verified |
| 관련 표는 있으나 질문 조건에 맞는 값 확인 못 함(모델이 못 찾음) | supported | **질문 조건 확인 필요** `condition_unconfirmed` | model_unmatched |
| 모델이 고른 값의 행·열이 질문 조건과 대응하지 않음(값은 쓰지 않음) | supported | **질문 조건 확인 필요** | condition_not_in_row |
| 형식·위치·숫자·금액·절 번호 검증 실패 | supported | **원문 확인 필요** `source_check_needed` | validation_failed |
| 생성 오류·시간 초과 | supported | **원문 확인 필요** | generation_failed |
| 원문이 길어 설명 입력에 다 못 줌·시험 한도 근접 | supported | **원문 확인 필요** | context_budget / cap_reached |
| 소속·수식·범위 등 미확정 | needs_confirmation | **확인 필요** | search_needs_confirmation |
| 번호만 있어 부문 선택 필요 | needs_confirmation | **확인 필요** | division_choice_required |
| 맞는 근거 못 찾음 | not_found | **근거를 찾지 못함** | search_not_found |
| 시험 한도 도달·서버 오류 | error | 별도 오류 안내 | trial_cap / 화면의 서버 오류 문구 |

- 값을 못 찾은 경우의 문구는 "읽은 원문에서 질문의 조건에 맞는 값을 확인하지 못했어요. 문서 전체에 값이 없다는 뜻은 아니에요."이며, "다른 두께·규격의 값을 대신 쓰지 않았어요"를 함께 보여 줍니다. 원문은 계속 열어 볼 수 있습니다("읽은 원문" 영역).
- "확인하지 못한 조건"으로 보여 주는 문구는 모델이 적은 표현 중 **질문에 글자 그대로 있는 것만** 남깁니다(모델이 새로 만든 표현은 버림).
- 전송·검증 실패와 값·조건 미확인은 이유 코드와 문구가 다릅니다(합치지 않음).

## 4. 모델은 위치를 고르고 코드가 인용문을 가져오는 경로

1. 모델 입력: 정상 답변 근거만 `[S1]`, `[S2]` 자료로 묶고 줄마다 `S2.1`처럼 위치 식별자를 붙입니다. 표는 선택 행만(선택 행이 없으면 조각 전체) 주고 `기준:`·`머리글:` 틀을 앞에 둡니다. **주지 않은 행은 허용 목록에 없습니다**(이전에는 전체 본문을 검증 허용 범위로 보관했던 문제를 없앰). 필요한 줄이 빠졌을 때 조용히 범위를 넓히지 않습니다. 원문이 한도를 넘으면 줄이거나 넓히지 않고 호출 없이 원문 표시로 전환합니다.
2. 검토용 원문·진단 후보는 모델 입력에 넣지 않습니다(`needs_confirmation`은 모델 호출 0).
3. 모델 출력: `status`(answered / condition_unconfirmed / not_found), `evidence`(위치·값·단위), `unmatched_conditions`.
4. 코드 검증과 인용: 위치는 `S숫자.숫자`만 받습니다(접두어 보정·비슷한 ID 맞춤 없음). 없는 줄·주지 않은 줄·다른 자료·글이 붙은 식별자·옛 조각 ID는 거절합니다. 인용 기록의 `quote`는 DB 원문 줄 그대로이고 `search_uid`, 쪽, `기준:`·`머리글:`, `[공동값 …]` 표지(칸 식별자 포함)를 보존합니다. 모델이 쓴 글은 인용으로 쓰지 않습니다.
5. 값 대응 검사(코드): 값이 그 줄에 있어야 함 → 질문의 치수 숫자가 (머리글 열이면) 값의 열에, (행 이름이면) 같은 열 묶음에, 같은 길이의 값 목록이면 같은 순서 위치에 있어야 함. 범위(`a~b`)·`이하/미만/이상/초과`는 해당 범위 안이면 인정하고, 그 경계 숫자는 값이 아니라 조건 경계로 기록합니다. 답변 글에 나온 표 숫자는 선언하지 않았어도 같은 검사를 받습니다. 인용 줄·질문에 없는 숫자, 금액, 질문·자료에 없는 절 번호, 내부 식별자 노출은 거절합니다.
6. 공동값 표지: 모델·화면에는 긴 표지를 `[공동값#1]`+관계 설명 한 줄로 줄여 보여 주되, `quote`는 원본 그대로이며 값을 새로 만들지 않습니다.
7. "답변에 인용" 표시: 코드가 확인한 인용 위치(자료·줄)에서만 만듭니다. 인용하지 않은 같은 문맥의 정상 근거는 "함께 읽은 정상 근거 N개(답변에는 인용하지 않았어요)"로 접어 둡니다.

## 6. 최종 구성의 생성 결과 (실제 모델 호출만, 강제 실패 제외)

| 구분 | 횟수 | 설명 |
|---|---|---|
| 모델 설명 통과 → **답변 확인** | **11** | 1차 4 + 2차 6 + 화면 1 |
| **질문 조건 확인 필요** (값·조건 미확인) | **4** | 자유 질문 3(기대한 결과), G10 1(모델이 `condition_unconfirmed` 응답, 1차) |
| **원문 확인 필요** (검증 실패 전환) | **1** | G03 1회, 숫자 `2`가 인용 줄·질문에 없다는 이유(`numbers`). 1차에는 거절된 출력 글을 기록하지 않아 정확한 문장은 확인하지 못함(공구손료 2% 주를 인용 없이 쓴 것으로 추정) |
| 생성 오류·시간 초과 | 0 | — |
| 합계 | 16 | 답변 생성 호출(원장 `answer` 기준 23회 중 나머지 7회는 아래 개발 중 호출) |

- 위 전환 1/16은 **과거 5단계의 27회 중 6회 전환과 같은 지표가 아닙니다.** 과거 전환에는 수정 전 형식 실패(조각 ID 접두어 2·`[공동값]` 주석 2)가 섞여 있었고, 이번에는 그 경로 자체가 없습니다. 조건 미확인 4회는 전환이 아니라 값·조건을 확인하지 못했다는 별도 결과입니다.
- 개발 중 호출 7회(구성이 최종과 달라 위 표에서 제외): G03·G01·G08·G10·자유 질문 1회씩과 수정 뒤 G10·G01 재확인. 이 중 첫 G10은 조건 경계값(1.2~1.5이하의 1.5)을 값으로 오인해 거절했고, 이를 조건 경계로 취급하도록 고친 뒤 최종 구성에 반영했습니다.
- 모델 출력은 같은 입력에서도 달라집니다. G10은 같은 최종 로직으로 1차에 조건 확인 필요, 2차에 답변 확인이었습니다. 표본이 작아 비율의 일반화는 하지 않습니다.

## 7. 가상 검사 (강제 실패, 실제 모델 실패율에 넣지 않음)

실제 응답 조립 경로(`Engine.build_response`)에 모델 출력을 직접 넣었습니다(`virtual_checks_05b.json`, 호출 0).

| 입력 | 결과 |
|---|---|
| 정상(0.6/400 → 0.084) | 답변 확인 |
| 없는 줄 / 모델에 주지 않은 행 / 다른 자료 줄 | 원문 확인 필요(`line_missing` / `line_not_provided` / `source_not_provided`) |

## 12. 남은 문제와 한계

분류: 검증 / 생성 / 화면 / 기존 검색.

1. (검증) 값 대응 검사는 **치수 숫자**(㎜·m·ø 등)와 머리글 칸 수가 줄의 칸 수와 같을 때만 열·행 묶음 단위입니다. 칸 수가 다르면 "같은 줄" 수준(`line_only`)까지만 확인하고 그렇게 표시합니다. 1종/2종·건물용/세대용 같은 **글 조건**은 코드가 확인하지 않고 검색 단계와 모델에 맡깁니다.
2. (검증) 설명 문장이 인용하지 않은 줄의 글자 내용을 쓰는 것은 코드가 의미로는 막지 못합니다(숫자만 검사). G03 한 번은 인용 없이 주(note) 내용을 설명에 쓰려다 숫자 검사에 걸렸고, 다른 때는 주를 함께 인용했습니다.
3. (생성) 같은 입력에서 모델 결과가 달라집니다(G10 확인/조건 확인 필요, G03 1/6 검증 거절). 이번 단계에서는 프롬프트를 더 조정하지 않았습니다.
4. (화면) "확인하지 못한 조건"이 모델 표현에 따라 `0.5`처럼 짧게 나올 수 있습니다(질문에 있는 글자만 남기는 규칙의 결과). 값이 속한 열 묶음의 첫 칸이 "행 0.6"처럼 보이는 표시도 어색합니다.
5. (화면) 표 원문 쪽에서 `[공동값#1]` 표지가 줄마다 반복됩니다(원문 왜곡을 피하려고 숨기지 않음, 설명은 줄 아래 한 줄).
6. (기존 검색) G02 불필요 보류, N19 가까운 표 후보, G14 목록 완전성, G09 대상 정체성은 5단계·4i 한계 그대로입니다.
7. 기존 상담 경로와의 비교는 하지 못했습니다(5단계 8절과 같은 이유).
