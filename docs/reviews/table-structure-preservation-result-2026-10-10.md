**이어진 길 (이번에 코드로 재현한 것):**

```text

  → chunk.make_chunks    변경 없이 호출
```

## 5. 기존 청킹까지 무엇을 전달했고 무엇은 못 전달하는가

**전달한 것**

| 청킹 입력 필드 | 값 |
|---|---|
| `kind`, `section`, `page`, `text` | 보관 구조에서 생성 |
| `table_id`, `bbox` | `p185-o145`, 왼쪽 위 원점 pt(운영 레코드와 같은 방식) |
| `structure` | `{status, issues}` — 아래 대응 규칙 |
| 추가 `record_uid`, `generation_id` | 레코드·청크·연결 정보가 같은 생성 결과를 가리키게 함 |

**보관 상태 → 청킹 structure 대응 규칙**

| 보관 구조 표지 | 레코드 structure | issues 코드 |
|---|---|---|
| 값 훼손 의심 칸 | `uncertain`(표 전체 레코드) | `value_suspect`, `table_held` |
| 행 대응 확인 필요 | `uncertain`(표 전체 레코드) | `row_alignment_unconfirmed` |
| 조립 단계가 추정으로 나눈 행 | `uncertain`(그 레코드) | `row_split_unconfirmed` |
| 머리글을 숫자 규칙으로 정하지 못함 | `uncertain`(그 레코드) | `header_fallback`, `header_extended_numeric` |
| 위 표지 없음 | `ok` | 없음 |

`ok`는 "구조 표지가 없다"일 뿐이다. 계산 명세, 값, 단위의 검증이나 사람 검토를 뜻하지 않으며, 연결 정보의 `calc_use`가 "계산 승인 아님"으로 따로 적는다. 레코드 하나라도 `uncertain`이면 기존 `make_chunks`가 그 표 청크 전체를 `uncertain`으로 둔다.

**청크에서 되돌아가는 길** (`links.json`)

`청크 → record_uids → 레코드의 cell_ids(칸) / note_id(주석) / basis_id(기준) → store.json의 칸(ODL id·좌표·병합)`. 공동 값은 `shared_values`에, 주석·기준·작은 표·참조 관계는 `relations`에 상태와 근거 문구가 함께 있다.

**아직 전달하지 못하는 것**

- 13개 보류 표의 행 대응 확정(작업 2). 조립 단계의 후보 분리와 `uncertain` 표시만 전달한다.
- 다음 쪽 주석, 이어지는 표, 번호 없는 소제목 끝의 기준 연결(작업 3).
- 참조 대상 원문. 참조는 부문·번호·제목·조건만 있고 대상은 미조회다.
- 단독 쪽 처리의 한계: 555·807쪽은 상위 절 제목이 이 출력에 없어 `section`이 `(절 제목 미확인·555쪽)`이다. 쪽마다 다른 표시를 써서 떨어진 쪽의 소제목이 서로 이어지지 않게 했다. 전체를 순서대로 처리하면 앞 쪽 제목을 이어받는다.
- 운영 ID와의 대응(새 식별자 `p185-o145` ↔ 운영 `p185-t0`)과 영구적으로 안정적인 ID.
- 계산 명세, 계산기, 검색 순위, 대화, Excel은 변경하지 않았다.
