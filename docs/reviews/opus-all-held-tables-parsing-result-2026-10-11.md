# 남은 파싱 보류 전체 검토 결과 — 중단된 오퍼스 작업을 이어서 수행

작성일: 2026-10-11. 이번 작업은 파싱만 진행했다.

## 먼저 알아야 할 결과

**기존 보류 표 286개 중 285개를 교정했고, 1개는 원문 설명이 없어 미해결로 남겼다.** 별도로 수정 없이 정상 확인만 하고 끝낸 표는 없다. 여기서 보류는 표를 버렸다는 뜻이 아니라, 구조나 적용 조건을 확정하지 못했다는 표시다.

같은 원시 출력으로 **982쪽 전체, 표 2,328개, 레코드 22,548개**를 새로 만들었다(아래 '이어받은 뒤 추가 확인'의 443·523쪽 교정 반영). 대상 밖 표 **2,042개**의 레코드 내용·순서·상태는 이전 검증본과 같다. 기준·주석·제목과 쪽 사이 연결도 같다.

미해결 1개는 **758쪽 바탕만들기의 Shot Blast**다. 같은 자재 설명에 수량 `0.215`와 `0.415`가 적혀 있으나 두 값을 구분하는 적용 조건이 없다. 이 작업은 한 공법의 원문 묶음으로 두 값을 모두 보존했다. 하나를 선택하거나 두 값을 더하지 않았다. 이 표의 레코드 네 건은 보류를 유지한다. **286개 모두 해결됐다고 보고하지 않는다.** 추가 파싱 규칙으로 원문에 없는 조건을 만들 수는 없다.

## 이어받은 뒤 추가 확인 (오퍼스, 19:10 이후)

오퍼스 작업이 사용량 한도로 멈춘 동안 Codex가 이 폴더에서 작업을 이어 위 결과를 만들었다. 오퍼스는 재개 후 다음을 했다.

1. **Codex 결과를 그대로 받지 않고 대조했다.** 823쪽은 26행 전체를 원문 그림과 칸 단위로 맞춰 보았고 일치한다. 굵은 계단선의 번호별 경계(`out/graphic_trace_log.txt`)는 오퍼스가 따로 읽은 275쪽 첫 표의 선(①: 500~1,000m는 N30 아래, 1,200m부터 위로 올라감)과 같다. 검증 스크립트를 다시 돌려 실패 0건을 확인했다.
2. **재개 직후 오퍼스가 `line_regrid.py`를 고친 것을 되돌렸다.** 원문 공백 글자 보존 수정이었으나, Codex가 고정한 `reviewed_tables.json`이 이 파일의 해시에 묶여 있어 그대로 두면 재생성이 거부된다. 해시가 실행 기록과 다시 같아진 것을 확인했다. 함께 만들던 미사용 교정 파일도 지웠다.
3. **443·523쪽 괄호 그림의 글이 출력에 없던 문제를 고쳤다.** Codex는 두 표의 머리글만 바로잡았다. 그런데 그림의 나머지 글(`적재 : 5.5km/hr`, `공선(空船) : 9.3km/hr`, `독항시(獨航時) : 12.9km/hr`, `(촬영운항시간)`과 그 구성 `계기비행시간·왕복운항시간·순촬영운항시간·예비운항시간`)은 어느 레코드에도 없었다. 원래 표 영역 밖에 있어 표 영역 글자 확인으로는 잡히지 않았다. 원문 위치로 그림 전체를 표로 옮겼다(`diagram_tables.json`, `pipeline/diagram_tables.py`).
   - 칸마다 PDF 영역을 고정하고, 적용할 때 그 영역의 글자를 다시 읽어 같아야 한다.
   - 원문·원시 출력·`reviewed_tables.json`·엔진 해시나 교정 전 칸이 다르면 거부한다. 글자를 바꾼 자료와 버전이 다른 자료를 거부하는 확인을 검증에 추가했다.
   - 523쪽 오른쪽 괄호는 `(촬영운항시간)` 높이에 놓여 있고, 같은 쪽 식 `(촬영운항시간)+(천후장애시간)+(보완촬영시간)`과 맞는다. 그래서 네 항목을 그 행에 연결했다.
   - 결과: 레코드 22,542 → 22,548(443쪽 +1, 523쪽 +5). 대상 밖 변화 0건, 검증 실패 0건.

### 새로 발견한 문제 (이번 범위 밖, 고치지 않음)

443·523쪽 원인을 따라가 보니 **보관 단계가 ODL의 `text block` 안에 든 글과 목록 항목 아래의 하위 글을 읽지 않는다.** 표 밖 본문에서 **185쪽, 623개 글 묶음**이 출력에 없다(목차 줄 제외). 예: 60쪽 `가. 콘크리트 구조물 중의 말뚝머리` 등 체적 공제 제외 목록, 65쪽 토취장·골재원 기준, 72쪽 인력운반 공식의 변수 설명.
- 보류 표 문제가 아니라 본문 전달의 일반 결함이다. 고치면 185쪽의 결과가 바뀌어 대상 밖 무변경 조건과 충돌한다. 그래서 이번에는 고치지 않았다.
- 목록은 `out/dropped_text_nodes.json`(쪽, 상위 구조, 글 앞부분)에 있다.
- **청킹 전에 반드시 먼저 고쳐야 한다.** 표만 보류 해제되고 적용 기준 문장이 빠진 상태로 넘어가면 근거 제시가 틀어진다.

## 이어서 처리한 내용

오퍼스가 남긴 행·이름 설정 222개와 원문 대조 기록, 번호 설정 48개를 보존하고 함께 실행했다. 중단 당시 파일의 문자열 줄바꿈 문법 오류를 먼저 복구했다. 기존 폴더 상태와 코드 13개 파일의 해시는 `baseline/codex_resume`에 보관했다.

| 문제 | 실제 처리 |
|---|---|
| 행과 이름 연결 | 원래 표의 열과 가로선 구간 안에서 글자 위치로 행을 나누고, 줄바꿈·공통 칸·묶음 이름을 구별했다. 표별 원문 확인 설정을 적용했다. |
| 68쪽의 두 행 이름 | 병합된 이름 열을 문장으로 보고 나누지 않던 경우를 고쳤다. 기계실·옥내일반 등 12개 하위 행이 자기 값과 연결된다. 중복 이름 표시도 한 번만 읽히도록 정리했다. |
| 번호 연결 | 완전한 번호, 바로 위 품목 제목, 앞 쪽의 명시적인 이어짐을 근거로 앞자리를 잇는다. 원래 짧은 번호와 연결 근거를 보존한다. 쪽을 따로 시험할 때 남던 네 표도 전체 문맥에서 연결됐다. |
| 머리글 여섯 표 | 397·443·523쪽은 머리글 없는 정의·설명 표라서 첫 줄부터 본문으로 보존했다. 778쪽 두 표와 936쪽 작은 표는 첫 줄을 머리글로 원문 대조 지정했다. |
| 175쪽 작은 표 | T, t1~t5, f 작업마다 한 행으로 보존했다. 그라우팅·용접의 작은 표와 바깥 작업의 연결을 유지했다. |
| 823쪽 재료 표 | Steel plate의 10개 규격과 Channel의 두 규격에 이름을 연결했다. 단위 열 26행과 수량을 대조했다. 3,000 용량 열의 pipe ø12 빈 칸을 남기고 용접봉 세 값과 모래 48의 행을 바로잡았다. |
| 82쪽 경계와 줄 | 기존 표 영역의 실제 글자 위치로 각 행·칸을 다시 보관했다. 경계와 행 대응 보류가 남지 않는다. |
| 굵은 계단선 여덟 표 | 275~277쪽의 선 번호 ①~⑥을 277쪽 출력표의 각 공칭·전동환산 출력과 연결했다. 값마다 N값, 배사거리, 번호별 선 위아래 위치를 담았다. 원문 `-` 칸에도 조건과 값 없음 표시를 전달한다. |

굵은 선은 원문을 네 배로 그려 가로선과 세로선의 실제 연결을 확인했다. 번호의 끝 위치, 선의 연결·겹침을 함께 사용했을 때 각 거리 열의 연결이 하나로 정해지는지 확인했고, 굵은 가로선을 빠짐없이 사용했다. 원문 위에 번호별 선 표시를 겹친 그림 세 장을 직접 대조했다.

**도표 아래끝에서 잘린 선은 실제 경계 N값을 확정하지 않았다.** 표시된 아래끝과 실제 숫자 경계를 구분하고, 표 범위 밖으로 값을 늘리지 않는다. 작업능력 계산·단거리 보정·장비 선택을 실행한 결과가 아니다. 출력의 `선 위쪽`은 원문 도표에서의 위치를 뜻한다.

## 실행 중 추가로 확인해 고친 것

- 68쪽은 오퍼스 설정을 적용해도 병합 이름 열을 문장으로 판단해 행이 나뉘지 않았다. 원문을 확인하고 해당 구조에서 기준 이름 열을 유지하도록 고쳤다.
- 275쪽 세 번째 표는 N값 여덟 개가 한 칸에 남아 있었다. 실제 원문 행 경계와 N값 글자로 각각의 행에 나눴다. 이미 보류였던 계산표 안의 문제다.
- `-` 칸은 기존 내보내기에서 읽기용 값에서 빠지므로 계단선 조건도 전달되지 않았다. 보관 칸과 레코드 연결 자료에 조건을 남기고, 읽기용 글에도 원문의 값 없음과 배사거리를 표시했다.
- 두 줄의 Steel plate를 합칠 때 기존 공백 정리가 단어 사이까지 붙였다. 원래 두 줄과 위치를 보존하고 읽기용 이름은 Steel plate로 전달하도록 고쳤다. 이번 연결 과정에서 발견하고 바로 정리한 표시 문제다.

## 확인 결과와 한계

- 최종 출력의 문서·원시 출력·코드·교정 자료 버전이 일치한다.
- 대상 286개 표의 원문 영역에서 출발한 글자 확인 결과, 보관 결과에 빠진 글자는 **0건**이다. 단, 이 확인은 표 영역 안만 본다. 표 영역 밖으로 이어진 그림 글(443·523쪽)은 이 확인으로 잡히지 않았고 별도로 고쳤다. 각 숫자 칸 7,062개를 실제 PDF 위치와 대조한 차이도 **0건**이다.
- 최종 확인 항목 908개와 기존 적용 제한 확인 9개가 통과했다. 이는 정확도 점수가 아니다.
- 원문 버전, 엔진 버전, 교정 전 내용, 기대 구조가 다르면 실제 적용 경로에서 거부한다.
- 대상 밖 표의 내용·상태 차이 0건, 대상 밖 새 보류 0건이다.
- 기존 숫자 칸 교정, 555쪽 13행, 224쪽 식, 501쪽 누락 열, 502쪽 분수식과 여섯 표 행 연결, 복구 표 24개를 유지했다. 이전 교정 자료 세 파일은 그대로다.
- 행·이름의 원문 검토에는 오퍼스가 남긴 기록을 재사용했다. 이 결과는 전체 문서의 모든 의미를 새로 사람이 검토했다는 뜻이 아니다. 글자 개수 확인만으로 값·행 연결을 판단하지 않고, 원문 검토 설정·기대 칸·번호 근거·계단선 연결·실제 내보낸 결과를 함께 확인했다.
- 견적 계산 로직이나 문서에 없는 수량 조건은 검증·승인하지 않았다. 현재 파싱 보류 목록은 758쪽 한 표다.

## 최신 수정본과 입력 파일

최신 작업 폴더: `experiments/parsing-all-held-resolution-2026-10-11`.

- 실행 코드: `pipeline/`.
- 후속 단계가 읽을 파싱 결과: `out/records.jsonl`.
- 원문 칸·기준·주석 보관: `out/store.json`.
- 레코드에서 원문으로 돌아가는 연결: `out/links.json`.
- 실제 실행 버전: `out/generation.json`.

- 확인 결과: `out/resume_checks.json`, `out/source_window_audit.json`, `out/numeric_position_audit.json`.
