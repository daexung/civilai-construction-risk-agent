# 실제 PDF 186·195·645쪽: 파싱부터 청킹까지 비교 (기준 코드 vs 두 수정안)

**실제 PDF 세 쪽에서 기준이 청크까지 전달됐다.** 다섯 대상 표(186쪽 6-1-3, 195쪽 6-3-5, 645쪽 4-1-1·4-1-3·4-1-4)의 `basis`가 모두 원문 기준대로 채워졌고, 표 값·제목·주변 주석은 바뀌거나 사라지지 않았다. 실패한 대상은 없다.

이 결과는 가상 기능 검사 입력이 아니라 **실제 `parse_pages`가 PDF에서 만든 레코드**를 기존 `make_chunks`에 넣은 것이다. 검사한 쪽은 세 개발 쪽뿐이며, 전체 문서의 정확성·검색·계산 명세·운영 적용을 검증한 것이 아니다.

## 실행 방법

- **기준 코드:** `git show baf186f:pipeline/parse.py`, `git show baf186f:pipeline/chunk.py`를 메모리 모듈로 읽었다. 저장소 파일은 건드리지 않았다.
- **수정안 모듈:** 기준 코드 소스 문자열에 두 수정안만 반영했다.
  1. `read_text_blocks`를 `parse-filter-reviewable-change-result.md`의 제안 함수로 교체(원문 함수가 소스에 정확히 한 번 일치함을 확인하고 교체).
  2. `parse_pages`의 동일 문자열 제거 루프에 기준 레코드 예외 한 줄 추가(`parse-repeated-basis-single-check-result.md`)와 `BASIS_RECORD_RE` 정의.
- **실행:** 두 모듈 각각 `parse_pages(PDF, 쪽, 쪽)`를 186·195·645쪽에 **쪽별로 한 번씩** 호출했다(`main` 미실행, 출력 파일 없음). 만든 레코드를 기준 코드 `make_chunks(records, PDF, {쪽: 부문})`에 넣었다. 부문은 `data/processed/page_map.json`에서 읽어 명시적으로 전달했다. 청킹 함수는 수정하지 않았고 `basis`는 직접 대입하지 않았다.
- 새 라이브러리 설치, ODL·Docling 실행, 전체 문서 재파싱은 하지 않았다. 저장소 코드·설정·데이터는 변경하지 않았고 커밋·푸시도 하지 않았다.

## 대상 표 비교

표 대응은 `p...-t...` 번호가 아니라 **절 번호·제목·bbox**로 확인했다. 기준 코드와 수정안의 표는 bbox가 완전히 같고, 기존 표 census(`experiments/table_census/results/tables.json`)의 같은 bbox 표 번호와도 일치한다. 두 수정안은 표 추출(`find_tables`)을 건드리지 않으므로 표 순번 차이는 없었다.

| 대상 | 원문 기준 | 기준 코드 청크 `basis` | 수정안 청크 `basis` | 표 값·제목·구조 | 검색용 글에 `기준 …` |
|---|---|---|---|---|---|
| 186쪽 6-1-3 표면 마무리 `p186-t0` | `(100㎡당)` | `None` | `(100㎡당)` | 동일 | 포함 |
| 195쪽 6-3-5 맨홀 거푸집 `p195-t3` | `(개소당)` | `None` | `(개소당)` | 동일 | 포함 |
| 645쪽 4-1-1 먹매김 `p645-t0` | `(㎡당)` | `None` | `(㎡당)` | 동일 | 포함 |
| 645쪽 4-1-3 마루바탕 `p645-t2` | `(일당)` | `None` | `(일당)` | 동일 | 포함 |
| 645쪽 4-1-4 마루널 `p645-t3` | `(일당)` | `None` | `(일당)` | 동일 | 포함 |

- 645쪽 4-1-3·4-1-4의 `(일당)`은 절 제목이 서로 달라 글이 다르므로, 동일 문자열 제거와 무관하게 남았다. 같은 절의 반복 기준 검사(`parse-repeated-basis-single-check`)와는 별개 확인이다. 이 세 쪽에서는 수정안 기준 레코드의 글 중복이 0건이라 중복 제거 수정은 결과에 영향을 주지 않았다.
- 참고(범위 밖 관찰): 195쪽 6-3-4 `p195-t2`는 `None → (㎡당)`, 645쪽 4-1-2 `p645-t1`은 `(일당)`으로 두 방식에서 같다. 195쪽 `p195-t0`도 `(일당)`으로 같다.

### 대상 표 청크 글자 (기준 코드 → 수정안)

- `p186-t0`: `6-1-3 표면 마무리 / 미장공 | 단위 인 | 수량 0.34` → 둘째 줄에 `기준 (100㎡당)`이 추가, 나머지 줄 동일.
- `p195-t3`: 표 4줄(`ø740 0.13 … ø1800 0.97`, `H = 1.0m` 포함) 동일, 제목 아래 `기준 (개소당)` 한 줄 추가.
- `p645-t0`: 값 줄(`거푸집 먹매김 주택 0.021 …`) 동일, `기준 (㎡당)` 추가.
- `p645-t2`·`p645-t3`: 값 줄(`수량 4 | 시공량(㎡) 155`, `… 70` 등) 동일, `기준 (일당)` 추가.

## 표 값·제목·주석 유지

- **표 청크 10개 전부**(186쪽 2, 195쪽 4, 645쪽 4)를 bbox로 짝지어 비교했다. `basis` 줄을 뺀 글, 절 제목, `structure`, 청크 ID가 모두 같다. `basis`만 `None → 기준`으로 바뀐 표는 6개다(위 5개와 `p195-t2`).
- **줄글 청크**: 쪽별 기준 코드 4·3·4개가 수정안에서 글이 모두 같고, 새로 생긴 줄글 청크는 없다. 기존 레코드 중 사라진 것은 없다(186쪽 19→20, 195쪽 22→24, 645쪽 17→20 레코드, 추가분은 기준 레코드뿐).
- **주변 주석**(`[주] …`): 대상 표 뒤 줄글 청크의 글이 기준 코드와 같다(예: 6-1-3 `[주] 본 품은 콘크리트 타설 후 쇠흙손을 이용하여 마감하는 기준이다.`).
- 추가된 레코드 전부:
  - 186쪽: `6-1-3 표면 마무리 | 설명 | (100㎡당)`
  - 195쪽: `6-3-4 … | 설명 | (㎡당)`, `6-3-5 … | 설명 | (개소당)`
  - 645쪽: `4-1-1 … | 설명 | (㎡당)`, `4-1-3 … | 설명 | (일당)`, `4-1-4 … | 설명 | (일당)`

## 청크 수와 줄글 ID 변화

청크 수는 쪽마다 같다(186쪽 6, 195쪽 7, 645쪽 8). 기준 레코드는 청크를 만들지 않고 다음 표의 `basis`가 되기 때문이다. 줄글 ID는 쪽 안 레코드 순번이 기준 레코드 추가로 밀려 바뀐다. 변화 전부가 "그 줄글보다 앞에 추가된 기준 레코드 수"로 설명된다.

| 쪽 | 기준 코드 ID → 수정안 ID | 설명 |
|---|---|---|
| 186 | `x4→x5`, `x6→x7`, `x16→x17` | 앞에 `(100㎡당)` 1개 추가 |
| 195 | `x5→x5`, `x14→x15`, `x20→x22` | `x5`는 앞에 추가 없음, `x14`는 `(㎡당)` 1개, `x20`은 `(㎡당)`·`(개소당)` 2개 |
| 645 | `x1→x2`, `x7→x8`, `x11→x13`, `x15→x18` | 앞에 추가된 기준 1·1·2·3개 |

표 ID(`p…-t…`)는 모두 같다. 청크 ID 사용처와 벡터·캐시·근거 혼용 위험은 `parse-filter-reviewable-change-result.md`의 "청크 ID 고지" 그대로이며, 이번에 새로 확인한 것은 아니다.

## 기준 코드 결과의 타당성 점검

기준 코드로 쪽별 실행한 청크를 저장된 `data/processed/chunks.all.jsonl`의 같은 ID 청크와 비교했다(`section`·`text`·`basis`).

- 645쪽 청크 8개는 전부 같다.
- 186쪽은 6개 중 5개가 같다. 다른 1개는 `p186-x0`(앞 쪽 6-1-2의 주석)으로, 쪽별 실행이라 앞 쪽 마지막 제목을 이어받지 못해 `section`이 빈 값이다.
- 195쪽은 7개 중 4개가 같다. 다른 3개(`p195-t0`, `p195-x5`, `p195-t1`)는 같은 이유로 `section`이 비어 있다(앞 쪽 6-3-3 문맥 없음). 대상 표 `p195-t2`·`p195-t3`는 같다.
- 이 차이는 두 수정안과 무관하게 기준 코드에서도 나타나며, 대상 표(6-1-3, 6-3-5, 4-1-1~4-1-4)의 절 제목에는 영향이 없다.

## 한계

- **쪽별 실행:** `parse_pages`를 쪽마다 따로 호출해 이전 쪽에서 이어받는 제목(`last_title`)이 없다. 그래서 쪽 맨 위 글과 쪽 위쪽 표(186쪽 `p186-x0`, 195쪽 `p195-t0`·`t1`)의 `section`이 빈 값이다. 동일 문자열 제거도 쪽 단위로만 적용되어, 쪽을 넘는 같은 글 제거는 이번에 확인하지 않았다. 전체 문서 실행과 완전히 같은 결과가 아니다.
- **구조 불확실 표:** `p645-t2`·`p645-t3`은 기존 저장 청크에서도 `structure=uncertain`이다(행 라벨이 `건축목공 보통인부`로 이어져 있음). 기준이 붙었어도 이 표의 계산 가능 여부가 바뀐 것은 아니다.
- **알려진 제목 오인 가능성:** 줄별 제목 판정은 블록 시작이 아니라 모든 줄에 `숫자-숫자 `형 정규식을 적용한다. 줄바꿈된 본문 줄이 우연히 이 형태로 시작하면 제외될 수 있다. 세 쪽에서는 사라진 레코드가 없었지만 다른 쪽에서의 위험은 이번 검사로 해소되지 않았다.
- **표와 기준의 연결 규칙:** `make_chunks`의 `pending_basis`(같은 절·같은 쪽 바로 앞 기준)가 이 세 쪽에서 맞게 작동했다는 것까지다. 표가 쪽을 넘거나 기준과 표 사이에 다른 글이 끼는 경우는 이번 입력에 없었다.
- **전체 적용 전 필요한 것:** 전체 파이프라인 회귀 검사(전체 문서 재파싱·재청킹, `parsed`·`chunks`·벡터 동시 갱신, 줄글 ID 대응, 183개 후보 점검)는 미실행이다. 운영 적용도 하지 않았다.
