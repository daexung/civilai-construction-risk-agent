## DEC-3 v2 큰 그림: AI 기본 2회·최대 3회, 상담·견적 공통 검색, 숫자 빈칸 방식

- **상태:** 확정 (2026-11-08)
- **관련 문서:** [에이전트 v2 설계](에이전트-v2-설계.md) 0장(큰 그림)
- **이유:** 외부 LLM 검토 2회를 반영. 근거 고르기와 답 쓰기를 합쳐 속도·뜻 변형을 줄이고, 숫자는 AI가 다시 쓰지 않게 해 숫자 검사 실패를 줄인다. 상담·견적이 같은 원문 항목 찾기를 써서 섞인 질문을 요청별로 처리한다. 결과 상태 4가지(통과·근거 부족·출력 오류·처리 실패)를 요청별로 기록한다. 빈칸 방식의 실제 구현 가능성은 원문 DB 점검 후 정한다(검증 필요).
- **검토한 다른 방법:** AI 하나가 도구를 알아서 고르는 에이전트 루프(경로 예측·검증 어려움, 느림) / 근거 고르기·답 쓰기 분리 3회 직렬(느림) / AI 실패 시 형태소 분석기 예비 경로(낱말 규칙 재발) / 비슷한 질문 답 재사용(15mm·20mm처럼 답이 달라 위험) / 조건 검사를 행·열 제목 문자열 포함으로(다른 열 숫자 오인)

## DEC-2 에이전트 판단층을 다시 설계한다: 뜻 판단은 AI, 사실 확인은 코드, 노드끼리는 스키마로만

- **상태:** 검토 중 (2026-11-08)
- **관련 문서:** [에이전트 v2 설계](에이전트-v2-설계.md)
- **이유:** 첫 질문 갈래(`_rule_route`)와 상담 보류 판단이 손으로 적은 낱말 목록에 기대 있어 평범한 질문이 범위 밖으로 가고, 상담 시험 6문 중 5문이 말끝(되나요 등)을 공종 이름으로 착각해 보류됐다. 판단하는 곳이 dialogue.py 안 여섯 곳에 흩어져 있고, 응답 형태도 25개 필드 한 덩어리다.
- **검토한 다른 방법:** ① 말끝 목록에 낱말을 더 넣기: 끝이 없고 같은 문제가 반복된다. ② 전체(자료·계산 포함)를 처음부터 다시 만들기: 원문 DB·계산 엔진·명세 대조는 문제가 없고 버리면 손해가 크다.

## DEC-1 명세는 저장본으로 쓰고, 없으면 LLM이 원문을 즉시 읽는 혼합 구조

- **상태:** 검토 중 (2026-11-05)
- **이유:** 명세는 LLM이 PDF를 읽은 결과를 저장해 둔 것이라 일관성, 사전 검토, 속도, 비용에서 유리하다. 매번 읽는 방식은 개정에 강하지만 답이 흔들리고, 어려운 표(쪽 넘김, 분수식, 참조 주석)에서 매번 틀릴 위험이 있다.
- **검토한 다른 방법:** (1) 명세 925개를 미리 다 만들고 사람이 전부 검토 (2) 명세 없이 질문마다 LLM이 PDF 원문을 읽고 값을 뽑음

### 제안

- **이해**(의도, 범위, 공종 선택, 조건 읽기): 좋은 LLM + 구조화 출력 + 서버 검증으로 처리하고, 정규식과 if문(scope.py, route.py, dialogue.py)을 걷어낸다.
- **계산**: 코드가 한다. 계산기 4종에 명세 데이터를 넣어 숫자를 낸다.
- **명세 선택**
  - 검증된 명세가 있으면 명세로 계산한다.
  - 없거나 검토 전이면 LLM이 원문 표를 즉시 읽어 값을 뽑고 코드가 계산한다. "검토 전"으로 표시하고, 뽑은 값은 명세 초안으로 자동 저장한다.
- **매년 개정**: 새 PDF로 명세를 다시 뽑아 작년 명세와 자동 비교하고, 바뀐 부분만 사람이 검토한다.
- **검토 우선순위**: 자주 묻는 공종 20~30개부터 검토한다.

### 현재 상태 (2026-11-05)

- 명세 925개 중 사람이 검토한 것은 1개(6-1-4 펌프)뿐이다.
- 원문 청킹·임베딩은 찾기용이고, 명세는 계산용이다.

### 다른 LLM 의견

#### 의견 1 (2026-11-05)

- **동의**: 계산을 코드로 분리한 것은 올바르다. 질문 이해의 if문을 걷어내는 것이 1순위다. 자주 묻는 공종 20~30개를 완벽하게 검증하는 것이 925개 초안보다 가치가 크다.
- **반대**: 계산용 값을 질문마다 PDF에서 즉시 뽑는 방식은 버려야 한다. 표 아래 주석(할증, 적용 제외)을 놓치기 쉽고, 느리며, B2B에서는 "검토 전" 표시가 면책이 되지 않는다. 틀린 숫자 하나에 서비스 가치가 0이 된다.
- **반대**: 즉시 뽑은 값을 초안으로 저장해 다른 사용자에게 다시 쓰면 오류가 퍼진다(초안 오염).
- **제안**: 명세가 없는 공종은 "준비 중"으로 답하고, 질문 로그를 모아 사람이 명세를 추가한다. 계산 전에 "이해한 조건"을 보여주고 사용자가 고칠 수 있게 한다.

#### Claude 검토

- 초안 오염 지적은 맞다. 그런데 **지금 운영에서 이미 같은 일이 일어나고 있다.** 검토 전 초안 924개가 실행 목록(executable.json)에 올라 "AI 초안 · 검토 전" 표시와 함께 실제 계산에 쓰인다.
- "준비 중"만 답하면 검증된 공종이 1개라 초기에 거의 모든 질문이 막힌다. 중간안으로, 계산은 하지 않고 원문 표와 주석을 근거와 함께 보여주는 상담 답을 주면 된다. 의견 1도 원문 질의응답에는 즉시 검색이 괜찮다고 했다.
- 조건 확인 화면은 해결과제 '질문 과다'와 충돌한다. 계산 전에 한 번 더 묻는 대신, 결과 옆에 "이해한 조건"을 보여주고 바로 고칠 수 있게 하는 쪽이 낫다.
- 표를 PostgreSQL로 옮기라는 제안은 지금 필요 없다. 명세 JSON이 이미 그 역할(정형 데이터)을 한다.

#### 의견 2 (2026-11-05)

- **핵심**: 가장 큰 위험은 계산 오류가 아니라, 틀린 표·조건·규칙을 고른 뒤 코드가 그것을 정확하게 계산하는 것이다.
- **검증 4단계**: 원문 일치(값·단위·행·열) → 적용 타당성(이 작업에 이 표·할증이 맞는가) → 계산 정확성 → 설명 일치. 지금의 숫자 대조는 마지막 단계의 일부만 본다.
- **작업 묶기**: 작업을 나눌 뿐 아니라 함께 판단해야 하는 작업을 묶는 단계가 필요하다(예: 소규모 기준은 여러 규격의 소요일수를 합쳐 판단).
- **표현 못 하는 규칙은 멈추기**: 계산 유형 4종에 억지로 넣지 말고 계산을 중단한다(할증 합산·중복 금지·적용 순서 등).
- **if문 전부 걷기에는 반대**: 자연어 해석용 정규식만 줄이고, 단위·필수 조건·모순·미지원 공법·유효기간 검사는 코드에 남긴다. 조건마다 사용자 명시 / 프로젝트 설정 / 시스템 가정을 구분한다.
- **저장 구분**: 원문에서 뽑은 공통 사실과 이번 견적에만 해당하는 판단을 섞지 않는다. 반복 사용이나 사용자 동의만으로 검토 완료로 올리지 않는다.
- **재현성**: 입력 조건, 품셈 판본·정오표, 단가·요율 버전, 사용 명세, 계산 엔진 버전, 사용자 수정값을 함께 보존한다.
- **연간 갱신**: LLM 결과끼리 비교하지 말고 공식 개정자료·정오표와 원문 변경부터 확인한다 → 바뀐 표·주석·공통 규칙을 찾는다 → 그것을 참조하는 명세를 검토 대상으로 돌린다 → 계산 사례를 다시 돌려 승인한다.
- **즉시 추출**: 조건부 찬성. 드문 공종, 프로젝트별 문서, 전문가 검토 도구, 신규 항목 탐색에는 유리하다. 표 전체·다단 머리글·주석·공통 기준을 함께 준다.
- **1인 창업 순서**: (1) 첫 고객과 첫 산출물을 좁힌다 (2) 실제 견적 사례로 평가 기준을 만든다 (3) 작은 범위(한 공종군 20개 + 공통 기준)를 끝까지 검토한다 (4) 검토 화면과 계산 이력을 만든다 (5) 그다음 LLM 질문 이해와 즉시 추출을 넓힌다.
- **가장 강한 반대**: "925개를 만들어 놨으니 대부분 지원한다"는 해석. 초기 약속은 "지원 공종의 견적 초안을 근거와 함께 만들고, 실무자가 확인·수정하는 시간을 줄인다"로 좁힌다.

#### 두 의견 비교 (Claude)

- **같은 점**: 계산은 코드, 검증된 명세 우선, 질문 이해는 LLM, 검토 전 표시는 면책이 아님, 작게 시작.
- **다른 점**: 즉시 추출을 의견 1은 폐기, 의견 2는 초안 수집용으로 허용한다. 순서는 의견 1이 if문 제거 먼저, 의견 2는 고객·평가 사례 먼저다.
- **현재 코드와 비교**
  - 조건 출처 구분: 일부 있다(공통 조건의 default/answer, explicit).
  - 단가·장비 요율 버전 저장: 있다(rate_version).
  - 품셈 판본·정오표 버전: 없다.
  - 소규모 합산 같은 묶음 판단: 6장 일부 명세에만 있다.
  - 원문 일치·적용 타당성 검증: 명세 단위로는 없다. 답변 숫자 대조(reply_check)만 있다.
- **판단**: 순서는 의견 2가 맞다. 평가 사례가 없으면 if문을 LLM으로 바꾼 뒤 더 나아졌는지 알 수 없다. 즉시 추출은 "계산은 하지 않고 원문·초안을 보여주며 후보로 수집"이 두 의견의 공통분모다.

### 수정안 2 (두 의견 반영, 아직 검토 중)

1. 첫 고객·첫 산출물을 좁힌다. (사업 결정)
2. 실제 견적 사례로 평가 세트를 만든다. 아버지·적산 실무자 도움.
3. 그 범위의 명세 약 20개 + 관련 공통 기준을 끝까지 검토한다. 검토 상태에 판본과 확인한 조건 범위를 붙인다.
4. 검토 화면과 계산 이력(원문 위치, 고른 행·열, 적용·제외 규칙, 계산식, 판본)을 만든다.
5. 자연어 해석은 LLM으로 바꾸고, 검사 규칙(단위·필수·모순·미지원)은 코드에 남긴다.
6. 검토 범위 밖 공종: 계산하지 않고 원문 표·주석과 근거를 보여준다. 질문은 후보로 수집한다.
7. 명세로 표현하지 못하는 규칙을 만나면 계산을 멈춘다.
8. 연간 갱신은 원문·정오표 변경부터 찾고, 의존하는 명세를 다시 검토한다.

### 자동 검증 시범: 1단계 원문 대조 (2026-11-05)

- 대상: 공통 6장(콘크리트·철근·거푸집·교량·PC) 실행 명세 37개. 파싱된 원문(chunks.all.jsonl)과 코드로 대조했고, 외부 호출은 없다.
- 도구: `evals/check_spec_source_match.py` (커밋 전)
- **명세 단위**: 통과 16, 경고 3(계산에 영향을 주는 주석 미언급), 확인 필요 18, 불일치 0
- **숫자 값 단위 (450개)**
  - 원문의 같은 칸에서 확인: 333 (74%)
  - 숫자는 표에 있으나 칸을 글만으로 확정하지 못함: 116. 원인은 거의 파싱 흔적이다(직종 이름이 한 칸으로 뭉침, 행·머리글이 쪽개짐).
  - 원문 빈칸을 0으로 채움: 1
  - **원문에 없는 값: 0**
- 인용문 검사: 문제 0
- 계산에 영향을 주는데 명세가 언급하지 않은 주석: 8건 (예: 6-3-1 폼타이 수량·구멍때 별도 계상)
- 검사기 신뢰도: 통과한 명세의 값 121개를 일부러 틀리게 바꾼 시험에서, 다른 칸 값으로 바꾸기 121/121, 없는 값으로 바꾸기 121/121을 잡았다.
- **해석**: AI 초안의 값은 원문 글이 또렷한 곳에서는 틀린 것이 하나도 없었다. 남은 위험은 (1) 파싱이 뭉개진 표의 칸 확인 (2) 빠진 주석 두 가지다.
- **다음**: 확인 필요 18개는 원문 표 이미지를 보고 판단해야 한다. 사람이 보거나, 2단계(다른 모델이 표 이미지를 읽어 교차 추출)로 줄인다. 같은 검사를 나머지 장에도 돌릴 수 있다.
