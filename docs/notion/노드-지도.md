기준: 2026-11-05 코드 (브랜치 codex/hotfix-conversation-20261101)

## 엔진이 두 개다

- **옛 그래프** (`backend/agent/graph.py`): 노드 11개. route → retrieve → select → fill → ask → gate → compute → price → statement → compose / answer. 예전에 시작한 대화에서만 쓴다.
- **새 대화 엔진** (`backend/agent/estimate/dialogue.py`): LangGraph 노드는 `turn` 하나뿐이고, 그 안에 1,425줄 파이썬 분기가 있다. `AGENT_MODE=tools`가 기본값이라 **새 대화는 모두 이쪽**으로 간다.
- 옛 노드 함수(검색, 공종 선택, 조건 추출, 라우팅 규칙)는 새 엔진 안에서 부품으로 다시 쓰인다.

## 현재 노드: 첫 질문부터 답변까지

1. **화면 → 서버** (`main.py` /api/chat): 회원·비회원 확인, 사용 횟수 차감. `_uses_dialogue`가 엔진을 정한다.
2. **질문 종류 판단** (`route.py` `_rule_route`): 단어 규칙. 돈 관련 말(비용·얼마·견적)이 있으면 견적, 품·인원·몇 명이면 상담.
3. **견적일 때**
   1. 범위 나누기 (`scope.py`): 여러 작업이 섞였는지 본다. 애매하면 범위 확인 카드를 보내고 턴이 끝난다.
   2. 견적 세션 만들기: 확정된 작업마다 항목을 하나씩 만든다.
   3. 작업마다 도구 실행. LLM이 도구를 고르고, 한 턴에 최대 4번 실행한다.
      - `find_work`: 원문 검색 → 공종 후보 선택. 확실하지 않으면 되묻는다.
      - `set_conditions`: 조건·물량을 원문 근거와 대조해 검증한다.
      - `compute_labor`: 품(인원·작업일수·장비)을 계산한다.
      - `estimate_cost`: 일위대가와 원가계산서를 만든다.
      - LLM이 실패하면 같은 도구를 규칙 순서대로 부른다.
   4. 부족한 조건은 질문 카드로 묻는다. 사용자가 답하면 다음 턴에 3번부터 다시 진행한다.
   5. 합치기 (`aggregate.py`): 작업별 직접비를 더해 통합 원가계산서를 한 번 만든다.
4. **상담일 때**: `search_standard`로 원문 문단을 찾는다. `KNOWLEDGE_RETRIEVAL=v1`이면 검증형 답을 그대로 쓴다.
5. **답변 문장**: 서버가 템플릿 답을 만든다 → LLM이 문장을 다듬는다 → `reply_check`가 숫자를 대조하고, 틀리면 템플릿으로 되돌린다.
6. **화면·Excel** (`dialogue_service.py`): 결과를 화면 형식으로 바꾼다.

- 한 턴 한도: LLM 6회, 도구 4회, 25초.

## 잘 된 점 (유지)

- LLM은 도구 선택과 문장만 맡고, 숫자는 서버가 계산하고 검증한다.

## 부족한 점 (중요한 순서)

1. **계산 명세 925개 중 사람이 검토한 것은 1개** (6-1-4 펌프)다. 924개는 "AI 초안 · 검토 전". 유료 서비스의 가장 큰 위험이다.
2. **흐름이 노드가 아니라 if문 속에 숨어 있다.** 범위 → 공종 → 조건 → 계산 → 가격 → 답변이 모두 노드 하나에 들어 있어서 구조가 보이지 않고, 고칠 때마다 부작용이 생기기 쉽다.
3. **판단하는 곳이 흩어져 있다**: 엔진 선택(main.py), 견적·상담 구분(route.py 규칙), 범위 나누기(scope.py 정규식, 도장·조적·방수·철거 4개 공종만 인식).
4. **옛 그래프가 남아 있어** 두 엔진을 함께 관리하는 비용이 든다.
5. **상담 경로**: 배포 설정 기본값이 `legacy`라 검증형 지식 검색(4h/5b)이 운영에서 꺼져 있을 수 있다. 실제 값은 GitHub 변수에서 확인해야 한다.
