> 노션에서 옮김 (2026-11-08). 시험 예문·결과는 [라우터 v2 시험](라우터-v2-시험.md).

상태: **초안 · 검토 중** (2026-11-08). 사장님·아버님 검토 후 확정한다. 확정 전에는 코드를 바꾸지 않는다.

## 0. 큰 그림 (2026-11-08 확정, 외부 검토 2회 반영)

아래 4장 이후의 상세 노드는 이 큰 그림에 맞춰 다시 정리한다. 이 절이 우선한다.

```txt
1 질문 받기 → 2 질문 이해하기(AI ①) → 3 요청마다 길 보내기(코드)
   ├─ 상담·견적 요청 → 4 원문 항목 찾기 + 근거 묶음(코드, 공통)
   │     ├─ A 상담: 근거 판단·답 구성(AI ②) → 검사(코드) → 숫자 넣기(코드)
   │     │        └─ 근거 부족: 추가 검색 → AI ③ → 재검사 / 출력 오류: 오류 전달 → AI ③ → 재검사
   │     └─ B 견적: 항목 확정(AI 또는 사용자) → 조건 → 계산(코드) → 정해진 문장으로 표시
   ├─ C 되묻기
   └─ D 범위 밖
→ 9 화면에 보내기
```

**확정**

- **AI 호출:** 기본 2회(① 이해, ② 근거 판단·답 구성). 수정·보완을 포함해 **전체 최대 3회**. ①의 출력 수정에 호출을 썼다면 이후 보완 호출은 없다.
- **요청별 실행:** 질문 하나에 요청이 여럿일 수 있다("몇 인이고 얼마예요?"). 3은 하나를 고르지 않고 요청마다 길을 보낸다. 상담 부분은 먼저 답하고, 견적에 필요한 조건만 묻는다(B0와 같은 방향).
- **결과 상태 4가지, 요청별로 기록:** 통과 / 근거 부족 / 출력 오류 / 처리 실패. "원문에 근거가 없음"과 "처리하지 못함"을 섞지 않는다.
- **"못 찾음"과 "금지됨"을 구분:** 금지·허용 결론에는 직접 근거가 있어야 한다. 없으면 "확인한 원문에서는 근거를 찾지 못했다"까지만 말한다.
- **숫자 빈칸 방식:** AI ②는 "배관공 품은 {값}입니다"처럼 빈칸과 표 칸 번호만 고른다. 숫자·단위·기준량은 코드가 원문에서 넣는다.
- **조건 검사는 같은 속성끼리:** AI가 사용자 조건과 표 조건을 각각 `구경 → 15mm`처럼 대응시키고, 코드는 출처와 정규화한 값을 대조한다. 속성이나 단위가 불명확하면 '확인 필요'. 단순 문자열 포함 검사는 쓰지 않는다(다른 열의 숫자를 잘못 잡는다).
- **찾은 항목 ≠ 확정한 항목:** 상담에서 관련 항목으로 보여 준 것을 견적이 바로 계산하지 않는다. 견적은 항목·조건을 AI 판단 또는 사용자 확인으로 확정한 뒤 계산한다.
- **견적 결과 문장:** 처음에는 정해진 문장으로 표시한다(AI 문장 생략).
- **처음부터 넣을 안전장치:** 문서 버전, 출처 위치, 표 소속 확정 여부, 확인 못 한 참조 표시. 참조 자동 따라가기·캐시는 나중에.
- **쓰지 않는 것:** AI 실패 시 형태소·낱말 규칙으로 계속 진행하기, 비슷한 질문 답 재사용(15mm·20mm처럼 답이 다르다), 동의어 사전을 코드 분기에 쓰기(AI 참고 자료로만).

**검증 필요 (DB 점검 결과로 정함)**

- 빈칸 방식을 지금 원문 DB로 만들 수 있는지. 완료 조건: ① 셀을 안정적으로 식별하고 원문 위치로 돌아갈 수 있다 ② 다단·병합 제목을 포함해 행·열 조건을 복원할 수 있다 ③ 단위와 기준량을 구분하고 각각 출처가 있다 ④ 적용 주석과 절 소속의 확정·미확정 상태가 보존된다 ⑤ 원문 표기와 비교용 정규화 값을 따로 둔다(`0.50`과 `0.5`는 같게 비교, 표기는 유지).
- 지난번 답 검사 실패 2문(소재 표면처리 도장공, Ventri Scrubber 제관공)이 해결되는지 — 다시 시험할 질문으로 둔다. 빈칸 방식도 20mm 행을 골라 15mm 질문에 답하는 오류는 막지 못한다.

- **진동기 질문:** 원문에 직접 근거가 있다(6-1-4 주① "진동기를 사용하지 않는 경우 콘크리트공과 특별인부를 각 1인 제외"). '명시적 허용' 시험 사례로 쓴다.

**판단:** 빈칸 방식은 한 장짜리 표에서는 지금 DB로 만들 수 있다. 먼저 필요한 자료 작업 3가지: ① 잘린 표 잇기(후보 106개) ② 기준량 연결 확정(미확정이면 답에 '기준량 확인 필요' 표시) ③ 칸마다 정규화 값 추가(띄어쓴 글자 붙이기, 숫자 변환, 원문 표기는 유지). 설계에는 '계산 빈칸'을 더한다.

## 0-1. 라우터 ([2] 질문 이해 + [3] 길 보내기) — 2026-11-08 초안 (R1)

아래 4장의 [2]·[3]보다 이 절이 우선한다.

**큰 갈래 4가지**

| 갈래 | 들어가는 것 |
| --- | --- |
| 견적 | 새 견적, 진행 중 견적 바꾸기, 진행 중 견적에 대한 질문, 글자로 입력한 카드 답 |
| 단순 질문(상담) | 품셈 값·조건·정의·적용 가능 여부 |
| 범위 밖 | 품셈과 무관한 질문, 인사·잡담 |
| 다시 물어보기 | 뜻이 애매해 갈래를 정할 수 없을 때 |

- 한 질문에 견적과 질문이 섞이면 요청을 나눠 각각 꼬리표를 단다. [3]은 요청마다 길을 보낸다.

**들어오는 길 두 가지**

```txt
버튼 답   ──────────────────────────→ 견적 에이전트 (라우터 안 거침)
글자 입력 → 라우터(직전 대화·떠 있는 카드 함께 봄)
              ├ 견적 (새 견적 / 바꾸기 / 진행 중 질문 / 카드 답)
              ├ 단순 질문
              ├ 범위 밖
              └ 다시 물어보기
```

- 버튼 답은 화면이 `{question_id, 값}` 형태로 보낸다. 뜻을 판단할 게 없고 입력 형태가 다르므로 낱말 규칙이 아니다.
- 카드가 떠 있어도 글자로 입력하면 라우터를 거친다. "철근이요"(카드 답)인지 "펌프카 할증 있어요?"(새 질문)인지는 뜻을 봐야 안다.

**[2] 입력 `RouterInput`**

```json
{
  "message": "사용자 문장 원문",
  "previous": {
    "kind": "qa_answer | estimate_result | needs_input | null",
    "work": "진행 중 견적 공종 | null",
    "pending_questions": [Question],
    "last_answer_summary": "직전 답 한 줄 | null"
  }
}
```

**[2] 출력 `RouterOutput`**

```json
{
  "route": "work | out_of_scope | clarify",
  "requests": [{
    "id": "r1",
    "kind": "estimate | qa",
    "estimate_mode": "new | change | ask_about | card_answer | none",
    "target": { "user_text": "벽체 콘크리트 타설", "evidence": "벽체 콘크리트를", "search_terms": ["콘크리트 펌프차 타설"] } | null,
    "quantity": { "value": "260", "unit": "㎥", "evidence": "260㎥" } | null,
    "conditions": [{ "text": "펌프카 사용", "evidence": "펌프카로" }],
    "asks": "무엇을 묻는지 한 줄",
    "wants": "explain | value | calculate",
    "card_answer": { "question_id": "q3", "value": "철근콘크리트", "evidence": "철근이요" } | null
  }],
  "clarify": { "ask": "어떤 작업의 견적을 원하세요?", "options": [] } | null,
  "out_of_scope_kind": "unrelated | chitchat | none",
  "confidence": 0.0
}
```

- 4갈래와의 대응: 견적 = `work` + `kind: estimate`, 단순 질문 = `work` + `kind: qa`, 범위 밖 = `out_of_scope`, 다시 물어보기 = `clarify`.
- **코드 검사(사실만):** `evidence`가 사용자 문장에 글자 그대로 있는지, 물량 숫자·단위가 문장과 같은지, 선택지 값이 목록 안인지, `work`면 요청이 1개 이상인지, `clarify`면 물을 문장이 있는지, 카드 답이면 `question_id`가 떠 있는 카드인지와 값이 허용값 안인지.
- **검사 실패:** 한 번만 고쳐 달라고 다시 부른다(AI 호출 예산 안에서). 그래도 실패하면 '출력 오류'로 보여주고 기록한다. 낱말 규칙으로 대신 고르지 않는다.

**[3] 길 보내기 (코드)**: `clarify` → C1 질문 카드 / `out_of_scope` → X1 안내 / `work` → 요청마다 `estimate`는 B 견적 길, `qa`는 A 상담 길. 사용자 문장의 낱말은 보지 않는다.

**예시**

| 상황·질문 | route | requests |
| --- | --- | --- |
| "자동문 3개소 설치비 견적 내주세요" | work | r1 estimate·new, 대상 자동문 설치, 물량 3 개소 |
| "진동기 없이 콘크리트 타설하면 인원 줄여도 되나요?" | work | r1 qa, 대상 콘크리트 타설, 조건 진동기 없이, 묻는 것 인원 감축 가능 여부 |
| "벽체 콘크리트 260㎥ 펌프카로 타설하면 얼마고, 할증도 있어요?" | work | r1 estimate·new(260㎥, 펌프카) + r2 qa(할증 조건) |
| (견적 중, 카드 "구조물 종류?" 떠 있음) "철근이요" | work | r1 estimate·card_answer(q번호, 철근콘크리트, 근거 "철근이요") |
| (견적 중) "물량 300으로 바꿔줘" | work | r1 estimate·change, 물량 300 |
| (견적 중) "인건비가 왜 이렇게 나와요?" | work | r1 estimate·ask_about |
| "오늘 점심 뭐 먹지" | out_of_scope | 없음(chitchat) |
| (직전 대화 없음) "그거 얼마예요?" | clarify | 없음, 물을 것 "어떤 작업의 견적을 원하세요?" |

**정식 스키마·규칙 (R2, 2026-11-08 코드 반영)**

| 칸 | 형태 | 허용 값 / 규칙 |
| --- | --- | --- |
| route | 필수, enum | work · out_of_scope · clarify |
| requests[] | 필수, 목록 | work면 1개 이상, 아니면 빈 목록. id는 겹치지 않음 |
| requests[].kind | 필수, enum | estimate · qa |
| requests[].estimate_mode | 필수, enum | new · change · ask_about · card_answer · none. qa면 none, estimate면 none 아님 |
| requests[].target | 객체 또는 null | user_text, evidence, search_terms[]. new 견적이면 필수(모르면 clarify) |
| requests[].quantity | 객체 또는 null | value, unit, evidence. 숫자·단위가 문장에 있어야 함 |
| requests[].conditions[] | 목록 | text, evidence |
| requests[].asks | 필수, 글 | 무엇을 묻는지 한 줄 |
| requests[].wants | 필수, enum | explain(기준·뜻 설명) · value(원문 값: 품·인원·할증률) · calculate(계산 결과: 금액·기간·총 품). 사용자가 원하는 결과로 고른다. 낱말로 고르지 않는다 |
| requests[].card_answer | 객체 또는 null | estimate_mode=card_answer일 때만. question_id는 떠 있는 카드, value는 allowed_values 안 |
| clarify | 객체 또는 null | route=clarify일 때만, ask는 비면 안 됨 |
| out_of_scope_kind | 필수, enum | unrelated · chitchat · none. route=out_of_scope일 때만 none 아님 |
| confidence | 필수, 0~1 | 기록용. 코드가 이 값으로 판단을 뒤집지 않음 |

- **추출값은 확정값이 아니다 (2026-11-08 추가):** 라우터는 문장에 적힌 값과 그 위치만 뽑는다. 코드는 그 값이 문장에 있는지만 확인한다. 120㎡가 시공 면적인지 제외 면적인지, 어느 계산에 쓰이는지는 견적 단계가 판단하고 필수 조건을 확인한다.
- **애매할 때 (2026-11-08 추가):** 대상·원하는 결과가 분명하면 바로 답한다. 일부만 답할 수 있으면 그 부분을 work로 보내고 나머지 필요한 조건은 다음 단계가 묻는다. 원하는 결과 자체가 없으면("타일 80㎡ 좀 봐줘") clarify로 짧은 선택형 질문(options)을 만든다. 상담 답 아래 '이 조건으로 견적 내기' 버튼은 후속 기능이며 애매한 질문을 대신 풀지 않는다.
- **갈래 기준은 낱말이 아니라 원하는 결과:** "간접노무비 계산 기준은?"은 돈 낱말이 있어도 qa·explain. "타일 80㎡ 며칠 걸려?"는 돈이 없어도 qa·calculate(작업 인원 등 조건 필요). "블록 120㎡ 인건비랑 할증 붙어?"는 estimate·calculate + qa·value. 견적(estimate)은 사용자가 금액 계산 결과를 원할 때다.
- 추가 규칙: change·ask_about은 진행 중 견적(previous.work)이 있어야 한다. 모든 evidence는 공백을 무시하고 사용자 문장에 글자 그대로 있어야 한다.

**라우팅 원리 (키워드 기반 아님)**

1. **구조화 출력:** Gemini에 response_schema(enum 포함)를 줘서 정해진 JSON만 받는다.
2. **시스템 프롬프트:** 갈래 정의와 판단 순서를 적는다. ① 떠 있는 카드의 답인지 먼저 본다 → ② 진행 중 견적을 바꾸거나 묻는지 → ③ 원하는 결과가 여럿이면 나눈다 → ④ 답할 수 있는 부분은 work로 → ⑤ 원하는 결과 자체를 모를 때만 clarify.
3. **few-shot 13개:** 모두 지어낸 예시(시험 질문과 겹치지 않음). 새 견적·인원 질문·섞인 질문·카드 글 답·카드 떠 있는데 새 질문·물량 바꾸기·결과 묻기·기간 계산·기준 설명·선택형 되묻기·영화 추천·인사·대상 모를 때.
4. **직전 맥락:** previous(종류·공종·떠 있는 카드·직전 답 한 줄)를 함께 넘긴다.
5. **코드 검사 + 한 번 고치기:** 위 규칙을 어기면 오류 목록을 붙여 한 번만 다시 부른다(라우터 최대 2회). 그래도 틀리면 '출력 오류', AI 호출 자체가 안 되면 '처리 실패'. 코드는 enum 값으로만 다음 노드를 고른다.

## 1. 왜 다시 설계하나

- 첫 질문을 견적·상담으로 나누는 판단이 낱말 규칙(`_rule_route`)이다. 운영에서 AI 판단이 켜져 있어도 이 규칙이 먼저 갈래를 정한다. "벽돌 1000장 쌓는데 며칠 걸려?", "도배 하루에 몇 평 해?"가 범위 밖으로 분류된다.
- 같은 낱말 규칙을 대화 엔진(`dialogue.py`, 1,472줄) 안 여섯 곳에서 따로 부른다. 판단하는 곳이 흩어져 있다.
- 상담 답 보류 원인: 질문 낱말이 원문에 글자 그대로 없으면 보류하는데, 말끝 목록이 손으로 적혀 있어 `되나요`→"되나"를 공종 이름으로 착각한다. 상담 시험 6문 중 5문이 이 이유로 보류됐다.
- 응답 형태가 필드 25개짜리 한 덩어리다. 상담·견적·되묻기가 같은 그릇에 섞여 있다.
- 시험에서 틀릴 때마다 규칙을 덧붙이는 방식으로 고쳐 왔다. 처음에 원칙과 입출력을 정하지 않은 것이 근본 원인이다.

## 2. 원칙

1. **뜻 판단은 AI, 사실 확인은 코드.** 코드가 사용자 문장의 낱말을 보고 갈래를 고르지 않는다.
2. **노드끼리는 스키마로만 주고받는다.** 모든 노드는 입력·출력 형태가 정해져 있고, 한 노드의 출력이 다음 노드의 입력이다.
3. **AI 출력은 항상 정해진 JSON(구조화 출력)으로 받고, 코드가 검사한 뒤 넘긴다.** 검사 실패는 오류로 기록한다.
4. **선택지(enum) 자체는 괜찮다.** 문제는 코드가 낱말을 보고 선택지를 고르는 것이다. 선택지는 AI가 고르고, 코드는 그 값으로 갈래만 나눈다.
5. **사용자 응답은 종류(kind)별로 형태가 하나다.**
6. **AI가 실패하면 실패라고 표시한다.** 예비 경로를 쓰더라도 "AI 실패" 표시를 남긴다. (정할 것 ②)

## 3. 전체 흐름

```txt
[1 입력] → [2 이해 · AI] → [3 갈래 · 코드]
   ├─ 상담:   [Q1 원문 검색] → [Q2 근거 고르기 · AI] → [Q3 근거 검사] → [Q4 답 쓰기 · AI] → [Q5 답 검사]
   ├─ 견적:   [E1 공종 찾기 · 검색+AI] → [E2 조건 채우기] → [E3 품 계산] → [E4 가격] → [E5 원가계산서] → [E6 답 쓰기 · AI + 검사]
   ├─ 되묻기: [C1 질문 카드]
   └─ 범위 밖: [X1 안내]
→ [9 응답 조립] → 화면
```

- AI 노드: 2, Q2, Q4, E1(후보 고르기), E6(문장). 나머지는 코드.
- 계산(E3~E5)은 지금 코드(`calc/`)를 그대로 쓴다.

### [2] 이해 (AI) — 새로 만드는 핵심 노드

- 입력: `TurnInput`
- 출력 → [3]: `Understanding`
- 하는 일: 사용자가 무엇을 원하는지, 대상 작업·물량·조건이 무엇인지 한 번에 판단한다. 지금의 `_rule_route`, `_lookup_only`, `_cost_target`, `scope.py` 정규식, 말끝 목록을 모두 대신한다.

```json
Understanding {
  "intent": "estimate | qa | change | lookup | answer_card | out_of_scope | chitchat",
  "confidence": 0.0,
  "focus": "cost | value | method | definition | applicability | list",
  "targets": [{
    "work_text": "벽체 콘크리트 타설",          // 사용자 표현 그대로
    "evidence": "벽체 콘크리트를",              // 사용자 문장 안의 구절
    "standard_terms": ["콘크리트 펌프차 타설"],  // 품셈 용어로 바꾼 말 (검색용)
    "quantity": { "value": "260", "unit": "㎥", "evidence": "260㎥" } | null,
    "conditions": [{ "text": "붐 길이 32m", "evidence": "32m" }],
    "excluded": false                           // "철근은 빼고" 같은 제외
  }],
  "search_queries": ["콘크리트 펌프차 타설 32m 붐 벽체"],
  "refers_to_previous": true,
  "ambiguity": { "ask": "어느 견적을 바꿀까요?", "options": ["현재 견적", "새 견적"] } | null
}
```

- 코드 검사: `evidence`가 사용자 문장 안에 글자 그대로 있는지, 숫자·단위가 문장과 같은지, 선택지 값이 정해진 목록 안인지. 통과 못 한 값은 버리고 기록한다.
- intent 뜻: estimate=돈을 묻는 새 견적 / qa=돈 없이 품셈을 물음 / change=진행 중 견적의 물량·조건 변경 / lookup=진행 중 견적에 대한 조회·설명 / answer_card=질문 카드에 대한 답 / out_of_scope=품셈과 무관 / chitchat=인사·잡담

### [3] 갈래 (코드)

- 입력: `Understanding`
- 출력: 다음 노드 이름 하나
- 규칙은 이것뿐이다: `ambiguity`가 있으면 C1 → intent가 qa면 Q1 → estimate·change·lookup·answer_card면 E 갈래 → out_of_scope·chitchat이면 X1. 낱말을 보지 않는다.

## 9. R3 연결 설계 (2026-11-10)

지금 대화 엔진(`dialogue.py`)은 `_rule_route`를 6곳에서 부른다(새 견적 시작, 상담 검색 여부, 계산 목표, 규칙 도구 순서, 범위 카드 새 견적, 여러 작업 중 상담 분기). 화면은 `mode`를 보내지 않으므로 운영 질문은 모두 이 규칙을 지난다.

**스위치:** 환경변수 `ROUTER_V2=on`일 때만 v2를 쓴다. 기본은 꺼짐(지금과 똑같이 동작).

**연결 방법 (작게):**
1. `run_turn` 맨 앞에서, 글 메시지가 있고 카드 답이 아니면 v2 라우터를 **한 번** 부른다. 같은 턴 안에서 다시 부르지 않는다(여러 작업 견적의 하위 호출 포함).
2. 6곳의 `_rule_route(message, …)`를 `_route(message, …)`로 바꾼다. `_route`는 이번 턴 메시지에 대한 v2 판단이 있으면 그것을, 없으면 지금 규칙을 돌려준다. 그래서 엔진의 나머지 흐름(세션·도구·계산)은 그대로다.
3. v2 결과별 처리:

| v2 결과 | 처리 |
| --- | --- |
| 견적 / 상담 / 범위 밖 | 규칙 대신 이 값을 쓴다. 나머지 흐름은 지금과 같다 |
| 되묻기 | 계산·검색 없이 질문 카드를 낸다. 선택지가 있으면 버튼(`kind: choice`), 없으면 질문 문장만 |
| 실패 (AI 2번 다 실패·검사 실패) | "잠시 후 다시 시도해 주세요." 안내. 낱말 규칙으로 되돌아가지 않는다(정할 것 ② 추천안) |

4. **되묻기 버튼 답:** 원래 질문에 고른 값을 붙여("도배 30평 한번 봐줄래? → 공사비") 새 메시지로 다시 라우터에 넣는다(AI 1번). 선택지는 자유 문장이라 코드가 창구를 정하지 않는다.
5. 화면: 질문 카드는 이미 `choices`가 있으면 버튼으로 그린다. 새 화면 코드는 필요 없을 것으로 보고, 로컬에서 확인한다.
6. 기록: 턴 `trace`에 `router_v2`(창구·원하는 것·AI 호출 수·오류)를 남긴다.

**이번에 하지 않는 것:** 견적 진행 중 카드에 글로 답하는 경우의 v2 카드 판단(`card_answer`)은 지금 엔진의 대기 질문 처리에 맡긴다. 상담 길(B7)·견적 길(B8) 교체는 다음 단계.

**구현 결과 (2026-11-10, 브랜치 `feat/v2-router-connect`):**
- `run_turn`이 입구가 되고, 원래 몸통은 `_run_turn`이 되었다. 이번 턴의 v2 판단은 `contextvars`에 두며, 같은 턴의 하위 호출은 v2를 다시 부르지 않는다. 되묻기 카드의 필드 이름은 `router_clarify`(scope `clarify`).

**문제:** 지금은 라우터가 표(스키마)로 뽑은 내용 중 '견적/상담' 라벨 한 칸만 넘긴다. 견적 엔진은 원래 문장을 받아 낱말 규칙(`scope.analyze_request`, 공종 4개 목록: 도장·조적·방수·철거)으로 처음부터 다시 쪼갠다. 그래서 "방수 200㎡ 어떻게 생각해?"가 통째로 작업 이름이 된다.

**라우터가 이미 뽑아 둔 것 (요청 하나마다)**

| 칸 | 예: "방수 200㎡ 어떻게 생각해?" | 코드가 이미 확인하는 사실 |
| --- | --- | --- |

| target.search_terms | ["방수"] | — |
| quantity.value / unit / evidence | 200 / ㎡ / "200㎡" | 숫자·단위가 문장에 있다 |
| conditions[].text / evidence | (없음) | 근거 구절이 문장에 있다 |
| estimate_mode | new | 진행 중 견적이 없으면 change·ask_about 불가 |

| 계획 항목 칸 | 채우는 값 |
| --- | --- |

- 견적 요청이 1개면 범위 카드 없이 바로 계산 흐름으로 간다. 2개 이상이면 각각 항목이 된다(여러 공종 흐름은 지금 그대로).

```txt
  └─ 그 밖 → [Q1 검색 · 코드] → [Q2 근거 고르기 · AI] → [Q3 근거 검사 · 코드] → [Q4 답 쓰기 · AI] → [Q5 답 검사 · 코드]
```

- 갈래는 라우터 값(`kind`·`wants`·`quantity`)만 본다. 낱말을 보지 않는다.
- AI 호출: 라우터 1 + Q2 1 + Q4 1 = 3번. 고치기 재시도는 Q2·Q4 각 1번까지(검사 실패 때만).
- 목표 시간: 상담 한 질문 15초 안(7절 ⑤ 추천 10초는 이 결과를 보고 다시 정한다).

### [Q1] 원문 검색 (코드)

- 입력: `QaRequest` (라우터 요청 1개에서 가져온다)
- 출력 → Q2: `SearchResult`
- 하는 일: `search_terms` 각각과 `asks`로 지금의 하이브리드 검색(`knowledge.search` → `Retriever.search`)을 돌려 합친다. 같은 조각은 한 번만. 표 조각은 표 전체를 줄 번호와 함께 붙인다(새로 조회하지 않고 청킹 묶음에 있는 글을 쓴다). 상위 8개 조각, 전체 글자 수 상한을 둔다.

```json
QaRequest {
  "request_id": "r1",
  "asks": "펌프카 타설 품이 얼마인지",          // 라우터 asks
  "wants": "explain | value",
  "target": { "user_text": "펌프카 타설", "evidence": "펌프카 타설", "search_terms": ["콘크리트 펌프차 타설"] } | null,
  "conditions": [{ "text": "붐 32m", "evidence": "32m" }],
  "message": "사용자 문장 원문"                  // Q2·Q4에 보여 주기만 한다. 검색어로 쓰지 않는다
}

SearchResult {
  "queries": ["콘크리트 펌프차 타설", "펌프카 타설 품이 얼마인지"],
  "candidates": [{
    "chunk_id": "...", "division": "공통부문", "section_no": "6-1-4", "section_title": "콘크리트 펌프차 타설",
    "kind": "table | text", "page": 185,
    "lines": ["1| 구분 | 붐 길이 | ...", "2| ..."],   // 줄 번호 붙인 원문
    "score": 0.0
  }]
}
```

### [Q2] 근거 고르기 (AI 1회)

- 입력: `QaRequest` + `SearchResult`
- 출력 → Q3: `EvidencePick` (4절 형태에 `request_id`만 더한다)
- 하는 일: 옛 '대상 비교'와 '고르기'를 한 번에 한다. 대상마다 원문에서 어떤 말로 적혀 있는지(`target_match`) 짚고, 답이 되는 줄을 고른다. 조건이 표의 어느 칸인지 못 정하면 `missing_conditions`에 적는다. 질문의 말끝·단위 표현("m당", "얼마")은 조건이 아니다(프롬프트 규칙).

```json
EvidencePick {
  "request_id": "r1",
  "picks": [{ "chunk_id": "...", "lines": [3, 4], "role": "answer | context" }],
  "target_match": [{ "target": "펌프카 타설", "source_term": "콘크리트 펌프차 타설", "same_thing": "yes | no | unsure" }],
  "condition_match": [{ "condition": "붐 32m", "source_term": "32m", "line": 4 }],
  "missing_conditions": ["붐 길이"],
  "no_answer_reason": "not_in_candidates | needs_calculation | null"
}
```

### [Q3] 근거 검사 (코드)

- 입력: `EvidencePick` + `SearchResult`
- 출력 → Q4: `VerifiedEvidence` (4절 형태 그대로)
- 검사:
  - `chunk_id`가 후보 안에 있는지, 줄 번호가 있는지
  - `source_term`이 고른 줄이나 그 조각의 절 제목에 글자 그대로 있는지(공백 무시)
  - `condition_match.source_term`이 그 줄에 있는지
- 상태 정하기:
  - `same_thing=yes`이고 answer 줄이 하나 이상 통과 → `supported`
  - `unsure`이거나 `missing_conditions`가 있음 → `needs_confirmation` (그래도 Q4로 간다. 값은 조건별로 나열하고 "어느 경우인지 확인" 문장을 붙인다)
  - 통과한 answer 줄이 없음 → `not_found` (Q4 건너뜀)
- 검사에 떨어진 값은 버리고 `reasons`에 기록한다. 낱말이 원문에 없다는 이유만으로 보류하지 않는다(대상 일치는 Q2가 판단하고, Q3은 AI가 짚은 원문 용어가 실제 있는지만 본다).

### [Q4] 답 쓰기 (AI 1회) — `supported`·`needs_confirmation`

- 입력: `QaRequest` + `VerifiedEvidence`의 통과한 줄
- 출력 → Q5: `AnswerDraft` (4절 형태 그대로)
- 지금의 답 쓰기(`ResponseBuilder.generate`, 모델이 위치를 고르고 코드가 인용)를 재사용할 수 있으면 재사용한다.

### [Q5] 답 검사 (코드)

- 입력: `AnswerDraft` + `VerifiedEvidence`
- 출력: `QaAnswer` — 지금 화면의 `KnowledgeResult` 형태(`public_result`)를 그대로 쓴다. 화면 수정 없음.
- 검사: 값의 숫자가 인용한 줄에 있는지, 금액이 없는지(지금 `response.py` 검사 재사용). 실패하면 원문 줄만 보여 주고 이유를 붙인다.

### 계산 질문 (`wants=calculate`)

- `quantity`가 있으면 견적 길로 보낸다. 10절처럼 라우터 요청을 견적 계획 항목으로 옮기고 목표는 품(`goal=labor`)이다. 돈을 묻지 않았으니 가격 단계는 하지 않는다.
- "3명이서 며칠"(c14)처럼 인원으로 나누는 것은 이번에 하지 않는다. 품(인)까지 답하고 "인원으로 나누면 대략 며칠"은 다음 단계에서 정한다.
- `quantity`가 없으면(예: "철근 가공 품이 어떻게 계산돼요?") 상담 길로 간다.

### 한 턴에 상담 요청이 여럿일 때

- Q1은 요청마다 돌리고, Q2·Q4는 요청을 묶어 한 번씩 부른다(AI 3번 한도 유지). 출력에 `request_id`가 있어 코드가 나눈다.
- 상담 + 견적이 섞이면("몇 인이고 얼마예요?") 상담 부분은 먼저 답하고 견적 부분은 견적 길로 간다(지금의 여러 작업 흐름).

### 가져가는 것 / 바꾸는 것

- 가져간다: 하이브리드 검색(`Retriever`), 청킹 묶음, 답 쓰기·숫자 검사(`response.py`), 화면 형태(`KnowledgeResult`)
- 쓰지 않는다(스위치 켬일 때): `VerifiedSelector.run`의 질문 분석(`analyze`·말끝 목록·`question_roles`)·대상 비교·목록·보충 호출, 낱말 부재 보류
- 스위치를 끄면 지금 그대로다. 새 길이 시험에서 이길 때 옛 길을 지운다(6절 순서).

### 시험

| 노드 | 시험 데이터 | 채점 |
| --- | --- | --- |
