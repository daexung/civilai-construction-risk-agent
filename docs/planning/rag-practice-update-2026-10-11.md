# 청킹·검색 실무와 최신 대안 조사

조사일: 2026-10-11. 공식 기술 문서, 개발팀 공개 글, 원저자 논문과 저장소를 읽었다. 제품을 설치하거나 외부 임베딩·추론 API를 호출한 결과는 아니다. 각 제품의 공개 설명과 우리 서비스에 대한 설계 판단을 구분한다. 이 조사와 [실행 계획](RAG-IMPLEMENTATION-PLAN-2026-10-11.md)이 다음 작업의 기준이다.

## 1. 조사 결론

우리의 구조 기반 청킹, 부모 근거 조회, 명시적 참조 연결, 키워드·벡터 결합 방향은 공개 실무 구성과 부합한다. 다만 이것이 품셈에서 최선이라는 실측 증거는 아직 없다. 데이터와 질문을 고정한 비교로 선택한다.

기존 계획에서 더 구체화할 것은 네 가지다. 검색 조각과 답변 근거를 별도로 저장하기, 참조 대상을 사전에 실제 식별자로 연결하기, 검색 뒤 원문을 식별자로 읽기, 근거의 충분함을 확인하고 제한적으로 추가 조회하기다. 관계가 있다는 사실과 이번 작업에 적용된다는 판단도 구분해야 한다.

## 2. 실제 제품 개발팀과 관리형 서비스에서 확인한 구성

| 공개 사례와 자료 성격 | 확인한 구성 | 우리에게 적용할 판단 |
|---|---|---|
| Anthropic의 Claude Code 설명, 실제 제품 설계 공개 | 가벼운 위치 정보와 도구를 이용해 필요한 내용을 그때 읽는다. 미리 제공할 정보와 실행 중 탐색을 조합한다 | 절과 표의 위치를 미리 만들고, 검색 뒤 `read_evidence`로 원문을 읽는다. 숫자와 조건을 질문마다 새로 추출하는 방식은 선택하지 않는다. [개발팀 글](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) |
| Cursor 검색 개발팀 글, 발표 당시 제품 실험 | 의미 검색과 글자 검색을 에이전트의 도구로 사용하고 관련 코드를 읽는다 | 후보 찾기와 원문 읽기를 분리하는 사례로 참고한다. 코드 검색 성과를 한국어 품셈 성과로 환산하지 않는다. 이 글이 모든 최신 Cursor 설정의 현재 상태를 증명하는 것은 아니다. [개발팀 글](https://cursor.com/blog/semsearch) |
| Amazon Bedrock, 관리형 기능 문서 | 작은 자식 조각을 검색한 다음 더 큰 부모 조각으로 대체해 문맥을 제공하는 계층 청킹 | 작은 검색 조각과 큰 근거 묶음을 따로 관리한다. 부모를 항상 절 전체로 고정하지 않는다. [공식 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html) |
| Azure AI Search, 관리형 기능 문서 | 질문 분해, 여러 검색, 재순위, 출처와 실행 기록을 제공한다. 일부 기능은 정식 제공이며 LLM 질문 계획 등에는 미리보기 구분이 있다 | 여러 공종 요청의 항목 분리와 조회 기록을 참고한다. Azure 서비스 이전은 필요 조건이 아니다. [공식 문서](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview) |
| LangChain, 구성 지침과 예제 | 고정 검색 후 생성, 에이전트가 검색하는 방식, 중간 검증을 둔 방식의 장단점을 구분한다 | 첫 조회는 예측 가능한 공통 경로로 실행하고, 부족할 때만 추가 조회한다. 공식 예제를 실제 고객 운영 성과로 표시하지 않는다. [공식 문서](https://docs.langchain.com/oss/python/deepagents/retrieval) |

공개 자료만으로 각 회사의 비공개 데이터베이스 배치, 전체 운영 지연, 실패율까지 알 수는 없다. 위 표는 확인 가능한 설계 패턴의 비교다.

## 3. 청킹과 검색 대안

| 방법 | 이번에 확인한 내용 | 도입 판단과 재검토 조건 |
|---|---|---|
| 구조 기반 청킹과 길이 조정 | Docling HybridChunker는 문서 구조를 바탕으로 길이를 조정하고, 나뉜 표에 머리글을 반복한다. [문서](https://docling-project.github.io/docling/concepts/chunking/) | 기본 원칙에 채택. 현재 ODL 결과를 새 파서로 바꾸지 않고 같은 원칙을 구현한다 |
| 검색용 문맥 추가 | Anthropic은 조각에 짧은 문맥 설명을 붙여 벡터와 BM25에 사용하고 재순위를 결합했다. [개발팀 실험](https://www.anthropic.com/engineering/contextual-retrieval) | 먼저 원문에서 얻은 연도·부문·절·공법·단위를 붙인다. LLM이 만든 설명은 추가 비교 후보다. 공개 개선율을 우리 예상 개선율로 쓰지 않는다 |
| 문맥을 함께 반영하는 임베딩 | 공식 안내는 `voyage-context-4`를 현재 후보로, `voyage-context-3`를 이전 세대로 제시한다. 이미 나눈 조각들을 같은 문서 그룹으로 넣을 수 있다. [문서](https://docs.voyageai.com/docs/contextualized-chunk-embeddings) | 임베딩 비교의 우선 대안 한 개. 같은 절 안의 문맥 손실을 줄일 가능성이 있다. 공동 값·참조 조건의 확정은 별도다. 자동 청킹은 끄고 우리가 정한 경계를 유지한다 |
| 재순위 | Voyage 안내에 `rerank-3`, `rerank-3-lite`가 있다. 질문과 후보를 함께 읽어 순서를 다시 정한다. [문서](https://docs.voyageai.com/docs/reranker) | 정답이 후보에는 있는데 상위 순서가 틀릴 때 우선 비교. 정답 후보 자체가 없으면 먼저 검색을 고친다. 기본 비교는 끈 상태이며 추가 호출과 지연을 기록한다 |
| 목차를 따라가는 PageIndex | 트리 색인을 미리 만들고 LLM이 탐색한다. 저장소에는 2026년 8월 SDK 로컬 모드와 Flash 업데이트가 기록돼 있다. [공식 저장소](https://github.com/VectifyAI/PageIndex), [설계 설명](https://pageindex.ai/blog/pageindex-intro) | 전문 문서의 절 탐색에 유용한 대안. 기존 절 목록을 활용하는 제한된 보조 탐색으로 먼저 비교할 수 있다. 기본 검색을 교체하려면 한국어 표 질문의 정확성과 추가 지연을 직접 측정해야 한다 |
| 페이지 이미지 검색 | ColPali는 페이지 이미지의 시각 정보를 여러 벡터와 후단 비교로 검색한다. [원저자 논문](https://arxiv.org/abs/2407.01449) | 수식·선·배치가 핵심인 질문의 보조 경로 후보. 검색한 그림에서 정확한 값을 읽고 검증하는 일은 여전히 필요하다. 현재 구조 보관을 대체하는 계획으로 잡지 않는다 |
| Gemini의 이미지·문서 임베딩 | 현재 사용 모델 계열인 Gemini Embedding 2는 텍스트 외 입력도 지원한다. [공식 문서](https://ai.google.dev/gemini-api/docs/embeddings) | 이미지 검색이 실제로 필요하면 새 다중 벡터 서버 전에 소수 페이지로 비교할 수 있다. 텍스트·이미지 표현은 구분하고 출처를 함께 보관한다 |
| GraphRAG·LightRAG | GraphRAG는 추출된 지식 관계와 요약 기반 검색을, LightRAG는 관계와 본문 검색을 섞는 경로를 제공한다. [GraphRAG](https://microsoft.github.io/graphrag/query/overview/), [LightRAG](https://github.com/HKUDS/LightRAG) | 현재 필요한 것은 원문에 쓰인 절 참조의 정확한 연결이다. 광범위한 개체 추출·요약 색인은 여러 문서의 주제 관계 탐색 수요가 확인될 때 비교한다 |
| 의미 경계 분할·Late Chunking·전체 문서 장문 입력 | 경계 선택, 벡터에 주변 문맥 반영, 전체 문맥 제공은 서로 다른 방법이다. [기존 조사](chunking-and-retrieval-options.md), [장문 문맥 관리](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 표 행·단위·적용 조건 보존을 대신하지 못한다. 긴 설명문의 검색 실패가 남으면 해당 설명문에 한정한다. 문맥 임베딩은 위 Voyage 후보로 비교 범위를 좁힌다 |

새 모델의 실제 계정 접근 가능 여부와 호출 형식은 실행 시 소량 호출로 확인해야 한다. 안내 문서와 API 참조가 서로 다른 이전 모델을 표시할 수 있으므로 모델명·버전·입력 제약을 실행 기록에 고정한다. 여기서는 출시일을 확인하지 못한 모델에 임의의 출시일을 붙이지 않았다.

## 4. 저장 방식 비교

| 선택 | 장점 | 부담 또는 제약 | 결정 |
|---|---|---|---|
| SQLite 원문·관계 + Parquet 벡터 | 기존 파일 배포·정확 벡터 검색을 활용. 서버 설치 없이 한 버전 묶음을 재현 | 이미 사용하는 Supabase PostgreSQL 외에 저장소·동기화·운영 경로를 추가하게 됨 | 사용자 지적 후 기본안에서 제외 |
| 기존 Supabase PostgreSQL 원문·관계 저장 | 기존 인프라와 SQL·버전·권한 관리 활용 | 지식 자료의 스키마·조회·적재를 설계하고 기존 회원·대화 자료와 충돌 방지 필요 | 수정된 1차 구현 권고 |
| PostgreSQL + pgvector 벡터 검색 | 관계·벡터·버전을 한 데이터베이스에서 관리하고 여러 작업자가 갱신하기 좋음 | 실제 확장 버전·차원·검색 전환 검증 필요. 지금의 한국어 BM25가 자동으로 대체되지는 않음 | 임베딩 단계에서 기존 Parquet 검색과 비교해 결정 |
| Qdrant + 관계 저장소 | 벡터·희소 검색, 결합 검색 구성이 제공됨 | 별도 서비스와 원문·관계 저장소 사이의 버전 관리 필요 | 전용 벡터 기능과 규모가 실제로 필요할 때 비교 |
| Neo4j 등 그래프 전용 저장소 | 복잡한 관계 질의에 적합한 후보 | 현재 명시적 절 연결 조회에는 추가 운영 요소가 됨 | 관계 질의가 복잡해져 SQL로 관리하기 어려워질 때 검토 |

SQLite는 응용 프로그램의 로컬 저장과 배포용 데이터 묶음에 적합하고, 동시 쓰기나 네트워크 공유에는 제약이 있다. 이 일반적인 장점만으로 기존 Supabase PostgreSQL을 사용하는 프로젝트에 별도 저장소를 추가할 이유가 충분하지는 않다. [공식 설명](https://www.sqlite.org/whentouse.html)

pgvector는 정확 검색과 근사 검색을 지원한다. 확인한 문서에서 HNSW의 `vector`는 최대 2,000차원, `halfvec`는 4,000차원을 지원한다. 현재 3,072차원을 그대로 `vector` HNSW로 옮기는 설계는 사용할 수 없다. 전환 시 반정밀도 색인 후 원래 벡터 재평가 또는 검증한 차원 축소를 비교한다. 저장 가능한 차원과 색인 가능한 차원을 구분한다. [공식 저장소](https://github.com/pgvector/pgvector)

Qdrant의 결합 검색·여러 단계 조회 기능은 확인했다. 기능 존재가 현재 서비스보다 좋은 품질이나 지연을 보장하지는 않는다. [공식 문서](https://qdrant.tech/documentation/search/hybrid-queries/)

## 5. 이번 조사로 내린 선택

필수 구성은 구조 기반 청킹, 원문 문맥, 부모 근거 조회, 명시적 참조 그래프, 기존 결합 검색이다. 후보 안에서 순서를 고치는 재순위는 조건부 추가한다. 임베딩은 기존 Gemini를 기준으로 두고 문맥 임베딩 한 개만 비교한다. 목차 탐색과 이미지 검색은 특정 실패 유형이 남을 때 켠다.

원문 관계를 미리 저장하는 것과 LLM이 필요할 때 원문을 조회하는 것은 함께 쓸 수 있다. 사전 색인은 안정적인 문서 구조를 담당하고, 실행 중 조회는 질문별로 필요한 근거를 고르는 역할을 맡는다.
