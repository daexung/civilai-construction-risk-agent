## 목적과 현재 상태

운영자가 별도 분석 도구나 SQL 화면을 오가지 않고 서비스 이용 현황과 사용자 평가, 실패한 에이전트 실행을 확인하는 자체 대시보드를 만든다.

구조는 기존 Vercel React 화면 `/admin` → 기존 GCP Cloud Run 백엔드 `/api/admin/*` → 기존 Supabase PostgreSQL이다. 새 서버나 SQLite, Grafana, 새 분석 플랫폼을 만들지 않는다. GCP 서버 간 인증과 실제 운영자 사용자 권한은 별도로 검증한다.

PR #36은 머지·운영 배포 완료 상태다. `answer_runs`, `answer_run_steps`와 평가 연결 컬럼의 두 마이그레이션은 로컬·운영 모두 적용됐다. 운영에서 시험 질문의 실행·단계 저장과 대화 삭제 연동을 확인했다. 기존 로그 스키마를 새로 설계하거나 마이그레이션을 재적용하지 않는다.

## 이번에 만들 범위

읽기 전용 첫 버전을 로컬에서 끝낸다. 권한 확인, 집계 API, 목록·상세 API, 실제 화면, 검사, 결과 보고까지 구현한다. 계획만 작성하고 멈추지 않는다.

### 1. 운영자 접근 제어

- 기존 Supabase 인증 검증을 재사용한다. 브라우저가 보낸 UUID·이메일·역할을 신뢰하지 않는다.
- 서버 환경 변수 `ADMIN_USER_IDS`에 등록한 인증 사용자 UUID만 허용한다. UUID 형식을 검증하고 설정이 없거나 잘못되면 접근을 차단한다.
- 비로그인·잘못된 인증은 401, 로그인한 일반 회원은 403으로 처리한다. 모든 관리자 API에 같은 권한 의존성을 적용한다.
- 사용자에게 허용할 실제 운영자 계정은 아직 정해지지 않았다. 현재 로그인 계정이나 DB 첫 계정을 자동 지정하지 않는다. 실제 계정 권한 부여는 이번 범위가 아니다.
- 로컬 검사는 시험 계정으로 한다. 실서비스에서 켤 수 있는 인증 우회 플래그나 누구나 접근하는 데모 API를 만들지 않는다.
- 비밀키·DB 연결은 서버에서만 사용한다. 로그 테이블의 일반 회원 접근 제한과 RLS를 풀지 않는다.
- 관리자 API는 `Cache-Control: private, no-store`를 적용한다. `/admin`과 관리자 API는 검색 제외로 설정하고 사이트맵에 넣지 않는다. 캐시나 초기 HTML에 관리자 자료를 넣지 않는다.

### 2. 요약 화면

오늘·최근 7일·최근 30일을 선택하고 다음을 보여 준다.

- 현재 가입자 수와 기간 내 신규 가입자 수. 비회원은 가입자로 세지 않는다. 삭제된 계정은 현재 가입자 수에서 제외한다. 실제 인증 스키마를 확인해 익명 사용자를 제외하는 기준을 문서에 쓴다.
- 실행 완료·실패·진행 중·미완료 건수. 실행 성공을 답변 정답률로 표현하지 않는다.
- 완료 실행의 처리 시간 중앙값·상위 95% 값과 표본 수. 시간 자료가 없는 기록은 0초로 넣지 않는다.
- 긍정·부정 평가 수, 검토 대기 수, 일반 의견 수. 평가 비율에는 실제 평가 수와 분모를 함께 표시한다.
- 날짜별 실행 추이와 최근 실패 목록. 그래프 라이브러리 추가는 필요한 경우에만 한다.

숫자의 뜻을 한 줄 도움말로 설명한다. 비회원 전체 대화는 `messages`에 없으므로 그 개수로 전체 이용량을 계산하지 않는다. 실행 로그는 수집을 시작한 시점 이후의 실행 기록이며, 인증·한도 차단 등 실행 전 요청까지 전부 포함하지 않는다. 이를 전체 질문 수로 부풀리지 않는다.

### 3. 평가와 일반 의견 목록·상세

- 기존 `answer_feedback`과 일반 `feedback`을 구별해 표시한다.
- 평가는 날짜·긍정/부정·이유·검토 상태로 필터링하고, 안정적인 정렬과 서버 쪽 페이지 나누기를 적용한다.
- 요약 목록에는 질문·답변 본문과 회원 이메일을 넣지 않는다. 선택한 평가 상세에서만 저장된 질문·답변·의견·검토 내용·연결된 실행을 조회한다.
- 과거 평가의 실행 연결이 비어 있으면 당시 실행 기록 없음으로 표시한다. 추측해서 다른 실행을 붙이지 않는다.
- 검토 내용 수정과 평가 사례 승인은 다음 단계다. 이번에는 조회만 한다.

### 4. 실행 목록·상세

- 날짜·실행 상태·처리 경로 필터와 페이지 나누기를 제공한다.
- 실행 하나를 열면 단계 순서, 부모 관계, 노드/도구/모델 구분, 시작·종료·소요 시간, 상태·실패 유형, 기록된 근거·계산 요약을 볼 수 있게 한다.
- 모델은 설정 모델과 실제 호출 모델을 구별한다. 토큰 수가 없으면 미수집으로 표시하고 비용을 지어내지 않는다.
- `capture_status=partial`, 중간 종료, 과거 단계 없음 등을 구별한다. 완료 로그를 정답 판정으로 표시하지 않는다.
- 비회원 실행에는 보관된 질문·답변이 없을 수 있다. 이를 복원하거나 모델 호출로 다시 만들지 않는다.
- 긴 요약은 접어서 표시하고, 기본 목록은 가볍게 유지한다. 원문 HTML이나 메모를 HTML로 실행하지 않는다.

### 5. 갱신과 조회 규칙

- 화면 진입 시 조회하고, 화면이 보이는 동안 60초마다 갱신하며 수동 새로고침도 제공한다. 숨겨진 탭에서는 주기 조회를 멈춘다.
- 기간 변경·로그아웃·계정 변경 시 이전 요청과 화면 자료를 정리해 오래된 응답이 섞이지 않게 한다.
- 시간대는 한국 시간이다. 날짜 구간은 서버가 계산하고 경계 포함·제외 기준, 기준 시각, 집계 제외 조건을 문서화한다.
- 운영 환경만 기본 집계하고 로컬 시험 실행을 운영 통계에 섞지 않는다. 시험에서는 로컬 DB의 명시적 시험 자료로 운영 필터를 확인한다.
- 기간·상태·페이지 크기를 서버에서 검증하고 제한한다. 사용자 입력을 SQL에 직접 붙이지 않는다. 무제한 전체 상세 조회를 만들지 않는다.
- 정상 0건, 아직 수집하지 않은 지표, 설정 미연결, DB 오류를 서로 다른 상태로 보여 준다. 오류를 0건으로 바꾸지 않는다.
- 표 조인으로 실행·평가 건수가 중복되지 않는지 확인한다. 새 색인은 실제 필요한 조회 근거가 있을 때만 제안한다.

## 다음 단계로 남길 것

- PostHog 방문·페이지 조회·엑셀 내려받기 통계의 서버 조회 연결.

- 실제 운영자 UUID 설정과 운영 배포.

기존 PostHog 수집은 유지한다. 공개 이벤트 수집 키로 통계 조회가 가능하다고 가정하지 않는다. 첫 화면에서 방문 통계가 미연결임을 명확히 표시하고, 이번에 페이지 이벤트 테이블이나 새 수집기를 만들지 않는다. 검색 유입·순위·실제 사람 수를 현재 없는 자료로 추정해 채우지 않는다.

## 실행 환경과 작업 제한

- 현재 로컬 Supabase를 재사용한다. 새 폴더 이름으로 다른 Supabase 프로젝트를 띄우거나 DB를 초기화하지 않는다.
- 기존 Python 런타임을 재사용할 수 있지만 가져오는 코드와 실행 경로는 반드시 이 작업 폴더로 확인한다. 로컬 DB 대상을 명시하고 운영 `.env` 연결을 그대로 사용하지 않는다.
- 대표 자료는 로컬 시험 계정·대화·실행·단계·평가로 만든다. 시험 자료는 끝나면 정리한다. 화면용 가짜 통계를 정상 API 응답으로 상시 반환하지 않는다.
- 운영 DB 읽기·쓰기, 외부 모델 호출, PostHog 원격 조회, 원격 설정, 유료 서비스 추가는 이번 작업에서 하지 않는다.
- 원본 PDF·벡터·임베딩·상담 검색 정책을 바꾸지 않는다. 새 VM·새 DB·새 인증 체계를 만들지 않는다.
- 기존 홈페이지 사전 렌더링, `/chat`, 로그인 콜백, 기존 사용자 평가 기능은 유지한다. `App.tsx`에는 필요한 경로 연결만 작게 추가하고 대시보드 코드는 별도 모듈로 나눈다.
- 사용자 화면과 보고는 쉬운 한국어로 작성한다. 확인하지 않은 것을 완료로 쓰지 않는다.

## 완료 확인

1. 관리자 API 전부에 대해 비로그인 401·다른 회원 403·허용된 시험 계정만 성공을 확인한다. UUID나 이메일을 요청 값으로 위조해도 통과하지 않아야 한다.
2. 로컬 DB의 독립적인 기대 집계와 화면 수치를 대조한다. 한국 시간 날짜 경계, 비회원, 실패·미완료, 단계 다수 조인, 평가 없는 실행, 과거 연결 없는 평가, 자료 없음·DB 실패를 포함한다.
3. 브라우저에서 권한 없음, 요약·기간 변경, 평가 상세→실행 상세, 실패 상세, 수동 갱신을 확인한다. 로그아웃하면 상세 자료가 사라져야 한다.
4. 관리자 응답의 캐시 금지와 검색 제외, 일반 회원의 로그 테이블 접근 차단을 확인한다.
5. 변경에 맞는 백엔드 검사·프런트 검사·운영 빌드를 실행하고 기존 상담·인증·홈페이지에 영향이 없는지 확인한다. 낮은 영향의 표시마다 불필요한 검사를 늘리지는 않는다.
6. 외부 API 호출 0회, 운영 자료 변경 0건을 확인한다. 소켓 자체를 전부 차단할 필요는 없고, 필요한 로컬 DB·서버 접속은 허용한다.

구현 중 작은 결함은 이번 범위에서 고친다. 검사 숫자를 늘리는 것을 목표로 삼거나 결과를 본 뒤 기대값을 조용히 바꾸지 않는다. 실제 스키마와 지시서가 다르면 증거와 영향을 기록하고 기존 구조를 우선 재사용한다.
