## 1. 로컬에서 명시적으로 켜는 연결

기존 API와 화면에 기본 꺼짐인 로컬 시험 옵션을 추가한다. 기존 서비스 동작은 옵션을 켜지 않으면 유지한다. 새 검색 경로의 연결 계층과 응답 상태 전달에 필요한 최소 수정만 한다. 기존 상담 생성 코드는 가능한 부분을 재사용하되 잘못된 상태 처리까지 그대로 가져오지 않는다.

서버·화면은 로컬 주소로만 실행한다. 원격 Supabase·대화 저장·회원·사용량 차감·피드백 저장·분석 이벤트가 로컬 시험 요청에서 호출되지 않도록 확인한다. 기존 인증을 운영에서 끄지 않는다. 현재 채팅 경로가 이 의존성 때문에 원격을 요구하면 기본 꺼짐인 로컬 전용 경로를 만들고 기존 화면 구성에 연결한다. 계정 결제나 회원 정책을 수정하지 않는다.

로컬 모드에서는 실제 화면에서 질문을 입력하고 결과를 볼 수 있어야 한다. 명령줄·정적 결과 파일만 만든 뒤 서비스 연결 완료라고 하지 않는다. 다른 서비스를 새로 설계하거나 화면 전체를 다시 만들지 않는다. 환경 변수와 값은 로컬 실행에만 적용하고 비밀 값을 출력하거나 기록하지 않는다.

기존 서버 초기화가 원격 저장을 연결한다면 그 초기화를 로컬 시험에서 사용하지 않도록 분리한다. 로컬 검증 DB의 원문 자료는 읽기 전용이며 테스트 대화는 메모리나 별도 로컬 기록에 보관한다. 현재 실행 중인 다른 서버를 임의로 종료하지 않는다. 포트 충돌 시 빈 로컬 포트를 사용하고 실제 주소를 보고한다.

## 2. 전달 계약: 정상 답변·검토용·진단을 분리

검색 결과에서 상태·사유·정상 답변 근거·검토용 원문·진단 후보·절/부문 대안·단위/참조 상태·버전 정보를 받아 연결한다. 연결 단계에서 검색을 옛 청크 파일로 다시 실행하거나 같은 절의 모든 표를 합치지 않는다.

현재 `qa_context.py`는 과거 `chunks.all.jsonl`을 읽고, `answer.py`는 기본적으로 그 경로를 사용한다. 새 검색을 실행한 뒤 답변만 옛 자료로 만드는 혼용을 막는다. 답변 문맥을 명시적으로 새 경로에서 제공하는 어댑터를 사용한다. 같은 번호라도 부문을 구분한다. 기존 출처 조회 경로가 옛 청크 ID만 처리하면 새 원문 ID·쪽·표/줄 위치를 올바르게 전달하는 로컬 어댑터를 둔다.

정상 답변 근거만 답변 생성 문맥에 전달한다. 검토용 원문과 진단 후보를 정답 자료처럼 모델에 합쳐 주지 않는다. 중요한 단위·기준·선택 행·주석·조건이 빠지거나 예산 때문에 잘리면 충분한 근거로 표시하지 않는다. 원문과 별도로 붙인 검색 제목을 원문 인용으로 쓰지 않는다.

## 3. 세 상태의 실제 사용자 처리

### 근거 있음(`supported`)

기존 서비스 모델과 호출 경로로 짧은 설명과 출처를 생성한다. 질문의 조건·규격·단위와 선택한 행을 그대로 반영한다. 원문에 없는 값·조건·계산을 만들지 않는다. 이번에는 per-unit 품과 적용 기준 설명을 확인하며 공사비·합산·Excel 계산을 확장하지 않는다. `applicability=unknown`을 계산 적용 승인으로 바꾸지 않는다.

답변의 인용 자료·원문 위치·수치와 단위·부문·절을 검증한다. 숫자가 문맥에 존재하는 것만으로 행 대응이 맞다는 증명이 아니므로 중요한 테스트 사례는 원문 표와 직접 대조한다. 기존 유사 문자열 인용 검증을 의미 정확성으로 보고하지 않는다. 출처 글은 원문에서 가져온다.

생성 실패·시간 초과·검증 실패는 상태와 이유를 남기고 검증된 원문 표시로 전환할 수 있다. 이 전환을 모델 답변 성공으로 집계하지 않는다. 기존 템플릿의 단정적 ‘확인했어요’ 문구가 미완료 상태에 붙지 않게 한다.

### 확인 필요(`needs_confirmation`)

소속·수식·범위·표현 불일치 등 실제 사유와 사용자에게 필요한 확인 항목을 쉬운 말로 보여준다. 검토용 원문과 출처는 별도 표시한다. 값을 확정 답변으로 쓰거나 계산하지 않는다. 번호 모호 질문은 부문·절 제목 대안을 표시한다.

G02의 불필요 보류와 N19의 자료 없음 미달은 현재 정책의 한계로 그대로 남긴다. 연결 작업 중 검색 규칙을 고쳐 이 상태를 해제하지 않는다. 검토용 원문을 사람이 열어 확인할 수 있게 하고, 로그에는 어떤 사유로 보류됐는지 남긴다.

### 근거 못 찾음(`not_found`)

현재 읽은 범위에서 맞는 근거를 찾지 못했다고 표시한다. 비슷한 표의 값을 대신 답하지 않는다. 진단 후보는 정상 답변·인용과 섞지 않는다. 문서 전체에 해당 작업이 없다고 단정하지 않는다.

상태 표기는 사용자에게 ‘근거 있음 / 확인 필요 / 근거를 찾지 못함’으로 보여준다. 내부 ID·DB·캐시·모델 상세는 사용자 흐름에 넣지 않고 실행 기록에 둔다. 서비스 모델이 원문 속 문구를 실행 지시로 받아들이지 않도록 자료 경계를 유지한다.

## 4. 실제 질문 시험과 기존 화면 비교

결과를 보기 전에 아래 10개 질문의 기존 기대 원문과 현재 정책의 상태를 고정한다. 4g·기존 개발 질문을 사용하며 이번은 서비스 통합 시험이지 독립 평가가 아니다.

- G01·G03: 특정 규격·단위·공동값의 품과 정확한 표 행.
- G08: 다른 절 참조 조건과 실제 출처.
- G02: 정상 근거가 있어도 현재 정책은 보류함을 화면에 정직하게 표시.
- G09: 소속 미확정 표·설명 검토용 전달.
- G10: 조건 설명과 기준 표 전달.
- G14: 모호 목록의 범위·부분성 표시.
- G19: 절 번호의 부문 대안 표시.
- G16: 같은 대상의 다른 작업에 근거 없음 처리.
- N19: 자료 없음 미달의 현재 정책, 확정 답변 없이 검토용과 경고 표시.

현재 새 API 경로를 통해 10문을 실행하고 각 응답의 버전·선택 ID·문맥 분류·생성 또는 템플릿 여부·검증·지연을 기록한다. 같은 입력 해시의 검색 선택 응답 캐시는 쓸 수 있으나 저장 JSON을 고정 응답으로 반환하는 모의 서비스로 바꾸지 않는다. 사용자 자유 질문도 현재 경로를 사용해야 한다.

G01·G03·G08처럼 현재 `supported`인 최소 3문은 실제 답변 생성 호출로 원문과 답변을 대조한다. 확인 필요·자료 없음은 원문 표시와 정해진 상태 설명으로 구현해 불필요한 모델 호출을 줄인다.

브라우저에서 최소 근거 있음·확인 필요·근거 없음·번호 대안의 네 흐름을 확인한다. 실제 화면 증거와 API 결과를 함께 남긴다. 출처를 열면 표시한 부문·절·쪽·표/설명이 맞는지 확인한다. 화면 도구가 없으면 API 확인까지만 완료로 보고하고 화면 확인은 미실행으로 남긴다.

기존 상담 경로가 로컬에서 원격 저장 없이 실행 가능하면 같은 주요 질문 3개(G01·G03·G08)의 기존 답변·출처와 비교한다. 가능하지 않으면 이유를 보고하고 비교 미실행으로 남긴다. 개선을 입증하기 위해 과거 결과를 임의로 만들거나 원격을 연결하지 않는다. 원문 정확성은 기존 답변과 비교가 안 되더라도 직접 확인한다.

## 5. 검사와 비용·실행 한도

관련 API·프론트 검사, 프론트 빌드, 상태 전달·버전 혼용·검토용 유출·모델 실패 처리의 필요한 검사를 수행한다. 검색 80문이나 파싱 전체를 다시 실행하지 않는다. 정상·확인 필요·근거 없음 응답이 화면에서 바뀌지 않는지 확인한다. 현재 운영 옵션 꺼짐일 때 기존 요청 형식과 핵심 동작이 유지되는지 검사한다.

새 유료 호출 상한은 **60회·예상 비용 2달러**다. 선택·목록·대조·답변 생성·질문 벡터·재시도를 모두 센다. 호출 전 실제 경로의 가격과 입력량을 확인하고 미확인이면 추정 한계를 기록한다. 같은 성공 응답은 재사용하고 실제 모델 생성 확인과 캐시 재생을 구분한다. 문서 벡터는 재생성하지 않는다.

서버나 브라우저 장애를 해결하면서 무관한 대규모 수정과 반복 평가를 하지 않는다. 직접 만든 프로세스만 세션 또는 PID로 정리한다. 서버를 사용자 시험용으로 남기는 경우 주소·포트·켜진 옵션·종료 방법을 적는다. 별도 도구로 자동 실행을 예약하지 않는다.
