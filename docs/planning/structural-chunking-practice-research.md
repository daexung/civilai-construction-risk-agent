# 구조 기반 청킹의 실무 사례와 품셈 적용안

조사일: 2026-10-10  
대상: 품셈 기반 목록·설명·품·견적 에이전트  
상태: 공식 자료 조사와 설계 재평가. 서비스 코드·데이터·설정 변경과 API 실험은 하지 않았다.

## 1. 결론과 이전 계획에서 달라진 점

품셈에는 **문서 계층을 보존한 검색 + 원문 표 보관 + 부모 문맥 확장 + 명시적 참조 조회**를 결합하는 안이 가장 적합한 우선 후보라고 판단한다.

이전 계획의 큰 방향은 유지하되 다음을 구체화한다.

1. 공종을 찾는 목록과 답변·계산에 사용하는 근거를 구분한다. 공종 목록, 규칙 문장, 표를 같은 문자열 묶음으로만 검색하지 않는다.
2. 짧은 절은 원문 절 전체를 부모 문맥으로 먼저 시험한다. 큰 절·큰 표에서만 소절이나 작업 조건별 행 묶음으로 범위를 줄인다. 처음부터 모든 표를 작은 조각으로 나누지 않는다.
3. 근거 조회 도구가 에이전트에 어떤 결과를 줄지 지금 설계한다. 에이전트의 전체 대화 행동 변경은 후속 단계지만 도구의 응답 형식은 데이터 설계와 함께 정해야 한다.
4. 검색용 설명과 계산 근거를 구분한다. 표의 요약이나 제목으로 찾았더라도 실제 값은 원문 셀과 검증된 계산 명세에서 가져온다.
5. 필수 주석은 서버가 함께 제공한다. 에이전트의 추가 검색은 부족한 근거를 보완하는 역할로 제한하고, 이미 아는 필수 근거까지 매번 모델의 선택에 맡기지 않는다.

이 결론은 아래 자료를 품셈의 요구에 맞게 해석한 설계 판단이다. 특정 제품을 설치하면 이 구조가 자동 완성된다는 뜻은 아니다.

## 2. 조사 자료의 성격

실제 운영 공개, 공식 구현 예제, 제품 기능 문서, 연구 결과를 구분했다. 공식 예제가 있다고 동일 구조의 운영 성과가 입증된 것은 아니다. 공개 성능 수치를 우리 서비스의 예상 개선율로 사용하지 않는다.

| 사례 | 자료 성격 | 확인한 핵심 |
|---|---|---|
| Amazon Finance 규제 질의 대응 | 내부 업무 시스템 활용을 설명한 공식 사례 | 작은 자식 검색 후 부모 반환, 대화·검색 이력 추적 |
| AWS AIDA 계약 검색 | 공식 솔루션 설명과 공개 계약 데이터 실험 | 메타데이터 필터와 문서 단위 문맥 보충 |
| Azure 건강보험 문서 검색 | 공식 구현 가이드 | 제목 계층과 부모 식별자를 보존한 구조 기반 분할 |
| Cohere 혼합 문서 에이전트 | 공식 코드 예제 | 표·본문 분리, 요약 검색 후 원문 반환, 도구 사용 |
| LlamaIndex 표 조회 | 공식 코드 예제 | 표의 설명을 검색한 뒤 연결된 표 조회기를 실행 |
| Google Document AI | 제품 기능·사용 예제 | 상위 제목을 청크에 포함하고 문서 요소를 보관 |
| Anthropic의 에이전트 문맥 설계 | 실제 제품을 포함한 공식 엔지니어링 설명 | 필요한 정보를 도구로 단계적으로 읽는 방식 |
| 독일 법령 청킹 연구 | 특정 법령·질문 집합의 연구 | 원래 조문 구조와 맞춘 분할의 유효성 |
| 금융 보고서 청킹 연구 | 금융 문서의 연구 | 표·문단 등 요소 종류를 구분하는 분할 |

## 3. 사례별 작동 방식과 판단

### 사례 1. Amazon Finance: 자식으로 찾고 부모로 읽는다

규제 질의에 대응하는 내부 업무 시스템에서 여러 형식의 문서를 계층형으로 색인한다. 작은 조각을 검색한 뒤 큰 부모 문맥을 반환한다. 대화와 검색 과정을 추적하는 관측 체계도 설명한다. [공식 사례, 2026-05-12](https://aws.amazon.com/blogs/machine-learning/how-amazon-finance-streamlines-regulatory-inquiries-by-using-generative-ai-on-aws/)

**품셈에 적용할 점:** '장비사용 타설'이라는 작은 검색 단서로 해당 절의 표와 설명을 읽게 한다. 어느 근거를 가져왔는지 기록한다.

**장점:** 검색 표현을 짧게 유지하면서 주변 조건을 제공할 수 있다.

**한계:** 부모 반환 자체가 다른 절 참조나 조건 적용을 해결하지 않는다. 큰 부모를 많이 반환하면 문맥이 늘어난다. 이 사례로 계산 정확성이나 청킹만의 독립적인 개선 효과를 판단할 수는 없다.

Bedrock 기능 문서도 자식을 검색한 뒤 부모로 대체하는 동작을 명시한다. 여러 자식이 같은 부모로 합쳐져 요청한 수보다 적은 결과가 반환될 수 있다. 검색 결과 수와 서로 다른 근거 수를 구분해야 한다. [Bedrock 청킹 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)

### 사례 2. AIDA 계약 검색: 조건으로 범위를 좁히고 문맥을 보충한다

계약 당사자·날짜·관할 같은 메타데이터로 검색 범위를 좁힌다. 검색 결과를 문서별로 묶어 공통 메타데이터를 한 번 붙인다. 공개 비교는 CUAD 계약 데이터의 예제이며, 필터만 적용한 경우보다 메타데이터까지 제공한 구성이 해당 질문에서 더 나은 답을 보였다. [공식 설명, 2026-08-18](https://aws.amazon.com/blogs/machine-learning/improve-contract-search-accuracy-with-auto-generated-filters-in-amazon-bedrock/)

**품셈에 적용할 점:** 연도·부문·절을 보존하고, 확인된 조건으로 후보를 제한한다. 같은 절의 여러 표를 전달할 때 공통 제목과 기준을 불필요하게 반복하지 않는다.

**장점:** 같은 표현이 다른 범위에서 쓰이는 문제를 줄일 수 있다.

**한계:** 추정한 부문이나 공법으로 강하게 제한하면 정답을 제외할 수 있다. 사용자나 견적 상태에서 확정된 조건은 필터로, 추정 조건은 순위 조정이나 추가 후보로 다루는 안이 적절하다. 연도 구분만 잘한다고 적용 조건까지 검증되지는 않는다.

### 사례 3. Azure 건강보험 문서: 제목 계층을 청크와 함께 저장한다

건강보험 문서 예제에서는 레이아웃 분석으로 제목과 본문을 얻고, 문서 구간 안에서 길이를 조정한다. 색인에 청크·부모 식별자·상위 제목 필드를 함께 둔다. [공식 구현 가이드](https://learn.microsoft.com/en-us/azure/search/search-how-to-semantic-chunking)

**품셈에 적용할 점:** '철근공' 한 단어 대신 '연도 → 부문 → 장 → 절 → 소제목 → 표' 경로를 보존한다. 표만 복사해도 원래 소속이 사라지지 않게 한다.

**장점:** 반복되는 용어의 배경을 유지하고 원문 이동과 인용에 도움이 된다.

**한계:** 부모 식별자를 저장하는 것과 검색 후 부모 내용을 자동으로 읽는 것은 별도 기능이다. 제목 계층으로 주석의 정확한 적용 범위를 모두 알 수는 없다. 이 예제는 실제 보험 업무 운영 성과를 공개한 사례가 아니다.

### 사례 4. Cohere: 표 요약으로 찾고 원문 표를 에이전트에 제공한다

혼합 문서 예제는 표와 본문을 분리하고 제목을 활용해 묶는다. 조각의 요약을 검색한 뒤 연결된 전체 내용을 반환한다. 이 검색 기능을 에이전트의 도구로 제공하며 별도 Python 도구로 수치 후처리를 하는 예도 포함한다. [공식 예제](https://docs.cohere.com/v2/page/agentic-rag-mixed-data)

**품셈에 적용할 점:** '이 표가 어떤 공법과 조건을 다루는지'라는 검색용 표현과 실제 원문 표를 연결한다. 먼저 제목·머리글·적용 범위로 설명을 구성하고, LLM 요약의 추가 효과는 나중에 비교한다.

**장점:** 큰 표의 숫자를 전부 검색 표현에 넣지 않고도 표의 주제를 찾을 수 있다.

**한계:** 요약이 중요한 조건을 생략할 수 있다. 원문 검색 경로도 유지해야 한다. 품셈의 최종 계산에는 이 예제의 자유로운 Python 생성을 그대로 도입하지 않고, 검증된 명세를 실행하는 서버 계산기를 사용한다. 예제의 파서 선택을 우리 파서 비교 결론에 덮어쓰지 않는다.

### 사례 5. LlamaIndex: 검색 결과가 실제 표 조회기로 이어진다

공식 예제는 세계 부자 순위와 연도별 통계를 담은 본문·표를 대상으로 한다. 표를 설명하는 노드를 검색하면 식별자로 연결된 Pandas 조회기를 실행한다. 예제의 표 설명은 직접 작성되어 있고 운영에 그대로 사용할 때의 제약도 명시되어 있다. [공식 예제](https://developers.llamaindex.ai/python/examples/query_engine/pdf_tables/recursive_retriever/)

**품셈에 적용할 점:** 검색 결과를 긴 문자열로 끝내지 말고, 표·행 묶음·규칙의 식별자로 연결한다. 해당 식별자로 원문과 계산 근거를 읽는 도구를 제공한다.

**장점:** 관련 표를 찾는 단계와 실제 값을 조회하는 단계를 구분할 수 있다.

**한계:** 표를 찾았다고 계산 규칙이 정해지는 것은 아니다. 예제처럼 표마다 사람이 설명이나 조회기를 새로 만드는 운영은 피한다. 공통 스키마와 일반 조회 도구를 사용하고 표의 설명은 자동으로 구성해야 한다. 이 사례는 재무 규제 서비스의 운영 실적이 아니라 구조화된 표를 다루는 구현 예제다.

### 사례 6. Google Document AI: 상위 제목을 포함하는 분할

Layout Parser 사용 예제는 문서 요소와 청크를 반환하며, 상위 제목을 포함하는 `includeAncestorHeadings` 설정을 제공한다. [공식 문서](https://docs.cloud.google.com/document-ai/docs/layout-parse-quickstart)

**품셈에 적용할 점:** 표와 주석에 상위 공종 경로를 붙이는 방식은 특정 파서에 종속되지 않는 설계로 가져올 수 있다.

**장점:** 짧은 조각에 소속 문맥을 보충하기 쉽다.

**한계:** 상위 제목은 적용 조건의 증명이 아니다. 이번에 확인한 것은 제품 기능이며 실제 고객의 견적 에이전트 성능이 아니다. 이를 사용하기 위해 기존 ODL 후보를 바꿀 이유는 없다.

### 사례 7. Anthropic: 필요한 정보를 도구로 단계적으로 읽는다

공식 엔지니어링 설명은 파일 경로나 식별자를 유지하고 필요할 때 내용을 읽는 접근을 소개한다. Claude Code를 사례로 들며 사전 제공 문맥과 실행 중 탐색을 결합한다. 실행 중 탐색은 사전 검색보다 느릴 수 있다는 점도 명시한다. [공식 설명, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**품셈에 적용할 점:** 초기 검색에서 관련 절을 찾고, 미해결 참조가 있을 때 해당 절을 추가로 읽는 도구를 제공한다.

**장점:** 처음부터 장 전체를 넣지 않아도 필요한 근거를 확장할 수 있다.

**한계:** 탐색을 전부 모델에게 맡기면 지연과 근거 누락을 관리하기 어렵다. 알려진 필수 주석은 서버가 제공하고 모델의 추가 조회에는 호출 횟수와 문맥 예산을 둔다. 예산이 끝났다고 근거가 충족된 것으로 처리하지 않는다.

## 4. 연구 결과로 보완한 판단

독일 법령 청킹 연구는 조문·하위 조문 구조에 맞춘 검색이 해당 벤치마크에서 높은 재현율을 보였다고 보고한다. 복잡한 요약·의미 분할이 항상 유리하지 않았다는 결과다. 다만 정답이 조문 단위로 표시된 평가이므로 이를 셀 단위 품셈 정확성으로 확대 해석하지 않는다. [연구 초록과 버전 정보](https://arxiv.org/abs/2605.19806)

금융 보고서 연구는 문단을 모두 동일하게 취급하는 대신 문서 요소 종류를 반영하는 분할을 평가한다. 표와 설명을 구별하는 방향의 근거로 참고할 수 있다. 이번 조사에서 해당 실험을 재현하지 않았으므로 최적 크기나 품셈의 기대 개선율을 인용하지 않는다. [연구 초록과 버전 정보](https://arxiv.org/abs/2402.05131)

이번에 확인한 자료만으로 '조건부 참조를 그래프로 만들면 계산 정확성이 보장된다'는 주장은 할 수 없다. 품셈의 명시적 참조 연결은 우리 문서의 실제 요구를 바탕으로 제안하는 기능이다.

## 5. 우리 서비스에 제안하는 구조

### 5.1 원문 보관과 세 가지 검색 표현

원문은 문서 계층, 표 셀과 병합 범위, 주석, 참조 문장과 위치를 보존한다. 이 원문에서 다음 검색 표현을 자동으로 만든다. 별도 데이터베이스 세 개를 운영한다는 뜻은 아니며, 기존 저장소와 색인에서 종류를 구분할 수 있다.

| 검색 표현 | 담을 내용 | 주로 해결할 질문 |
|---|---|---|
| 공종 목록 | 절 제목·공법·원문 적용 범위·표 목록·근거 식별자 | '콘크리트 관련 기준 있어?', '펌프카 타설' |
| 규칙·설명 | 하나의 조건과 결과가 완결되는 문장 묶음·예외·원문 위치 | '할증 기준은?', '무엇이 포함돼?' |
| 표 또는 작업 조건별 묶음 | 머리글·단위·기준·공동 값의 적용 범위·표 식별자 | '이 조건의 품은?', '이 물량의 견적은?' |

공종 목록은 계산 명세가 없는 절도 포함한다. 문서 제목과 표 구조에서 자동 생성하며, 새로운 공종이 늘어도 동일한 생성 절차를 적용한다. 공법·조건을 모르면 해당 필드를 비워 두고 이름만 보고 만들어 넣지 않는다.

같은 원문을 여러 검색 표현으로 만들더라도 답변 근거는 원문 식별자로 중복 제거한다. 같은 절의 조각이 많다는 이유만으로 그 절의 검색 순위가 과도하게 올라가지 않도록 후보를 절 단위로 묶어 평가한다.

### 5.2 짧은 절은 넉넉하게, 긴 표는 조건별로

185쪽처럼 한 절의 표와 주석이 비교적 짧으면 전체 절을 부모 문맥으로 가져오는 안을 우선 비교한다. 장 전체를 부모로 쓰지는 않는다.

큰 절은 소절이나 개별 표 단위로 부모 범위를 조정한다. 큰 표를 나눌 때에는 행 하나보다 공법·조건·공동 작업량이 완결되는 행 묶음을 우선한다. 각 조각의 머리글·단위·산출 기준을 보존한다.

부모에 무엇이 들어 있는지는 미리 저장하고, 질문에 따라 실제 전달 범위를 조립한다. 모든 부모에 모든 참조 절을 미리 복사하지 않는다. 공통 규칙과 참조 대상이 개정될 때 중복 사본을 일일이 고치는 부담을 줄인다.

### 5.3 관계를 세 종류로 구분한다

| 관계 | 예 | 조회 방식 |
|---|---|---|
| 문서 소속 | 표가 어느 절에 속하는가 | 확정된 계층으로 부모를 읽음 |
| 근거 연결 | 주석이 어느 표·행에 적용되는가 | 범위가 확인된 필수 근거를 함께 제공 |
| 조건부 참조 | 특정 작업이 필요하면 다른 절을 따름 | 참조 원문과 대상을 읽고 적용 여부를 별도 판단 |

단순한 관련 용어와 규칙의 적용 관계를 구분한다. '철근공'이 같다는 이유로 여러 절의 값을 합치지 않는다. '참조'와 '별도 계상'도 같은 관계로 처리하지 않는다.

대상 절을 식별하는 것, 참조 조건을 해석하는 것, 계산 명세에 적용하는 것은 각각 검증 상태를 가진다. 관계에는 원문 위치와 조건 문장을 남긴다. 해석이 불확실하면 원문을 제공하고 적용을 보류한다.

### 5.4 검색과 에이전트 도구의 역할

권장 흐름은 다음과 같다.

1. 질문에서 확인된 연도·부문·공종 조건을 사용한다. 추정만으로 후보를 강하게 배제하지 않는다.
2. 공종 목록과 필요한 규칙·표 검색을 수행한다. 넓은 질문에서 공종 하나를 너무 일찍 확정하지 않는다.
3. 상위 후보의 원문 부모와 필수 주석을 서버가 가져온다.
4. 조건부 참조가 있으면 필요한 대상 근거를 추가로 조회한다.
5. 답변 또는 계산 전에 미해결 조건·근거 누락·지원되지 않는 규칙을 확인한다.

도구 이름은 예시이며 실제 구현을 확정한 것은 아니다.

| 도구 | 책임 |
|---|---|
| `search_works` | 공종 목록과 후보 근거를 찾음 |
| `search_rules` | 조건·예외·포함 범위 문장을 찾음 |
| `read_evidence` | 식별자로 표·부모 문맥·필수 주석을 읽음 |
| `follow_reference` | 원문에 명시된 참조 대상을 읽음 |
| `calculate` | 검증된 계산 명세와 확정·표시된 입력으로 계산 |

처음부터 다섯 개의 공종별 에이전트나 수천 개의 도구를 만들지 않는다. 모든 공종이 공통 도구와 스키마를 사용한다. 계산 명세의 자동 생성과 검증은 별도 파이프라인 책임으로 둔다.

근거 응답에는 원문 식별자, 표와 조건, 가져온 이유, 미해결 참조, 추출 불확실 상태를 포함한다. '알려진 참조를 모두 조회했다'는 상태를 '필요한 규칙을 전부 정확하게 해석했다'는 보장으로 표시하지 않는다.

## 6. 185쪽에서 어떻게 보일까

질문이 '장비사용 콘크리트 타설 품 알려줘'라면 다음을 기대한다.

- 공종 목록에서 관련 절을 찾는다. 목록의 설명에는 원문이 뒷받침하는 공법과 적용 범위만 들어간다.
- 6-1-1의 표와 주석을 읽는다. 63/55는 원문 공동 셀과 적용 행으로 유지한다.
- 규칙 질문과 연결될 수 있도록 산재 조건이나 포함 범위의 주석도 독립적으로 검색할 수 있게 한다.
- 표면 마무리 참조를 확인한다. 작업이 필요한지 불명확하면 조건을 확인하고, 필요할 때 6-1-3의 근거를 읽는다.
- 실제 품·금액은 선택한 명세와 조건으로 계산한다. 검색 결과에 있는 63/55를 임의 산식으로 바로 금액에 바꾸지 않는다.

질문이 '콘크리트 관련 기준 있어?'라면 공종 목록을 여러 절 단위로 보여준다. 처음부터 하나의 계산 명세를 선택할 필요가 없다.

질문이 '산재하면 어떻게 달라져?'라면 규칙 문장을 직접 찾고 대상 표로 올라간다. 모든 질문이 공종 목록 → 표의 한 경로만 통과하도록 고정하지 않는다.

## 7. 후보 조합과 장단점

| 조합 | 장점 | 부담·위험 | 판단 |
|---|---|---|---|
| 구조 청킹 + 부모 확장 | 원래 문서 형태를 활용하고 상대적으로 단순 | 넓은 목록 검색과 다른 절 참조는 부족할 수 있음 | 기본 비교군 |
| 위 조합 + 공종 목록·규칙·표 검색 표현 | 질문 유형에 맞는 검색이 가능하고 반복 직종명을 구분하기 좋음 | 표현별 갱신과 동일 원문 연결을 관리해야 함 | 우선 권장 |
| 위 조합 + 명시적 참조 조회 | 떨어진 절의 필요한 기준을 확보 | 참조 조건·순환·대상 누락 검사가 필요 | 계산·설명 흐름에 추가 |
| 모든 내용을 LLM 요약으로 검색 | 자연어 검색 표현을 풍부하게 만들 수 있음 | 요약 오류·조건 생략·재생성 관리 | 기본 구조 검증 후 선택적으로 비교 |
| 에이전트가 매번 문서 전체를 탐색 | 예상 밖의 질문에도 유연하게 접근 가능 | 지연·재현성·필수 근거 누락 관리가 어려움 | 보조 조회에 한정 |
| 자동 생성한 범용 지식 그래프·요약 계층 중심 | 폭넓은 관계·개요 탐색에 활용 가능 | 품셈 조건과 계산 정확성의 검증 부담이 큼 | 지금 우선 도입하지 않음 |

## 8. 검증 계획

같은 파싱 결과를 사용해 다음을 순서대로 비교한다. 모든 조합을 여러 파서와 곱해 실험하지 않는다.

| 안 | 구성 | 분리해서 측정할 효과 |
|---|---|---|
| 가 | 구조 기반 표·설명 조각, 현재 수준의 제목 정보 | 공통 기준선 |
| 나 | 가 + 부모 문맥과 필수 주석 | 주변 근거 누락 감소 |
| 다 | 나 + 공종 목록·규칙 등 검색 표현 구분 | 공종 발견과 규칙 검색의 개선 |
| 라 | 다 + 명시적 참조 조회 | 다른 절의 필수 근거 확보 |

첫 비교에서는 새 임베딩 모델과 재순위 모델을 함께 바꾸지 않는다. 동일한 문맥 예산에서 비교하고 예산을 늘렸을 때의 품질·지연도 별도로 기록한다.

평가는 다섯 사용자 의도를 포함한 기존 질문 초안 약 20개에서 시작한다. 같은 직종이 반복되는 공종, 큰 표, 다음 페이지의 주석, 조건부 참조, 여러 공종 요청을 포함한다. 개발에 쓴 185쪽과 처음 확인하는 표본을 구분한다.

### 지표

- 목록: 관련 절이 얼마나 포함되며 무관한 절이 얼마나 섞이는지
- 설명: 조건·예외·대상 표를 함께 가져오는지
- 품·견적: 값·단위·산출 기준·참조 규칙이 완결되는지
- 연결: 필요한 관계를 빠뜨리거나 잘못된 관계를 적용하는지
- 재현: 같은 원문·변환·명세 버전으로 근거 선택과 숫자를 추적할 수 있는지
- 성능: 실제 검색과 답변의 지연, 문맥 길이, 추가 조회 횟수

API 금지 상태에서는 저장 형식·근거 조립·원문 추적·오프라인 키워드 검색까지 확인한다. 실제 벡터 검색과 에이전트 답변의 개선 여부는 이후 허용된 환경에서 검증해야 한다.

## 9. 지금 할 일

1. 원문 보관 형식에 공종 목록·규칙·표라는 검색 표현을 연결하는 식별자를 추가 설계한다.
2. 185쪽으로 '공종 목록에서 찾기'와 '주석 문장으로 찾기' 두 경로의 결과 예시를 만든다.
3. 짧은 절 전체를 부모로 쓰는 안과 표 중심 근거 묶음을 비교한다.
4. 참조 조건을 함께 보여주고, 조회와 계산 적용을 구분한다.
5. 이 결과로 공통 조회 도구의 응답 형식을 고정한 뒤 구현 범위를 정한다.

이 작업은 공종별 수작업 명세를 새로 만드는 일이 아니다. 문서 전체에 적용할 일반적인 저장·검색 규칙을 정하는 일이다. 자동 처리가 어려운 관계는 미확정으로 남겨 검토량을 측정한다. 모든 공종을 손대지 않고 완벽하게 처리할 수 있다고 미리 약속하지 않는다.
