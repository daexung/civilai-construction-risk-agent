# 청킹·참조 색인·저장·임베딩·서비스 확인 실행 계획

버전: 1.15 · 작성일: 2026-10-11 · 갱신일: 2026-10-14 · 상태: 5b 답변 상태·원문 위치 인용 보완 완료. 개발 코드·평가 기록 PR #33 머지와 기존 서비스 배포 완료. Google·네이버 등록과 사이트맵 제출 완료. 새 검색의 운영 상담 전환은 미실행.

최신 결정: [5b 결과](../reviews/retrieval-step-05b-answer-state-citations-result-2026-10-14.md)에서 검색 정책을 유지하며 별도 답변 상태와 모델 위치 선택·코드 원문 인용을 구현했다. G02·N19 등 검색 한계는 남아 있다. 사용자의 머지·검색엔진 등록 요청에 따라 [PR #33과 등록 결과](../reviews/rag-merge-search-registration-2026-10-14.md)를 완료했다. 운영 상담은 기존 검색 경로이고 새 검색은 기본 꺼짐인 로컬 시험 경로다. Google 수동 색인 요청은 일일 한도로 미처리됐으며 사이트맵은 처리 완료다. 4g 최초 독립 결과와 이후 개발 기록은 보존한다. [추가 조사](retrieval-selection-research-decision-2026-10-12.md)와 과거 단계 지시서·평가 기록은 당시 조건 그대로 보존한다. 후속 작업은 새 검색의 운영 전환과 다중 공종 견적 범위를 결정한 뒤 별도 지시한다.

수정: 사용자가 기존 Supabase의 PostgreSQL을 계속 활용하도록 방향을 바로잡았다. 원문·절·관계·청크 저장은 기존 PostgreSQL 기반으로 설계한다. SQLite를 별도 운영 저장소로 추가하지 않는다. 벡터 검색은 현재 파일 방식과 PostgreSQL 벡터 방식의 전환을 별도로 결정한다.

## 1. 목표와 이번 범위

최종 제품 목표는 원문 근거와 가정이 표시된 건설공사 품·견적·Excel이다. 이번 계획의 목표는 그 앞단인 **질문에 맞는 공종과 표를 찾고, 단위·산출 기준·필요한 설명·다른 절 참조까지 읽을 수 있는 검색 기반을 로컬 서비스에서 확인하는 것**이다.

순서는 최종 파싱 결과 → 원문·절·관계 색인 → 청킹 → 근거 조회 → 임베딩과 결합 검색 → 로컬 서비스 비교다. 계산 명세 확대, 새 단가 확보, 여러 공종 합산·Excel 개선은 이 기반 위의 후속 목표다. 검색만 성공한 결과를 견적 정확성으로 보고하지 않는다.

사용자는 Claude에게 한 단계씩 맡기고 Codex와 결과를 검토하는 방식을 요청했다. 전체 계획을 승인해도 한 번의 지시서는 지정 단계까지만 실행한다. 새 변수가 나오면 해당 결정과 영향을 문서에 기록한 뒤 다음 지시서를 갱신한다. 완료된 파싱이나 통과한 단계 전체를 매번 다시 시작하지 않는다.

## 3. 채택할 기본 구성

```text
고정한 파싱 결과와 원본 PDF
  → 기존 Supabase PostgreSQL의 원문·절 목록·참조 그래프
  → 공종 목록 / 규칙·설명 / 표·작업 조건 검색 조각
  → 같은 입력으로 BM25 + Gemini 벡터 색인
  → 후보 검색과 중복 정리
  → 필요하면 재순위
  → 원문 식별자로 부모·기준·설명·명시적 참조 조회
  → 근거 충분함과 미확정 조건 확인
  → 로컬 서비스의 설명과 기존 계산 경로
```

기본안은 공개 실무에서 쓰는 구성과 맞는다. 최선이라는 결론은 우리 질문의 비교 결과로 내린다. 최신 문맥 임베딩, PageIndex, 이미지 검색, GraphRAG 등의 비교는 [조사 문서](rag-practice-update-2026-10-11.md)에 있다.

결정: 기존 Supabase PostgreSQL에 원문·계층·연결·검색 조각을 저장한다. 지식 자료는 예를 들어 `rag_knowledge` 같은 전용 스키마와 릴리스 ID로 관리한다. 기존 실제 스키마와 마이그레이션 규칙을 확인하고 최종 이름을 정한다. 원문을 읽는 경로는 `EvidenceStore` 같은 얇은 접근 계층으로 감싼다. 벡터는 첫 비교에서 기존 Parquet 형식을 재사용하고, pgvector 도입 여부는 임베딩 단계에서 같은 데이터로 검증한다. PostgreSQL 원문과 벡터는 같은 `release_id`로 묶는다.

## 4. 청킹 규칙

### 4.1 검색 조각과 답변 근거

검색 조각은 관련 내용을 찾기 위한 표현이다. 답변 근거는 실제 원문과 필요한 주변 내용을 모은 결과다. 검색용 제목과 별칭을 원문 본문에 덮어쓰지 않는다.

| 검색 조각 종류 | 생성 단위 | 함께 담을 검색 문맥 | 검색 뒤 읽는 원문 |
|---|---|---|---|
| 공종 목록 `work` | 실제 본문에 있는 공종·절 하나 | 연도·부문·절 번호·제목·원문 적용 범위 | 해당 절과 표 목록 |
| 규칙·설명 `rule` | 번호 항목 또는 완결된 설명 묶음 | 절 제목·대상 표 이름·조건 원문 | 해당 설명, 관련 표와 확인된 조건 |
| 표·작업 조건 `table` | 작은 표 전체, 큰 표의 완결된 행 묶음 | 제목·머리글·행 이름·단위·기준·공동 값 범위 | 원래 표와 적용 범위가 확인된 설명 |

규칙 조각에 담았다고 규칙의 계산 적용까지 확정한 것은 아니다. 일반 글도 `rule`의 하위 종류 `description`으로 보존할 수 있다. 같은 원문이 여러 검색 표현에 등장해도 원문 식별자는 같다.

### 4.2 구체적인 경계

1. 작은 표는 통째로 둔다. 큰 표만 공법·조건·공동 값의 묶음을 기준으로 나눈다.
2. 나눈 표 조각에는 필요한 열 머리글과 행 라벨, 단위, 산출 기준을 반복한다. 공동 값은 원문 칸 하나와 적용 행으로 추적한다. 반복 출력이 독립 수량을 뜻하지 않는다.
3. 줄글은 번호 항목·문단·문장 경계를 우선한다. 한 조건의 본문과 예외를 길이 때문에 분리했으면 같은 부모 근거로 연결한다.
4. 같은 문장도 원문 위치가 다르면 별도 보존한다. 겹침은 기본 0이며, 잘린 설명 문맥에 필요한 경우에만 근거를 기록하고 추가한다.
5. 쪽 경계만으로 뜻이 끊기지 않게 한다. 다만 현재 이어지는 표 후보 93건을 전부 한 표로 합치지 않는다. 확정 전에는 별도 표와 이어짐 후보로 읽는다.
6. 목차·표지·반복 머리글은 원문 보관과 사용처 장부에 남기고 답변 근거용 임베딩에서 제외한다. 공종 목록은 실제 본문 절 목록으로 만든다. 목차만으로 본문이나 적용 범위를 만들어내지 않는다.
7. 수식 조각은 원문과 위치를 보존하며 `formula_unresolved` 같은 상태를 전달한다. 잘못 이어 붙인 식을 검색 단계에서 완성한 식으로 표시하지 않는다.
8. 소속 미확정 설명은 자체 검색이 가능하게 남기고 후보 관계를 표시한다. 가까운 표의 확정 적용 조건으로 자동 전환하지 않는다.

### 4.3 길이 설정과 과대 조각 처리

처음 비교할 목표는 설명 조각 약 800토큰, 표 묶음 약 1,600토큰이다. 최적값이라는 주장이 아니라 실험 시작값이다. 실제 토큰 분포와 실패 사례를 보고 한 번 좁혀 비교한다. 제목과 반복 머리글을 포함한 최종 임베딩 입력으로 계산한다.

Gemini 안내의 입력 한도는 8,192토큰이다. 우리 계획의 안전 상한은 6,000토큰으로 시작한다. 모델에 맞는 토큰 계산 방법의 지원 여부를 확인한다. 로컬 추정치를 실제 API 토큰 수로 표시하지 않고, 지원되는 계산 경로나 소량 호출로 한도를 확인한다. 입력을 조용히 잘라서 성공 처리하지 않는다. [모델 안내](https://ai.google.dev/gemini-api/docs/embeddings)

완결된 표 묶음 자체가 상한을 넘으면 원문 부모 표는 통째로 보존하고, 행 묶음 또는 열군을 머리글·행 식별자와 함께 나눈다. 이것도 불가능하면 해당 조각을 `oversize_unembedded`로 기록하고 절·표 목록을 통한 원문 조회 경로를 제공한다. 누락을 숨긴 채 전체 임베딩 완료로 보고하지 않는다.

## 5. 절 연결 그래프의 사전 색인

### 5.1 연결은 미리 만들고 적용은 질문 시 판단

예: 공통 6-1-1의 주석 → 공통 6-1-3 표면 마무리. 출발 주석, 도착 절, 조건 원문, 원문 위치를 미리 저장한다. 서비스는 질문을 받은 뒤 이 연결을 따라 읽고, 표면 마무리가 이번 작업에 필요한지를 별도로 판단한다.

`232건`은 현재 추출기가 찾은 참조 문장 수다. 문서에 존재하는 참조 전체를 빠짐없이 찾았다는 수치가 아니다. 첫 단계는 이 목록의 대상 연결과 본문에서의 일반 참조 후보 점검을 함께 한다. 추가 후보는 원문 근거와 별도 목록으로 남기고 기존 232건과 섞어 성과를 부풀리지 않는다.

### 5.2 대상 식별과 상태

- 절 키: 문서 버전 + 연도 + 부문 + 절 번호. 같은 번호의 공통·건축·기계설비 절을 구분한다.
- 원문에서 부문을 명시하면 그 부문을 사용한다. 부문이 없다고 같은 번호의 첫 결과를 고르지 않는다. 같은 부문 추정도 근거와 후보 상태를 남긴다.
- `1-2-4/7. 잡재료 및 소모재료`처럼 절 아래 항목을 가리키면 절과 하위 항목을 함께 기록한다. 절만 찾은 경우 부분 연결로 표시한다.
- 목차·반복 제목은 실제 본문 절과 구별한다. 항목 코드 `(7750)` 등을 절 번호로 강제 변환하지 않는다.
- `target_status`: `resolved`, `partial`, `ambiguous`, `missing`, `external`. 해석 전 원시 문구도 보존한다.
- `source_status`: 기존 파싱의 확인·미확정 상태와 판단 근거. 원래 `confirmed`를 덮어쓰지 않는다.
- `applicability`: 이번 질문의 적용 여부 `unknown`, `applies`, `does_not_apply`. 원문 DB의 전역 확정값으로 저장하지 않고 질문별 조회 기록에 둔다.
- `condition_text`가 비어 있어도 무조건 적용으로 간주하지 않는다. 문장 전체를 보존하고 조건 해석 여부를 따로 남긴다.

### 5.3 관계 종류와 탐색 범위

문서 소속, 표 기준, 주석 후보, 작은 표 소속, 표 이어짐, 명시적 참조, 제외·별도 계상 문구를 구분한다. 뒤의 의미 관계는 문구가 있다고 즉시 비용 규칙으로 확정하지 않는다.

명시적 참조 그래프에는 출발·도착 색인을 모두 둔다. 도착이 모호하면 후보 목록을 저장한다. 관계 출발점이 원시 제목 문자열 또는 행 선택자이면 원문 그대로도 남기고 정규화 성공 여부를 기록한다. 식별할 수 없는 끝점을 임의 생성하지 않는다.

조회는 처음 1단계 참조를 가져오고, 필요한 근거가 더 있으면 최대 2단계까지 추가한다. 이는 초기 운영 한도이며 문서 의미의 한도가 아니다. 방문한 식별자를 기록해 순환을 막는다. 깊이나 토큰 한도에 걸린 경로를 `unresolved_references`에 남기고 근거 완성을 거짓으로 표시하지 않는다.

## 6. 데이터베이스와 파일 저장

### 6.1 물리 배치

기존 원본 PDF와 최종 파싱 묶음은 변경하지 않는다. 새 구현 폴더는 `experiments/retrieval-v1` 하나로 이어가며, 단계마다 500MB 파싱 폴더를 복사하지 않는다. 작은 설정·검사·지시·보고서는 Git에 넣고 큰 결과는 버전별 별도 파일로 보관한다.

예정 출력 묶음:

```text
experiments/retrieval-v1/
  src/                       생성·색인·조회 코드
  checks/                    의미 있는 검사와 고정 사례
  config/                    길이·조회·모델 설정
  out/<release_id>/
    import_manifest.json     PostgreSQL 적재 대상·버전·행 수·해시
    chunks.jsonl             기존 검색·임베딩용 호환 내보내기
    vectors.<model>.parquet   임베딩 후 생성
    manifest.json            전체 파일 해시·버전·완료 상태
    source_coverage.json      모든 입력의 사용처와 제외 사유
    reference_ledger.json     참조 대상 연결 상태
    metrics.json              크기·시간·품질·미확정 집계
```

PostgreSQL에 적재한 릴리스가 새 조회 데이터의 기준이고 JSONL은 그 내보내기다. 양쪽을 독립 수정하지 않는다. SQL 마이그레이션·적재 코드·입력 장부를 함께 보관해 다시 만들 수 있게 한다. 원래 파싱 출력은 변환 전 원본이다. 파일 경로는 저장 위치, 식별자는 자료의 정체성이며 서로 섞지 않는다.

### 6.2 논리 테이블

| 테이블 | 역할과 주요 필드 |
|---|---|
| `documents` | 문서 ID, 연도, 파일 해시, 원문 위치, 파싱 생성 ID |
| `nodes` | 절·제목·표·칸·본문·행 묶음의 ID, 종류, 원문 글, 페이지, 좌표, 기존 원시 ID, 구조 JSON |
| `sections` | 절 ID, 문서·부문·절 번호, 제목, 부모 절, 본문 범위, 식별 상태 |
| `source_records` | 레코드 UID, 순서, 원문 글, 원래 JSON, 연결 정보. 23,481개 전부 보존 |
| `source_relations` | 기존 관계 11,823건의 원래 JSON과 출발·도착 원시 값. 복잡한 관계도 소실 없이 보관 |
| `edges` | 정규화한 출발·도착 노드, 종류, 조건 원문, 근거 위치, 대상 상태, 기존 상태, 판단 방법 |
| `edge_candidates` | 미확정 참조의 후보 대상과 선택 근거 |
| `chunks` | 조각 ID, 종류, 부모 ID, 검색 글, 원문 연결, 부문·절, 토큰 수·계산 방법, 불확실 상태 |
| `chunk_sources` | 조각과 원문 레코드·칸·문자 범위의 대응. 머리글 반복도 역할로 표시 |
| `embedding_jobs` | 조각 ID, 입력 해시, 제공자·모델·차원·입력 형식 버전, 성공 상태, 벡터 위치 |
| `releases` | 코드·설정·원문·청크·벡터 버전, 완료 상태와 생성 시각 |

첫 단계는 청크와 임베딩 테이블을 비워 둔다. 모양만 필요 이상으로 만드는 대신 이후 단계에서 사용하는 열을 추가할 수 있다. 원문 표의 셀·병합 범위는 구조 JSON도 보존하므로 SQL 열로 전부 펼칠 필요는 없다.

`nodes`의 원문 ID와 `source_records` UID는 원본 그대로 보존한다. 새로운 절·청크 ID는 원문 버전, 원문 위치, 포함된 원문 ID, 분할 규칙 버전으로 결정한다. 전체 레코드 순번만으로 만들지 않는다. 같은 원문을 다시 생성하면 같은 ID가 나오게 하고, 파싱·분할이 바뀐 경우에는 내용 기반 대응표를 남긴다. 임베딩 캐시의 재사용 키는 ID 외에 입력 해시와 모델 설정을 포함한다.

### 6.3 운영과 확장

적재 시 새 릴리스에 트랜잭션으로 기록하고 외래 키·유일성·무결성을 검사한다. `building` 결과는 서비스가 읽지 않는다. 완료된 PostgreSQL 릴리스와 JSONL·벡터의 해시를 묶고 새 릴리스 전체를 선택하는 설정으로 전환한다. 이전 릴리스는 되돌리기용으로 보관한다. 회원·대화 테이블을 덮어쓰지 않고 지식 자료에 필요한 서버 조회 권한만 부여한다. 운영 Supabase 적용에 앞서 같은 PostgreSQL 문법과 제약으로 별도 검증 환경에서 마이그레이션·적재를 확인한다.

1만 개 벡터 × 3,072차원 × float32는 벡터 행렬만 약 117MiB다. 실제 메모리는 본문·BM25·중간 배열 때문에 더 크다. 새 조각 수가 정해진 뒤 실제 최대 메모리와 지연을 측정한다.

벡터 검색 경로 검토의 초기 기준: 목표 동시 요청 5개에서 API 시간을 뺀 검색·근거 조회 p95가 1초를 넘거나, 프로세스 메모리 목표 1GB를 넘거나, 벡터를 자주 갱신해야 하는 경우다. 이 숫자는 현재 성능 측정값이 아닌 설계 목표다. 기존 Parquet 검색과 PostgreSQL+pgvector를 같은 자료로 비교한다. 원문 PostgreSQL 사용 여부와 벡터 검색 방식을 혼동하지 않는다. 실제 Supabase 자원·연결·권한·pgvector 버전은 적재 전 확인한다.

## 7. 임베딩·검색·근거 조회

### 7.1 임베딩 기본값과 비교 후보

기준 모델은 현재 구현된 `gemini-embedding-2`, 3,072차원이다. 예전 6장 비교에서 사용한 평가와 캐시 경로를 재사용하되 당시 작은 표본 성적을 전체 문서 성적으로 주장하지 않는다.

검색 입력은 문서 연도·부문·절·제목·해당 공법·단위와 원문 조각으로 만든다. 수량을 임의 환산한 문장이나 추정 조건을 붙이지 않는다. 문서와 질문에 각각 맞는 입력 형식을 사용한다. 현재 코드의 `title: ... | text: ...`, `task: search result | query: ...`는 확인한 공식 안내와 일치한다. [입력 형식](https://ai.google.dev/gemini-api/docs/embeddings)

우선 대안은 `voyage-context-4`다. 같은 절의 이미 나눈 조각을 묶어서 임베딩하고 자동 분할은 끈다. 원문 절이 입력 한도를 넘으면 구조 경계로 문맥 그룹을 나눈다. 원문 절 전체가 바뀌면 해당 문맥 그룹의 모든 벡터가 달라질 수 있으므로 캐시 키에 그룹 입력 해시와 순서를 포함한다. 조각 글자만 같다는 이유로 이전 문맥 벡터를 재사용하지 않는다. [공식 안내](https://docs.voyageai.com/docs/contextualized-chunk-embeddings)

비교는 동일한 조각·질문·검색 설정에서 한다. 초기 소규모 비교는 고정된 최대 1,000개 조각과 헷갈리는 다른 공종을 함께 넣고 별도 결과로 보고한다. 이는 전체 검색 품질의 증거가 아니다. 대안을 채택하려면 전체 후보 색인에서 다시 비교하고 기존 결과와 함께 보관한다. 접근 권한이 없거나 개선이 불명확하면 기준 모델로 진행하며, 새 모델 도입 대기로 모든 단계를 멈추지 않는다.

### 7.2 비용·중단·재개

전체 호출 전에 최종 입력 수, 토큰 합, 기존 캐시 재사용 수, 예상 호출·비용을 기록한다. 공식 가격표 조회 시 Gemini Embedding 2 텍스트는 표준 100만 토큰당 0.20달러, 비동기 Batch는 0.10달러다. 실제 실행 시 재확인한다. 지금 코드의 여러 입력 묶음 호출이 비동기 Batch 할인 대상이라는 뜻은 아니다. [가격표](https://ai.google.dev/gemini-api/docs/pricing)

문서 임베딩 예상액은 새 입력 토큰 합 ÷ 100만 × 선택한 경로 단가로 계산한다. 질문 임베딩, 재순위, 설명 생성 비용은 별도다. 아직 최종 청크가 없으므로 전체 비용이나 완료 시간을 확정하지 않는다.

첫 호출은 다양한 길이 32개로 입력 수=벡터 수, 차원, 유한값, 0벡터, 재실행 캐시를 확인한다. 성공한 결과를 단계적으로 저장하고 재시도 한도를 둔다. 이후 전체 색인에서는 필요한 모든 검색 조각의 벡터가 있어야 `ready`로 표시한다. 실패·상한 초과·제외 목록을 별도로 남긴다. 새 색인과 예전 질문 모델을 섞지 않는다.

### 7.3 검색 방식

기존 BM25+정확 벡터 검색과 RRF를 기준으로 둔다. 공종 목록·규칙·표는 하나의 논리 색인에서 `kind`로 구분하고, 처음부터 질문 의도에 따라 하나만 조회하도록 닫지 않는다. 기존 실험에서 그 방식의 전반적 개선이 없었다.

첫 비교는 현재 방식당 후보 20개를 유지한다. 후보 누락이 실제로 관찰되면 50개 설정을 한 번 비교한다. 원문 숫자와 단위는 보존하고 검색용 정규화에만 `루베/㎥/m3`, `펌프카/펌프차`, 숫자·단위 띄어쓰기 등을 적용한다. 임의 공법을 기본값으로 정하지 않는다.

같은 원문에서 파생한 여러 표현이 상위 결과를 독점하지 않게 원문 ID로 중복을 조절한다. 목록 질문은 공종 다양성을, 규칙 질문은 설명과 표의 연결을 확인한다. 근거를 모으기 전에 엉뚱한 공종을 선택한 문제와, 맞는 공종의 설명을 누락한 문제를 따로 측정한다.

재순위는 동일 후보 상위 최대 50개에 대해 끈 상태와 켠 상태를 비교하고 상위 10개를 근거 조회에 사용한다. 필수 주석과 참조는 재순위 결과에 없다는 이유로 빠뜨리지 않는다. 후보에서 정답을 찾는 비율이 낮으면 재순위로 해결됐다고 보고하지 않는다.

### 7.4 근거 조회와 서비스 연결

`search_evidence(query, filters)`는 후보와 원문 ID를, `read_evidence(ids, budget)`는 필요한 원문 묶음을, `follow_references(ids, max_depth)`는 저장한 참조 대상을 반환한다. 공종마다 별도 도구를 만들지 않는다.

조회 결과 공통 필드: `release_id`, `source_ids`, `pages`, `selected_nodes`, `why_included`, `target_status`, `source_status`, `unresolved_references`, `coverage_complete`, `applicability_unknown`이다. 출처 링크는 실제 원문 위치에서 만든다.

기준과 설명은 확정 관계면 적용 근거로, 위치 기반 관계면 확인할 문맥으로 표시한다. `confirmed=false`라는 이유로 전부 버리지도, 전부 확정하지도 않는다. 예산 초과 시 완결된 묶음 단위로 읽고, 추가 조회가 필요하다고 반환한다. 필수 조건 문장을 중간에서 잘라 정상 완료로 표시하지 않는다.

현재 `qa_context.py`의 고정 청크 경로와 별도 캐시를 새 릴리스 설정으로 통일해야 한다. 새 검색 결과와 옛 부모 문맥을 섞는 오류를 검사한다. 기존 PDF 직접 읽기 보충 경로가 교정된 원문을 덮어쓰거나 조각난 식을 정상값으로 바꾸지 않도록 출처와 용도를 구분한다.

에이전트는 공통 조회 후 근거가 부족할 때만 최대 2회 추가 검색을 시도한다. 여러 공종 질문은 항목별 근거를 유지한다. 계산 명세가 없는 공종도 목록·설명은 제공할 수 있게 한다. 계산 적용은 기존 검증 경로와 불확실 상태를 따른다.

## 9. 평가와 종료 기준

### 9.1 비교군

- A0: 보관된 기존 서비스 자료와 현재 방식. 제품 전체 변화 비교용.
- A1: 최종 파싱 + 기존 청킹·검색. 파싱 변화와 청킹 변화를 구별하는 기준. 기존 함수가 소비하지 않는 관계도 한계로 기록.
- B: 최종 파싱 + 새 청킹·근거 조회 + 기존 임베딩·결합 검색.
- C: B의 동일 후보에서 재순위만 추가. 정답 후보가 있을 때 순위 개선 평가.
- D: B의 같은 조각과 검색 설정에서 문맥 임베딩만 변경. 모델과 재순위를 동시에 바꾸지 않음.

A1의 완전한 실제 서비스 연결은 필요 없다. 같은 입력으로 조각·조회·순위를 재현할 수 있으면 된다. 이미 만든 비교 코드와 질문을 재사용한다. A0와 B의 차이를 모두 청킹의 효과라고 주장하지 않는다.

### 9.2 질문과 정답 자료

기존 20문은 개발·회귀로 재사용한다. 정답이 초안인 항목은 원문 대조로 보완하고 애매한 질문에 한 공법을 강제하지 않는다. 새 확인 질문 20문은 결과를 보기 전에 고정한다: 목록 4, 규칙 4, 품 4, 단일 견적의 근거 3, 여러 공종의 근거 3, 자료 없음 2. 최소 여러 부문·번호 충돌·표 이어짐·참조 조건·공동 값·동의어·수식 미확정을 포함한다.

각 질문에는 정답 공종 후보 집합, 필수 원문 위치, 붙이면 안 되는 근거, 허용 답변·확인 질문, 해석 보류 여부를 기록한다. 새 20문은 방법을 고정한 뒤 평가한다. 실패를 보고 고쳤다면 그 사례는 이후 개발 사례로 표시하고, 새 독립 평가라고 부르지 않는다.
