# 답변 실행 로그와 사용자 평가 연결 계획

작성일: 2026-10-14 · 상태: 구현과 로컬 검증 완료, PR 검토 준비. 운영 DB 적용과 배포는 미실행.

이 문서의 아래 현황은 설계 당시 기록이다. 실제 완료 상태와 검증 한계는 `docs/reviews/answer-trace-lifecycle-verification-2026-10-14.md`를 따른다. 로컬에는 두 마이그레이션이 모두 적용됐다. 운영에는 새 테이블이 필요하므로 운영 DB 변경을 검토·적용하기 전에 이 PR을 머지하지 않는다. 머지 시 기존 자동 배포가 시작된다.

## 목적과 결정

사용자 화면과 상담 API 응답은 유지하고, 백엔드에서 실행 과정을 수집해 Supabase에 저장한다. 사용자 평가에서 당시 검색·선택·계산·답변 생성 기록을 찾아 오류 원인을 검토할 수 있어야 한다.

전체 실행과 개별 단계를 분리하는 구조를 채택한다. 새 테이블은 `answer_runs`, `answer_run_steps` 두 개이며 기존 `answer_feedback`을 연결한다. 이 구조가 현재 목적에 적합하다는 설계 판단이며 모든 서비스에 가장 좋다는 주장은 아니다. 수집 형식은 trace와 span의 식별·부모 관계를 참고하지만 초기 구현에 별도 외부 추적 서비스나 Collector 설치를 요구하지 않는다.

## 현재 코드와 중단한 작성본

- `backend/agent/graph.py`는 여러 노드를 감싸 처리 시간을 합산한다. `ask`는 시간 래퍼 밖에 있고, 계산·선택 등은 하나의 시간 항목으로 합쳐진다.
- `backend/agent/estimate/dialogue.py`의 그래프는 `turn` 한 노드다. 실제 도구 호출은 `_run_tool`에서 이루어지고 현재 도구 이름·인수·상태·거절 이유를 턴 상태에 남긴다. 노드 기록만 넣으면 이 경로의 상세 계산은 보이지 않는다.
- 모델 호출 정보와 최종 표·행·열 인용 일부가 기존 응답과 회원 대화에 남지만 통일된 실행 이력은 아니다.
- 중단 전 `answer_runs` 단일 테이블과 평가 검토 컬럼을 로컬 DB에 추가했다. 운영 Supabase에는 반영하지 않았다. 코드에는 실행 정보를 API 응답에 넣는 작성본이 있으며, 승인된 새 구현에서는 제거한다.
- 작성본·로컬 자료는 그대로 보존한다. 재개 시 로컬 스키마 이행 파일을 추가해 새 안에 맞추고, 이미 적용한 로컬 마이그레이션을 조용히 덮어쓰거나 초기화하지 않는다. 원격 반영 전의 마이그레이션 목록과 적용 순서를 확인한다.

## 저장 구조

### answer_runs: 요청 한 번의 실행 요약

| 필드 | 형식 | 의미 |
|---|---|---|
| id | uuid, 기본 키 | 실행 번호. 답변 번호와 구별 |
| answer_id | uuid, 선택, 고유 | 실제 반환·저장한 답변 번호. 답변 생성 전 실패는 비어 있을 수 있음 |
| request_id | uuid, 선택 | 클라이언트 요청 번호. 단독으로 전역 고유하다고 가정하지 않음 |
| user_id / conversation_id | uuid, 선택, 연결 키 | 검증한 회원과 대화. 회원 대화 저장이 완료된 뒤 소속 연결 |
| thread_id | text | 서버가 관리하는 대화 번호. 비회원 세션 비밀키를 저장하지 않음 |
| environment | text | local / production 구분 |
| agent_mode | text | 기존 그래프 / 도구형 경로 구분 |
| started_at / finished_at | timestamptz | 실행 시작·끝 |
| status | text | running / completed / failed / incomplete |
| answer_status | text, 선택 | 실제 응답 상태. 실행 성공 여부와 구별 |
| versions | jsonb | 실제 코드·검색 자료·벡터·명세·단가 파일 버전 또는 해시 |
| capture_status | text | complete / partial. 기록 완전성과 답변 정확성을 구별 |
| expires_at | timestamptz | 보관 기한 |

검색 릴리스 ID가 없는 기존 운영 자료에는 실제 파일 해시를 쓴다. 새로운 실험 릴리스 ID를 붙여 운영 전환된 것처럼 표시하지 않는다. 설정한 모델과 실제 호출한 모델도 구별한다. 해시는 자료를 식별하지만 자료 자체를 복원하지는 못하므로, 배포 자료·코드·프롬프트를 버전으로 보존하는 기존 경로와 연결한다.

### answer_run_steps: 단계 한 번당 기록 하나

| 필드 | 형식 | 의미 |
|---|---|---|
| id | uuid, 기본 키 | 단계 실행 번호 |
| run_id | uuid, 연결 키 | 소속 전체 실행 |
| parent_step_id | uuid, 선택 | 도구·모델 호출을 포함한 상위 단계 |
| step_kind | text | node / tool / model |
| name | text | retrieve, compute, compute_labor 등 |
| sequence | bigint | 실행 내 기록 번호. 시간·부모 관계와 함께 읽음 |
| started_at / finished_at / duration_ms | 시간 / 수치 | 시작·끝과 처리 시간 |
| status | text | completed / rejected / failed / incomplete |
| input_summary / output_summary | jsonb | 단계별 허용한 항목만 수집한 입력·출력 요약 |
| error_code / error_type | text, 선택 | 정리한 실패 유형. 비밀정보가 섞일 수 있는 원문 예외는 넣지 않음 |
| metadata | jsonb | 실제 모델·제공자, 지시문·응답 스키마 해시, 재시도 번호, 토큰 수 등 확인한 정보 |

부모 단계는 같은 전체 실행에 속해야 한다. `(run_id, sequence)`는 고유하게 하고 반복한 같은 노드는 별도 행으로 남긴다. 병렬 실행을 단순 목록 순서만으로 앞뒤 관계라고 판단하지 않는다. 모델 재시도는 같은 답변 실행 아래에서 별도 시도 또는 확인된 시도 수로 표시하며, 추정 토큰·비용은 실제 수치와 구별한다.

DB 색인은 단계의 `run_id`, `(name, status, started_at)`, 전체 실행의 `answer_id`, `conversation_id`, `started_at`에 둔다. 초기에는 JSON 전체에 무거운 검색 색인을 만들지 않는다.

### answer_feedback: 기존 평가 유지

기존 `answer_id`, 평가·이유·질문·답변 저장은 유지한다. `run_id`는 전체 실행의 `id`에 연결한다. 이전 평가의 실행 번호는 확인할 수 없으면 비워 둔다.

검토 항목은 `review_status`, `error_type`, `review_note`, `expected_evidence`, `reviewed_at`으로 두고, 검토자 식별도 기록한다. 사용자가 평가를 변경하면 다시 검토가 필요하다는 상태로 표시하되 기존 검토 내용을 자동 삭제하지 않는다. 검토 결과 수정 이력은 평가 자료 고정 시 별도로 보존한다.

검토 화면을 새로 만드는 것은 초기 범위에 넣지 않는다. 운영자는 Supabase에서 평가와 실행·단계를 연결한 조회로 확인한다. 일반 이용자는 로그 테이블을 읽거나 쓸 수 없다. 회원 대화의 payload에도 운영자용 로그를 넣지 않는다.

## 단계에서 남길 내용

| 단계 | 입력·출력의 핵심 |
|---|---|
| 질문 분류 | 분류 결과·확인된 신뢰도·다음 경로. 원문 질문 전체는 로그에 복사하지 않음 |
| 검색 | 실제 검색한 자료 버전, 반환 후보의 조각 ID·순위·점수, 검색 방식과 대체 검색 여부 |
| 표 선택 | 후보 ID, 선택한 표·행·열·조건, 보류·거절 코드 |
| 조건 확인 | 계산에 필요한 수치·열거 조건의 확인 상태, 부족하거나 거절한 필드 |
| 계산·단가 | 사용한 품·수량·단위·적용 규칙 ID·단가 버전·산식·결과 |
| 답변 생성 | 실제 전달한 근거 ID·원문 위치, 모델 호출 metadata, 인용·숫자 검증 결과, 원문 표시로 전환한 이유 |

ID만으로 의미 오류를 판단할 수는 없다. 계산에 실제 사용한 원문 값과 행·열 위치도 보관한다. 원문 근거와 검색 문맥, 확정 근거와 검토용 자료를 구별한다. 기록된 선택·검증 결과를 근거로 원인을 검토하며 모델의 숨은 내부 사고를 기록하거나 추측하지 않는다.

## 수집과 저장 방식

1. 인증·대화 소유권과 기존 중복 요청 판정을 먼저 수행한다.
2. 새 실행에는 독립 실행 번호를 발급하고 시작 요약을 짧은 DB 작업으로 저장한다. 시작 시 아직 생성되지 않은 회원 대화를 연결 키로 넣지 않는다.
3. 공통 래퍼에서 노드 시작·끝·예외를 수집한다. 도구형 경로는 `_run_tool`도 감싸고 실제 모델 호출을 그 아래에 연결한다. 기존 단계별 시간 집계는 유지한다.
4. 상세 기록은 요청 안에서 모아 성공·예외 종료 시 묶어서 저장한다. 노드마다 원격 DB를 호출하지 않는다. 성공한 회원 대화가 확정되면 실행 기록에 소속·답변 번호를 연결한다.
5. 상담 저장과 진단 기록 저장을 분리한다. 상담 트랜잭션이 실패해도 실패 실행 기록을 남기며, 로그 저장 장애가 정상 답변을 실패시키지 않도록 한다. DB가 완전히 끊기면 무손실 저장을 보장할 수 없다. 이 경우 안전한 서버 경고에 실행 번호와 실패 유형을 남겨 수집 장애를 확인한다.
6. 응답을 반환하기 전에 제한 시간을 둔 일괄 저장을 시도한다. Cloud Run에서 응답 뒤 백그라운드 작업만으로 저장을 맡기지 않는다.
7. 서버 재시작으로 끝 기록이 없는 실행은 `incomplete`로 식별한다. 종료 시 묶기 때문에 마지막으로 실행한 미저장 단계까지 복원된다고 주장하지 않는다.
8. 같은 완료 요청을 다시 받으면 기존 실행을 연결한다. 모델·노드 실행 기록을 복제하지 않는다. 실패 후 실제 재실행은 새 실행 번호로 기존 요청과 연결한다.

로그 객체는 요청별 context로 관리하며 병렬·동시 사용자 실행이 섞이지 않게 한다. 프론트 응답·대화 복원 API에는 로그를 추가하지 않는다. UI의 `answer_id`와 기존 평가 버튼을 그대로 사용한다.

## 보관·용량·삭제

- 초기에는 성공·실패 모두 작은 요약을 수집해 평가 전에 로그가 없어지는 일을 줄인다. 전체 상태 덤프, 모델 원 응답, 원문 PDF·이미지, 벡터, 키·토큰·세션 비밀·IP·이메일은 넣지 않는다.
- 단계 요약에 크기 상한을 두고 잘린 항목·개수와 사유를 기록한다. 잘린 로그는 수집 완전으로 표시하지 않는다. 필요한 필드와 상한은 대표 실행의 실제 용량을 측정해 고정한다.
- 기본 보관은 90일. 평가가 연결되면 해당 평가의 보관 기한까지 연결 로그를 유지한다. 이후 평가만 남고 원인 기록이 먼저 사라지는 일을 방지한다.
- 회원 대화·계정 삭제는 연결 실행·단계에도 적용한다. 비회원 대화 삭제·회원 이전 처리도 기존 비밀 세션 검증을 통과한 범위에서 연결을 정리한다.
- 기존 개인정보 안내의 실제 수집 항목·보관 설명을 맞춘다. 비회원 질문·답변 본문은 기존 정책대로 평가한 경우에만 평가 테이블에 저장한다. 로그의 수치·조건 요약도 개인정보일 수 있어 접근과 삭제 정책을 동일하게 적용한다.
- 매번 커지는 기록은 단계 개수·평균 기록 크기·저장 실패 수로 집계한다. 현재 트래픽에서는 별도 메시지 큐나 외부 로그 서비스를 추가하지 않는다. 확장은 측정한 병목이 생기면 결정한다.

## 평가·개선으로 이어지는 후속 흐름

사용자 평가 → 운영자 원인 검토 → 올바른 원문 근거·결과 확정 → 개인정보를 제거한 평가 문제 등록 → 기존 평가 도구로 수정 전후 비교 → 승인 후 배포.

로그는 정답이 아니고 사용자 평가도 정답 확정이 아니다. 검토한 평가 사례만 기존 평가 자료에 연결한다. 조정에 쓴 사례와 새 독립 평가를 구별한다. 초기에는 자동 학습·자동 배포를 추가하지 않는다.

## 구현 순서와 완료 기준

1. **작성본 정리와 로컬 스키마 이행:** 응답에 실행 정보를 붙인 작성 부분 제거, 실행·단계 테이블 및 기존 평가 연결 설계 반영. 기존 데이터 보존.
2. **노드·도구·모델 수집:** 기존 그래프와 도구형 경로를 모두 포함. 실패·재시도·중복·비회원 이전 처리까지 로컬 검증.
3. **조회와 평가 연결:** 평가 한 건에서 당시 단계·표·산식·검증 결과를 찾는 운영자 조회와 검토 기록 확인.
4. **원격 반영과 배포:** 로컬 확인 뒤 Supabase 스키마 반영, 코드 배포, 통제된 시험 실행으로 실제 경로 저장 여부 확인.

필수 확인:

- API 응답과 회원 대화 복원에 운영자 로그가 나타나지 않는다.
- 답변 번호로 전체 실행과 단계 기록을 조회한다.
- 계산하지 않은 질문에 계산 기록을 만들지 않는다. 같은 노드를 반복한 실행은 구별한다.
- 도구형 `turn` 안의 실제 도구·모델 호출과 부모 관계가 보인다.
- 중간 오류·모델 재시도·로그 DB 장애·미완료 실행을 구별하고 정상 답변의 기존 동작을 유지한다.
- 동시 두 사용자 기록이 섞이지 않고, 중복 요청에서 로그·호출이 중복되지 않는다.
- 기존 답변은 과거에 없던 자료 버전·단계 기록을 만들어 넣지 않는다.
- 비회원 평가·회원 이전·대화 삭제·계정 삭제·보관 기한을 확인한다.
- 수집 전후 답변·계산 값과 API 계약이 같고, 추가 지연과 저장 크기를 측정해 보고한다.
