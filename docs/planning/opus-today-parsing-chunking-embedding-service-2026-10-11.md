# 오늘 실행 지시서: 남은 파싱 해결부터 로컬 서비스 확인까지

> 실행 보류: 사용자가 이후 작업 범위를 파싱 해결만으로 줄였다. 아래 통합 지시서는 현재 실행 지시가 아니다. 최신 지시서는 `opus-all-held-tables-parsing-only-2026-10-11.md`다. 청킹·임베딩·서비스 수정·API 호출로 진행하지 않는다.

## 최종 목표와 역할

사용자는 **오늘 2026-10-11 안에 파싱·청킹·임베딩을 거쳐 서비스 개선을 확인하는 것**을 목표로 정했다. 확인 환경은 **로컬 서비스**로 직접 선택했다. 당신은 Claude Code Opus로 구현·실행·원문 대조를 맡고, Codex는 결과 검토를 맡는다.

이번에는 파싱 보고서만 제출하고 멈추지 않는다. 다음 네 단계를 순서대로 이어서 수행한다.

`남은 파싱 보류 해결 → 전체 청킹과 원문 연결 → 실제 임베딩 → 새 데이터를 쓰는 로컬 서비스에서 질문 응답 비교`

각 단계의 진행과 결과를 짧게 알리되, 지시된 다음 단계마다 다시 승인을 요청하지 않는다. 사용자에게는 쉬운 한국어로 설명하고 한자는 사용하지 않는다. 단계별 부분 완료와 최종 완료를 구분한다.

## 승인 범위와 기존 제한

- 남은 보류 표 전체의 원문 대조와 파싱·후처리 수정, 청킹과 근거 연결 수정, 임베딩 생성, 로컬 서비스 연결과 필요한 검색·답변 경로 수정, 실제 질문 응답 확인을 진행한다.
- 기존 문서의 임베딩·API 금지는 이전 실험 범위다. 최신 사용자 지시의 **임베딩 생성과 로컬 서비스 검증에 필요한 기존 API 호출은 이번에 허용된 범위**다. 기존 자격 증명을 안전하게 사용하고 값은 출력하지 않는다.
- 새 모델 비교, 새 서비스 도입, 전체 계산 명세의 무검토 생성, 운영 데이터베이스 변경, 운영 배포는 하지 않는다.
- 기존 계산 로직과 지원 범위를 유지하면서 새 원문·청크와의 연결을 확인한다. 파싱 문제가 없다는 이유로 계산 명세나 모든 공종 견적을 승인하지 않는다.
- 커밋·푸시·머지·배포는 이번 작업에 넣지 않는다. 로컬에서 검토 가능한 코드와 결과를 남긴다.

## 1단계: 남은 보류 표 전체 해결

대상 목록은 최신 후보의 `out/remaining_review.json`에 있는 중복 없는 표 286개다. 사유별 표 수는 행 대응 144개, 이름 범위 81개, 번호 연결 48개, 머리글 6개, 칸 경계 1개, 68쪽 행 이름 1개, 계단선 8개다. 한 표에 여러 사유가 있어 이 수를 합하지 않는다.

- 전체 작업 목록에 표 식별자·쪽·사유·원문 근거·기대 구조·적용 교정·결과·미해결 이유를 기록한다. 같은 문제를 유형별로 묶고, 모든 해당 표를 대조한다.
- 행과 머리글을 먼저 정하고 이름·번호를 연결한다. 한 행의 줄바꿈과 별도 행, 상위 이름과 하위 이름, 공통 칸의 적용 범위를 원문으로 확정한다.
- 표의 역할을 구분한다. 정의·단위·설명 표를 억지로 계산 표로 만들지 않는다. 정상인데 보류된 표도 원문 확인 기록이 있어야 해제한다.
- 공통 규칙은 원문 근거가 있는 구조에서만 적용한다. 남은 예외는 버전이 고정된 표별 교정 자료로 마무리한다. 기준 완화나 표시 제거로 해결 수를 늘리지 않는다.
- 68쪽은 묶음 이름과 `기계실`·`옥내일반`을 나눠 각 값에 연결한다.
- 275~277쪽 8개 표는 굵은 계단선, 번호 표시, 관련 주석과 출력별 표를 함께 읽어 적용 범위를 행·열·값과 연결한다. 원문 그림만 붙이고 선 의미를 해결했다고 세지 않는다.
- 이미 복구한 표 24개, 칸 8개, 수식, 머리글·목록·설명, 행 연결 6개를 보존한다. 원문 값과 결과값을 임의로 재계산해 바꾸지 않는다.
- 원문 글자·칸과 읽기용 내용을 구분하고, 교정 전 내용과 문서 버전을 확인한 뒤에만 적용한다.

단계 완료는 286개 각각의 모든 사유가 원문 확인 또는 실제 교정으로 해결됐을 때다. 원문 자체가 모호하거나 충돌하면 구체적인 근거를 남기고 미해결로 보고한다. 추측으로 확정하지 않는다. 전체 파싱 출력을 별도 폴더에 생성한다.

## 2단계: 전체 청킹과 근거 연결

기존 `make_chunks`와 최신 `structure_export`의 기록 연결 기능을 읽고 재사용한다. 먼저 최신 기록으로 전체 청킹을 실제 실행하고 필요한 결함을 고친다. 새 청킹 기법 연구나 모델 비교로 작업을 넓히지 않는다.

- 이름·단위·값·산출 기준이 함께 이해되는 검색 단위로 묶는다. 원문 표·칸 구조는 검색용 문자열과 별도로 보관한다.
- 표 바로 앞의 `(일당)`, `(100㎡당)`, `(m당)` 같은 기준을 유지한다. 여러 행의 공통 값을 독립된 여러 값처럼 합산하지 않게 원문 칸과 적용 범위를 연결한다.
- 표의 관련 주석, 상위 절, 다음 쪽 이어짐, 원문에 명시된 참조를 근거 연결로 전달한다. 없는 참조를 만들어 넣거나 참조 전체 문서를 무조건 검색 본문에 복사하지 않는다.
- 쪽·부문·표·칸·레코드·청크 사이의 연결과 버전을 남긴다. 아직 미해결이면 불확실 상태가 사라지지 않게 전달한다.
- 청킹에서 새로 생기는 `uncertain`이나 이름 밀림도 확인한다. 파싱 보류가 해제됐다고 청킹까지 안전하다고 가정하지 않는다.
- 기존 계산 명세, 인용, 원문 그림의 옛 `chunk_id`·`table_id` 참조가 새 자료에서도 맞는지 확인한다. 내용과 원문 위치가 맞는 경우만 새 식별자로 대응한다. 번호만 비슷하다고 옮기지 않는다.
- 계산 명세의 값과 조건이 새 원문과 어긋나면 사용 가능 상태를 근거 없이 유지하지 않는다. 연결 오류를 고치고, 계산 지식 자체의 문제는 별도로 보고한다.

청크 수·식별자 중복·빈 내용·원문 연결 누락·기준과 필수 주석 전달·입력 버전 일치를 확인한다. 청크 그림으로 원문을 확인할 수 있어야 한다.

## 3단계: 실제 임베딩

현재 공통 설정은 `backend/shared/embedding_config.json`의 `studio / gemini-embedding-2 / 3072`다. 실제 환경 변수와 서비스 색인 설정도 확인해 문서·질문 모델과 차원이 같도록 고정한다. 모델 교체나 비교 실험은 하지 않는다.

기존 `pipeline/embed.py`는 `--chunks`, `--cache`, `--out`으로 별도 경로를 받을 수 있고 내용·모델·차원을 기준으로 캐시를 재사용한다. 이를 우선 활용한다.

- 먼저 소량 입력의 실제 호출 성공과 반환 벡터 수·차원을 확인한다. 자격 증명이 존재하는 것과 호출 가능 상태는 구분한다.
- 기존 벡터를 재사용하려면 모델·차원·문서 입력 해시가 정확히 같은 경우만 사용한다. 옛 청크 번호가 같다는 이유로 재사용하지 않는다. 필요하면 기존 Parquet을 읽어 안전한 캐시로 옮기는 경로를 만든다.
- 새 후보 폴더의 캐시와 Parquet에 저장한다. 캐시 상위 폴더를 준비한다. 중단 후 성공한 벡터부터 이어서 실행한다.
- 현재 studio 경로의 배치 기능을 활용한다. quota와 오류 상태를 확인하며 실행하고, 제한 우회·계정 변경·과도한 재시도는 하지 않는다.
- 최종 청크 전부에 정확히 맞는 벡터가 있어야 전체 임베딩 완료다. 누락·오래된 해시·중복 식별자·차원 불일치·비정상 벡터가 없어야 한다.
- API 호출 수, 새로 생성한 수, 재사용 수, 소요 시간, 실패와 재개 상태를 기록한다. 비밀 값이나 인증 정보가 담긴 SDK 오류 본문은 출력하지 않는다.

## 4단계: 로컬 서비스 연결과 개선 확인

먼저 현재 서비스에서 같은 질문을 실행한 기준 결과를 저장한다. 이미 운영 중인 기능과 지원 범위는 실제 코드로 확인한다. 새 데이터와 기존 데이터를 분리해 새 로컬 프로세스로 비교한다.

### 실제 코드에서 확인된 연결 주의점

- 검색은 `backend/agent/tools/search/vector.py`의 `INDEX_CONFIG`로 후보 청크와 벡터 경로를 지정할 수 있다.
- 그러나 `qa_context.py`, `select.py`, `bundle.py`는 `data/processed/chunks.all.jsonl`을 직접 읽는 부분이 있다. `source/citation.py`도 별도 청크 경로를 쓰고, `search/bm25.py`에는 좁은 청크·파싱 경로가 있다.
- **검색 색인만 바꿔서는 서비스 전체가 새 자료를 쓰지 않는다.** 검색·답변 근거·공종 선택·계산 출처·표 그림이 같은 후보 자료와 버전을 사용하도록 최소한의 공통 경로를 연결한다. 기본 운영 경로를 보존하고 후보 경로를 명시적으로 선택할 수 있게 한다.
- `get_search`, 명세 읽기, 인용·근거의 캐시는 기존 데이터를 잡고 있을 수 있으므로 후보 설정으로 새 프로세스를 시작하고 실제로 사용한 경로·버전을 기록한다.
- 계산 명세의 `source`와 옛 ID 대응, 원문 표 그림·인용 출력을 확인한다. 새 파싱 구조와 기존 원문 그림 생성기의 인터페이스 차이도 처리한다.
- 새 색인이 실패해 BM25 대체로 바뀌면 벡터 검색 성공으로 보고하지 않는다. 실제 검색 방식과 대체 이유를 기록한다.
- 의도 분기와 기존 기능 플래그를 확인한다. 설정 하나로 실제 응답 경로가 바뀌는지 확인하고, 인증·사용량 차감·기능 공개 정책을 임의로 바꾸지 않는다.

### 오늘 확인할 사용자 질문

최소 아래 질문의 기존 결과와 개선 후 결과를 비교한다. 실행 전에 기대 동작을 기록하고 실제 원문과 지원 명세를 기준으로 판단한다.

1. `콘크리트 관련 품셈 기준 있어?` — 목록 질문에 계산 명세 없음 오류로 종료하지 않고 관련 공종과 근거를 안내.
2. `펌프차 할증 기준이 뭐야?` — 조건·주석과 원문 근거를 전달. 할증 수치를 추측하지 않음.
3. `콘크리트 타설 1㎥ 품 알려줘` — 관련 공법을 찾고 필요한 선택을 안내. 무관한 도로 포장이나 다른 부문으로 잘못 연결되는지 확인.
4. `철근콘크리트 펌프카 타설 100루베 견적` — 입력에 이미 있는 물량·공법을 다시 묻지 않고 필요한 조건만 요청. 검증된 명세가 있을 때 기존 계산과 근거가 유지되는지 확인.
5. `교량 견적: 콘크리트 타설 300㎥, 거푸집 500㎡, 철근 가공조립 20톤` — 실제 구현된 여러 공종 흐름에서 항목이 섞이지 않는지, 지원·미지원과 합산·가정을 구분하는지 확인.

추가로 기존 `evals/rag_questions.json`의 관련 검색·근거 사례와 이번에 고친 기준 누락·501쪽 일수·502쪽 식·68쪽 이름·275~277쪽 적용 조건을 확인한다. 모든 표가 검색 상위에 나오도록 억지로 단어를 넣지 않는다. 검색 대상과 근거 확장을 구분한다.

검색·근거 조립·대화 분기 때문에 위 질문이 실패하면 해당 경로를 필요한 범위에서 고치고 재확인한다. 임베딩 파일 생성만으로 서비스 개선이 확인됐다고 보고하지 않는다. 기존 계산 결과·단위·Excel 출처가 달라졌다면 원인을 원문으로 확인한다.

로컬 API 서버를 실제로 띄워 응답을 확인한다. 필요한 경우 프론트도 연결해 질문과 원문 링크를 확인한다. 인증·과금 등 외부 상태를 바꾸는 검사는 피하고 기존 로컬 테스트 경로를 사용한다. 모의 벡터만 쓰거나 그래프 함수만 호출한 결과를 실제 임베딩·서비스 확인으로 표현하지 않는다.
