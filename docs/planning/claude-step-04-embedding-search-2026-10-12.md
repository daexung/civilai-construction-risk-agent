## 1. 준비와 실제 토큰 확인

기존 제공자·모델·차원·인증 방식과 캐시를 확인한다. 기준은 기존 계획의 Gemini 설정이며 실제 코드와 사용 가능한 계정 설정을 먼저 확인한다. 모델 변경이나 새 유료 계정 생성은 하지 않는다. 모델 한도·입력 형식·현재 가격은 제공자의 공식 문서로 확인하고 출처와 날짜를 남긴다.

사용자 후속 지시: `GEMINI_API_KEY`와 `GEMINI_API_KEY_SEC`를 둘 다 사용한다. 공통 `backend/shared/embedding.py`에 요청마다 두 키를 번갈아 사용하고 429 오류 시 다른 키로 한 번 이어가는 경로를 추가했다. 임베딩 어댑터도 이 공통 경로를 재사용한다. 두 키 값이 같으면 하나로 취급한다. 같은 프로젝트의 키는 한도를 공유할 수 있으므로 두 배 한도라고 가정하지 않는다. 두 키 모두 제한되면 기존 재시도·캐시 재개 규칙을 따른다. 키 이름만 기록하고 값은 출력하지 않는다.

기존 청킹 토큰 수는 글자 수 기반 추정이다. 현재 모델이 지원하는 토큰 계산 경로를 확인한다. 가장 긴 조각을 포함해 최종 포장된 입력이 한도를 넘거나 조용히 잘리는지 확인한다. 실제 토큰을 확인하지 못하면 추정이라고 표시하고 확인 가능한 API 동작과 한계를 기록한다. 한도 초과가 발생하면 해당 입력을 별도 실패 목록에 남기고 청킹을 임의 변경하지 않는다.

호출 전 전체 대상 수, 재사용 가능한 캐시 수, 예상 토큰·비용·요청 횟수를 기록한다. 이 지시 범위는 기존 설정으로 문서 임베딩과 평가 질문 임베딩을 실행하는 것이다. 같은 입력의 불필요한 반복 유료 호출을 하지 않는다. 키·결제·권한이 없으면 필요한 정보를 구체적으로 보고하고 호출 없이 할 수 있는 구현·검사는 진행한다. 비밀값은 로그나 보고서에 출력하지 않는다.

## 2. 소량 확인 후 전체 임베딩

길이·종류가 다양한 32개 조각으로 먼저 실제 호출한다. 입력과 출력 수 일치, 순서, 차원, 유한값·0벡터, 응답의 잘림 표시, 캐시 재실행을 확인한다. 캐시 검사 때문에 같은 입력을 다시 호출하지 않는다. 성공하면 나머지 전체 대상까지 이어서 생성한다.

기존 `pipeline/embed.py`를 재사용하거나 얇은 어댑터로 새 청크 형식에 연결한다. 기존 파이프라인은 `source`, `section_no` 같은 필드를 요구하므로 형식 차이를 실제로 확인한다. 단순히 새 파일 경로만 넣고 호환된다고 가정하지 않는다. `zip`이 출력 부족을 숨기지 않게 벡터 수를 먼저 검사한다.

벡터와 캐시를 기존 서비스 자료에 덮어쓰지 말고 청킹 묶음·모델·입력 형식 버전별 경로에 저장한다. 캐시 키에는 실제 입력 해시, 제공자·모델·차원·입력 형식과 문서/질문 용도를 포함한다. 문서와 질문에 같은 임베딩 공간을 사용한다. 성공분은 즉시 보관하고 실패는 유한한 재시도 후 기록한다. 중단·재개 시 성공분을 재호출하지 않는다.

모든 검색 대상의 벡터 대응과 입력 해시가 맞을 때만 색인을 준비 완료로 표시한다. 보류·미확정 조각도 검색할 수 있지만 상태를 그대로 유지한다. 일부 제외나 실패를 숨겨 전체 5,764개 완료라고 보고하지 않는다. 원문과 벡터 버전 혼용을 거부한다.

## 3. 결합 검색과 근거 조회 연결

기존 BM25·벡터 검색·RRF를 기준으로 새 청크에 적용한다. 세 종류 `work/rule/table`을 하나의 논리 색인에서 검색하고 질문 유형만 보고 하나를 강제로 제외하지 않는다. 같은 원문에서 파생된 조각의 중복을 조절하되 서로 다른 공종이나 조건을 합치지 않는다.

첫 설정은 각 검색의 후보 20개다. 후보 누락이 개발 질문에서 확인되면 50개 설정을 한 번 비교할 수 있다. 숫자·단위는 원문에서 유지하고 검색용 정규화만 따로 한다. 새로운 모델·재순위·그래프 도구 도입은 이번 기본 경로가 평가된 뒤 별도 제안한다.

검색 결과를 `Reader.read`로 연결한다. 원문·청크·벡터의 버전을 확인하고 출처와 미확정 상태를 그대로 반환한다. 질문별로 최대 2회 추가 검색을 지원할 수 있으나 호출·검색 기록을 남긴다. 적용 여부를 답변 모델 없이 억지로 확정하지 않는다.

상위 묶음 참조 24건은 3단계에서 하위 절 목록만 반환한다. 이번에는 필요할 때 그 목록 안의 하위 절을 질문으로 검색하는 제한 경로를 구현한다. 후보 여러 개와 선택 사유를 유지한다. 전체 하위 절을 무조건 붙이거나 한 절을 적용 확정으로 선택하지 않는다. 필요한 절을 못 고르면 미해결로 보고한다.

목록 질문은 여러 공종의 후보와 근거를 유지한다. 단일 견적 질문에서 다른 공법의 값을 섞지 않는다. 소속 미확정 설명·수식·보류는 정상 계산값으로 사용하지 않는다. 이번 결과는 근거 검색 결과이며 최종 견적 계산 승인이나 답변 정확도는 아니다.

## 4. 평가: 개발과 독립 확인 구별

기존 20문을 개발·회귀로 사용한다. 기존 자료와 평가 코드를 재사용한다. 비교할 기존 입력이 없다면 없는 비교를 만들지 말고 가능한 비교 범위를 명시한다. 같은 새 자료에서 키워드만, 벡터만, 결합 검색을 비교하고 근거 누락의 원인을 구별한다.

새 20문은 구현 조정에 쓰지 않는다. 최종 설정과 코드 해시를 고정한 뒤 한 번 평가한다. 실패를 보고 수정했다면 그 질문은 개발 사례가 되며 이후 결과를 독립 평가라고 부르지 않는다. 실패 결과도 보존한다. 자료 없음·보류·여러 공법 질문에는 억지 정답 공종을 지정하지 않는다.

질문별 정답 후보 Recall@5, 필수 근거 포함·제외, 잘못된 공종·부문·수치·조건, 후보 선택과 근거 조회의 실패 구분, 미확정 표시를 보고한다. 근거 완성은 `coverage.complete`만으로 판단하지 말고 사전 필수 근거 목록과 실제 내용을 비교한다.

계획의 초기 목표는 정답 있는 질문의 공종 Recall@5 90% 이상, 원문으로 확인 가능한 질문의 필수 근거 완성률 95% 이상, 중요 수치·조건 오류 0이다. 분모와 건수를 함께 보고한다. 해석 보류 질문을 몰래 분모에서 빼지 말고 별도 집계한다. 목표 미달이면 결과와 원인을 보고하고 서비스 연결을 자동 시작하지 않는다.

검색·조회 시간은 API 시간과 분리해 중앙값·p95를 측정한다. 벡터 수·용량·실제 최대 메모리, 새 호출·캐시 재사용·실패 수와 실제 또는 추정 비용을 기록한다. 작은 표본 성적을 전체 문서 정확도로 표현하지 않는다.

## 결과물과 종료

버전별 벡터 Parquet·캐시·검색 설정·실제 입력 해시·평가 결과와 재개 명령을 보관한다. 원문·청킹 결과 폴더와 과거 검사 기록을 덮어쓰지 않는다. 검사 기록은 별도 실행 폴더에 저장하고 해시 일치를 확인한다. 고정 사례로 기존 근거 조회와 데이터 보존도 회귀 확인한다.
