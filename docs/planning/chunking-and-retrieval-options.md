# 품셈 청킹과 근거 검색 후보 비교

작성일: 2026-10-10  
기준 코드: `baf186f`  
상태: 조사와 기획. 후보별 실제 품질 비교는 아직 하지 않았다.

## 1. 권장 방향

파싱 비교는 계속한다. 청킹은 **표 구조를 보존하는 분할 + 부모·자식 검색 + 원문에 명시된 참조 연결 + 검색용 문맥 정보**를 우선 후보로 삼는다.

이 네 가지는 서로 다른 역할이므로 함께 사용할 수 있다. 새로운 라이브러리 하나로 모든 문제를 해결한다고 가정하지 않는다. 실제 채택은 작은 비교 실험 결과로 결정한다.

현재 작업은 기획 문서 작성까지만이다. 코드·설정·데이터 변경, 패키지 설치, 운영 접속, LLM·임베딩 API 호출은 포함하지 않는다. 이후 구현이나 실험은 별도 지시서로 범위를 정한다.

## 2. 지금 해결하려는 문제

사용자는 짧게 묻지만, 올바른 답에는 여러 근거가 필요하다. 표의 숫자만 찾으면 단위나 적용 조건을 놓칠 수 있고, 해당 절만 찾으면 다른 절을 따르라는 주석을 놓칠 수 있다.

최근 육안 비교에서 확인한 사례는 다음과 같다. 자세한 기록은 [페이지 비교 결과](../reviews/parsing-page-185-findings.md)에 있다.

- 표 안의 작은 표가 평평한 문자열로 바뀌면서 조건과 값의 연결이 깨진다.
- 장비사용 타설의 공동 작업량 63/55가 적용되는 범위를 보존해야 한다. 빈칸이나 대시를 무조건 윗값으로 채우는 방식은 위험하다.
- 6-1-1에서 6-1-3 표면 마무리를 참조하는 문장이 있다. 참조의 적용 조건까지 함께 읽어야 한다.
- 추출 상태 표시가 원문과 섞이면 사람이 결과를 비교하기 어렵다.

파싱은 글자·셀·병합 범위를 제대로 복원하는 일이다. 청킹과 근거 검색은 복원된 내용 중 무엇을 검색 대상으로 만들고, 답변 전에 무엇을 함께 가져올지 정하는 일이다. 청킹으로 빠진 숫자를 복원할 수는 없다.

## 4. 후보를 구분하는 세 가지 질문

1. **어디에서 나눌까?** 글자 수, 절, 표, 행 묶음, 설명 항목 등 분할 경계를 정한다.
2. **찾은 뒤 무엇을 함께 가져올까?** 부모 문서, 연결된 주석, 참조 절을 모은다.
3. **검색할 때 어떤 문맥을 표시할까?** 연도·부문·공종·조건 정보를 검색용 표현에 붙인다.

부모·자식 방식과 그래프 연결은 두 번째 질문에 대한 답이다. 의미 기반 청킹은 첫 번째 질문에 대한 답이다. 같은 기능의 대체재로 비교하면 판단이 흐려진다.

구조 기반 분할의 사례로 Docling은 문서 구조 위에 토큰 길이 조정을 적용하고, 나뉜 표에 머리글을 반복하는 옵션을 제공한다. 다만 이 기능이 품셈의 병합 셀이나 주석 연결을 정확히 복원한다는 보장은 없다. Unstructured도 문서 요소를 활용하되 너무 큰 요소는 다시 나눈다. [Docling 공식 문서](https://docling-project.github.io/docling/concepts/chunking/), [Unstructured 공식 문서](https://docs.unstructured.io/open-source/core-functionality/chunking)

부모·자식 검색은 작은 조각을 찾고 부모 식별자로 더 큰 문서를 가져오는 패턴이다. 부모를 반드시 절 전체로 정할 필요는 없다. [LangChain 공식 구현](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain_classic/retrievers/parent_document_retriever.py)

의미 기반 분할의 한 구현은 문장 주변의 임베딩 거리와 경계값을 이용한다. 이는 표의 논리 구조를 보존하는 검사와는 다른 기능이다. [LangChain SemanticChunker 구현](https://github.com/langchain-ai/langchain-experimental/blob/main/libs/experimental/langchain_experimental/text_splitter.py)

Anthropic의 Contextual Retrieval은 LLM이 조각별 설명을 만들고 검색 입력에 붙이는 방식이다. 여기서는 먼저 원문에서 추출한 문맥 정보를 일정한 형식으로 붙이는 단순한 변형을 제안한다. 같은 방식이라고 부르거나 공개 성능 수치를 이 서비스의 예상 개선율로 사용하지 않는다. [Anthropic 공식 설명](https://www.anthropic.com/engineering/contextual-retrieval)

자동 병합의 공식 예시는 부모를 공유하는 자식 검색 결과가 경계 비율을 넘으면 합치는 방식이다. 필수 주석은 이 판단과 별도로 붙여야 한다는 것이 이 기획의 권고다. [LlamaIndex 공식 문서](https://developers.llamaindex.ai/python/framework/integrations/retrievers/auto_merging_retriever/)

Late Chunking은 긴 입력을 처리한 뒤 조각별 벡터를 만드는 연구이고, RAPTOR는 임베딩·군집·요약을 반복하여 트리를 만드는 연구다. 둘 다 품셈에 대한 검증 결과는 이번 조사에서 확보하지 못했다. [Late Chunking 논문](https://arxiv.org/abs/2409.04701), [RAPTOR 논문](https://arxiv.org/abs/2401.18059)

Microsoft GraphRAG의 표준 색인 과정은 개체·관계 추출과 여러 수준의 요약을 포함한다. 이 기획의 원문 참조 연결은 그 전체 구성을 도입하자는 뜻이 아니다. [공식 색인 설명](https://microsoft.github.io/graphrag/index/overview/), [공식 검색 설명](https://microsoft.github.io/graphrag/query/overview/)

## 7. 최종 구조 후보

### 7.1 원문 보관과 검색 표현을 분리한다

원문 보관에는 표의 셀·행·열·병합 범위, 제목, 단위와 산출 기준, 주석, 원문 위치를 남긴다. PDF 쪽과 인쇄 쪽도 구분한다. 숫자와 적용 범위가 불확실한 부분은 별도 상태로 표시한다.

검색용 조각은 이 원문을 가리키는 작은 표현이다. 검색을 위한 반복 머리글이나 문맥 설명을 붙일 수 있지만, 원문의 숫자·문장을 덮어쓰지 않는다. 둘을 분리하면 청킹 방식을 바꾸어도 파싱을 다시 할 필요가 줄어든다.

식별에는 문서 버전·연도·부문·절·표·조각을 함께 사용한다. 절 번호만으로 연결하지 않는다. 파서가 바뀌면 표 식별자가 바뀔 수 있으므로 원문 위치와 이전 결과의 대응 관계도 남긴다.

### 7.2 표는 직종 한 행보다 작업 조건이 완결되는 묶음을 우선한다

작은 표는 통째로 검색할 수 있다. 큰 표는 같은 공법·조건·공동 작업량을 공유하는 행 묶음으로 나누는 안을 비교한다. 각 묶음에는 필요한 머리글·단위·기준을 반복한다.

예를 들어 공동 작업량 63/55를 쓰는 인력·장비 묶음을 직종별로 분리하면 숫자가 어느 작업 전체에 적용되는지 잃을 수 있다. 검색 표현에 값을 반복하더라도 원문에서는 하나의 공동 값과 적용 범위로 보관한다. 반복된 값을 합산해선 안 된다.

모든 셀이나 모든 행을 독립 청크로 만들지는 않는다. 반복되는 '철근공'만으로 서로 다른 공종을 한 묶음으로 연결하지도 않는다.

### 7.3 부모는 필요한 근거의 묶음이다

검색 결과에서 표 또는 행 묶음을 찾으면 다음을 가져오는 안을 제안한다.

- 해당 표의 필요한 머리글·단위·기준과 작업 조건
- 그 표에 적용되는 주석과 설명
- 적용 범위가 확인된 상위 공통 기준
- 원문이 참조하는 다른 절의 필요한 부분

절 전체를 보관하더라도 매번 전부 전달하지 않는다. 주석이 어느 표에 적용되는지 모르면 가까운 표에 임의로 붙이지 않고 미확정 관계로 남긴다. 근거 예산을 넘으면 완결된 묶음 단위로 처리하거나 추가 조회한다. 필수 조건을 중간에서 잘라 계산을 계속하지 않는다.

### 7.4 연결은 종류와 조건을 가진다

| 연결 종류 | 용도 | 처리 원칙 |
|---|---|---|
| 소속 | 조각 → 표 → 소절 → 절 | 문서 계층을 복원한다 |
| 주석 적용 | 주석 → 표 또는 행 묶음 | 범위가 확인된 경우 함께 가져온다 |
| 참조 | 특정 문장 → 다른 절 | 참조 문장과 대상 위치를 보존한다 |
| 조건부 적용 | 조건 → 따를 규칙 | 조건이 충족되는지 별도 판단한다 |
| 제외·별도 계상 | 작업 → 포함 범위 또는 추가 작업 | 검색 후 확인한다. 연결만으로 금액을 자동 추가하지 않는다 |

명시된 절 번호와 문서 구조는 일반적인 추출 규칙으로 처리할 수 있다. 관계 종류와 조건의 의미는 어려운 경우가 있으므로 자동 검증, 미확정 표시, 예외 검토가 필요하다. 공종마다 사람이 처음부터 설정하는 운영을 목표로 하지는 않는다.

관계에는 출발 위치·대상 식별자·종류·조건 원문·확정 상태를 남긴다. 대상 누락·부문 모호함·연도 불일치·순환을 검사한다. 처음에는 파일이나 기존 저장소에 관계를 보관해도 되며 그래프 전용 데이터베이스가 필수는 아니다.

6-1-1 → 6-1-3 관계에서는 참조 대상이 검색되었다는 것과 실제 견적에 표면 마무리를 추가해야 한다는 것을 구분한다. 조건이 불명확하면 관련 문장은 가져오되 계산 적용은 보류한다.

### 7.5 질문에 따라 가져올 범위를 바꾼다

| 질문 | 우선 검색 대상 | 추가로 필요한 근거 |
|---|---|---|
| 관련 기준 목록 | 절 제목·적용 범위·공법 정보 | 후보별 짧은 근거. 계산 명세 유무와 목록 제공을 분리 |
| 할증 등 기준 설명 | 해당 주석·규칙 문장 | 대상 표·단위·참조 규칙 |
| 단위 품 | 조건에 맞는 표 또는 행 묶음 | 기준 물량·단위·적용 조건·계산 규칙 |
| 단일 견적 | 공종 후보와 계산 근거 | 입력 조건·단가·계산 이력 |
| 여러 공종 견적 | 항목별 공종 후보와 근거 | 공통 근거를 중복 없이 모으고 항목별 적용을 기록 |

검색과 근거 조립은 계산의 재료를 준비한다. 견적 상태 관리, 단가 관리, 정확한 산식 실행과 여러 공종의 합산은 별도 책임이다. 청킹 개선만으로 다공종 견적이 완성되지는 않는다.

## 8. 비교 실험은 네 가지 조합으로 제한한다

### 8.1 파싱 비교와 청킹 비교의 원인을 분리한다

파서마다 같은 페이지를 복원해 원문 구조의 정확성을 먼저 비교한다. 청킹 비교에서는 하나의 고정된 파싱 결과를 공통 입력으로 쓴다. 각 파서에 각 청킹 후보를 전부 곱한 대규모 실험으로 시작하지 않는다.

현재 운영 파이프라인의 결과는 별도 기준선으로 보관한다. 개선된 파싱 결과를 쓰는 후보의 이득 전체를 청킹의 이득으로 계산하지 않는다.

| 조합 | 내용 | 확인할 효과 |
|---|---|---|
| 가 | 같은 파싱 결과로 표·설명 항목을 나누고 현재 수준의 제목 정보를 붙임 | 구조 기반 공통 기준선 |
| 나 | 가 + 부모·자식 방식으로 표의 조건과 주석을 모음 | 같은 표·소절의 근거 누락 감소 |
| 다 | 나 + 명시적 참조 연결 | 다른 절의 필수 근거 누락 감소 |
| 라 | 다 + 원문에서 얻은 추가 검색 문맥 | 반복 직종명·짧은 질문의 공종 구별 개선 |

처음부터 의미 기반 청킹, 새 임베딩 모델, 재순위 모델까지 함께 바꾸지 않는다. 라이브러리 기본 크기를 최적 크기로 가정하지도 않는다. 조합을 좁힌 뒤 큰 표의 분할 크기를 소수 설정으로 비교한다.

### 8.2 기존 평가 초안을 재사용한다

기존 질문 초안에서 약 20개를 먼저 골라 다섯 질문 유형과 아래 오류 유형을 포함한다. 조정에 쓰는 사례와 방법을 정한 뒤 처음 확인할 사례를 구분한다. 이미 육안으로 본 페이지와 시제품 개발에 쓴 사례는 새로운 확인 사례로 부르지 않는다.

- 같은 직종명이 여러 절에서 반복되는 경우
- 여러 단계 머리글·병합 셀·공동 작업량
- 표 안의 표와 조건별 계수
- 다음 페이지로 이어지는 표·주석
- 다른 절을 따르는 조건부 참조
- 별도 계상과 제외 범위
- 여러 공종이 포함된 질문

기대 답안 전체보다 먼저 **반드시 함께 있어야 하는 원문 위치의 묶음**과 **적용하면 안 되는 근거**를 지정한다. LLM이 만든 평가 초안은 검토 상태를 표시한다. 실무자 검토가 당장 없으면 원문 대조로 확정할 수 있는 부분과 해석이 필요한 부분을 나누어 평가한다.

### 8.3 측정 항목

| 항목 | 확인 내용 |
|---|---|
| 공종 후보 정확성 | 정답 절이 후보에 있는지, 무관한 공종이 상위를 차지하는지 |
| 근거 묶음 완성률 | 필요한 표·단위·주석·참조 규칙을 모두 가져왔는지 |
| 잘못된 연결 | 다른 표의 주석, 조건에 맞지 않는 참조를 붙였는지 |
| 구조 보존 | 머리글·공동 값·단위·조건이 분할 후에도 연결되어 있는지 |
| 근거 추적 | 반환한 문장과 숫자를 원문 위치까지 확인할 수 있는지 |
| 문맥 크기와 중복 | 제공한 길이와 동일 근거의 반복량 |
| 응답 시간 | 이후 실제 검색과 답변에서 중간값·느린 구간을 함께 측정 |

검색 방식·후보 수·재순위 여부를 고정한다. 같은 문맥 예산에서 품질을 비교하고, 예산을 늘렸을 때 얻는 품질과 지연도 별도로 보여준다. 단순히 더 많이 넣은 후보의 점수가 높다고 최선으로 판정하지 않는다.

API 금지 상태에서는 분할 구조·관계 검증·근거 조립·오프라인 키워드 검색까지 검사할 수 있다. 고정된 검색 시작점을 넣는 검사도 가능하지만 이는 검색 성능 검사가 아니다. 새 조각의 벡터 검색 품질, 실제 LLM 답변 정확성, 전체 응답 시간은 이후 API 사용이 허용된 비교에서 확인해야 한다.

### 8.4 통과 기준

- 비교 대상에서 확인된 숫자·단위·공동 값의 적용 범위 오류를 숨기지 않는다.
- 부모 확대가 필수 주석 누락을 줄이는지 사례별로 설명한다.
- 참조 확대가 필요한 근거를 추가하면서 부적절한 규칙을 적용하지 않는지 확인한다.
- 모든 근거의 원문 위치와 가져온 이유를 보여준다.
- 개발 사례와 처음 확인한 사례의 결과를 따로 보고한다.
- 검증 범위 밖의 정확성이나 품셈 전체 적용을 주장하지 않는다.

## 9. 진행 순서와 완료 기준

| 순서 | 할 일 | 완료 기준 |
|---|---|---|
| 1 | 파싱 비교를 진행하면서 표·주석·원문 위치의 공통 보관 형식을 정한다 | 동일 페이지를 후보별로 육안 비교할 수 있고, 알려진 공동 값·주석 문제가 구분되어 있다 |
| 2 | 고정된 파싱 입력으로 구조 기반 조각을 만든다 | 작은 표·큰 표·설명 항목을 원문과 나란히 볼 수 있고 머리글·단위·근거를 잃지 않는다 |
| 3 | 부모·자식 근거 조립을 비교한다 | 나 조합이 가 조합보다 무엇을 개선했는지 필수 주석 누락과 문맥 크기로 제시한다 |
| 4 | 명시적 참조 연결과 추가 문맥 정보를 각각 비교한다 | 다·라 조합의 추가 효과와 잘못된 연결을 분리하여 제시한다 |
| 5 | 선택한 조합의 전체 검색·답변을 확인한 뒤 적용 범위를 넓힌다 | 허용된 환경에서 질문별 검색·근거·계산 이력과 지연을 확인하고, 연도 개정 시 연결 재검증 절차를 갖춘다 |

## 10. 가장 큰 위험

가장 걱정되는 것은 보기 좋은 구조가 잘못된 의미 연결을 숨기는 일이다. 숫자가 존재하고 표가 읽기 좋다는 이유만으로 계산에 안전하다고 판정할 수 없다. 공동 값의 범위와 조건부 참조를 검증해야 한다.

두 번째는 너무 많은 문맥을 가져오는 일이다. 다른 절을 많이 읽는다고 더 정확해지는 것은 아니다. 필수 근거와 선택적 참고를 구분하고, 여러 단계 참조가 예산을 넘으면 불완전 상태를 명시해야 한다.

세 번째는 매년 개정 시 식별자와 연결이 바뀌는 일이다. 이전 연도의 관계를 그대로 재사용하지 않고 문서 버전·원문 변경·참조 대상의 존재를 다시 검사해야 한다.

## 11. 사용자에게 제안하는 다음 결정

파싱 도구 비교를 중단하거나 전체 서비스를 다시 만들 필요는 없다. 지금은 이 문서의 네 조합을 비교 대상으로 정하고, 먼저 같은 페이지에서 **검색 조각과 실제 전달 근거를 나란히 보여주는 결과물**을 만들도록 다음 실험을 준비한다.

사용자가 확인할 핵심은 세 가지다. 표의 뜻이 유지되는가, 필요한 주석과 참조 절이 붙는가, 무관한 내용이 과하게 섞이지 않는가. 그 결과가 나온 뒤 라이브러리와 청킹 방식을 선택한다.
