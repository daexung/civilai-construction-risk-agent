# 품셈이 운영자 대시보드 초안

작성일: 2026-10-14. 상태: 데이터 경로 확인과 설계 초안. 기능 우선순위와 관리자 계정을 사용자에게 질문했다. 운영 권한은 아직 부여하지 않았다.

확정한 접근 구조: 사용자가 Vercel 관리자 화면 → 기존 GCP 백엔드 → Supabase 구성을 수락했다. GCP 서버 간 인증과 관리자 사용자 인증은 별도이며, 모든 관리자 API에서 서버가 검증한 사용자 UUID를 허용 목록과 대조한다. 관리자 설정이 없으면 기본 차단한다. 비로그인·일반 회원은 관리자 자료를 받지 못하게 하고, 서비스 키는 서버에만 둔다. 관리자 응답은 공유 캐시에 저장하지 않는다. 정확한 관리자 계정과 첫 기능 범위는 아직 미확정이며 실제 권한 설정·대시보드 구현은 진행하지 않았다.

## 목표

운영자가 복잡한 분석 도구와 SQL 화면을 오가지 않고 방문·사용 현황, 사용자 평가, 에이전트 실행 문제를 한 화면에서 확인한다. 초기 권장 범위는 통계 요약·평가 검토·실행 조회다. 상담 화면과 분리된 `/admin` 경로를 기존 React 앱에 추가한다.

## 확인한 현재 자료

- `frontend/src/analytics.ts`는 PostHog로 방문, 질문 전송, 견적 내려받기, 일반 의견 제출, 답변 평가 이벤트를 전송한다. 수집 거부와 DNT를 존중한다.
- PostHog 이벤트에는 질문·답변 원문, 회원 ID, 이메일, 유입 주소와 검색어를 넣지 않는다. 기존 수집 자료로 회원별 행동이나 Google·네이버 유입 검색어를 복원할 수 있다고 가정하지 않는다.
- Supabase에 `conversations`, `messages`, `feedback`, `answer_feedback`이 있다. 비회원 전체 대화는 DB에 보관되지 않으므로 messages 건수로 전체 질문 수를 계산하면 누락된다.
- `answer_runs`, `answer_run_steps`와 평가 연결 컬럼은 로그 작업 PR #36에서 구현되어 로컬·운영에 반영된 상태다. 구체적인 필드와 보관·삭제 동작은 `docs/operations/answer-run-feedback.md` 및 로그 생명주기 확인 문서를 기준으로 재사용한다. 대시보드에서는 과거 실행 시각·단계·버전을 추측해 만들지 않는다.

## 첫 화면의 권장 구성

| 영역 | 표시 내용 | 자료와 정의 |
|---|---|---|
| 이용 요약 | 방문 브라우저 수·페이지 조회·질문 전송·엑셀 내려받기 | PostHog 기존 수집을 서버에서 요약 조회. 방문 브라우저 수를 실제 사람 수로 표시하지 않음 |
| 상담 처리 | 완료·실패·미완료, 응답 시간 | 운영 answer_runs. API·노드 실행 성공을 답변 정답률로 표시하지 않음 |
| 사용자 의견 | 새 제보·나쁨 평가·검토 상태 | feedback와 answer_feedback. 평가 비율에 평가 수와 분모 표시 |
| 실행 상세 | 노드·도구·모델 단계, 선택 근거, 오류 | answer_run_steps와 연결된 실행. 수집 불완전 표시 유지 |
| 검토 | 오류 유형·검토 메모·올바른 근거·평가 사례 승인 | 로그 담당 작업의 검토 컬럼과 내보내기 규격 재사용 |
| 비용 | 확인된 토큰·사용량과 비용 추정 | 확인한 기록만 사용. 미수집 비용은 0원이 아니라 미확인 |

초기 화면에는 기간 선택(오늘·7일·30일), 이용 추이, 검토 대기 목록, 최근 오류를 배치한다. 제보를 열면 해당 답변과 실행 단계로 이동한다. 수집 자료가 없으면 0건, 연결 자체가 안 됐거나 조회가 실패하면 미연결·오류로 구별한다. 기본 시간대는 한국 시간이다.

## PostHog와 자체 수집의 구별

사용자가 불편하다고 한 분석 화면을 대신하는 자체 대시보드는 기존 PostHog 수집을 유지하면서도 만들 수 있다. 초기 권장안은 서버 전용 PostHog 조회 어댑터와 Supabase 조회를 결합해 기존 통계를 보존하는 것이다. PostHog 개인 API 키를 프론트에 넣지 않는다. 기존 공개 수집 키가 서버의 통계 조회 권한을 뜻하지는 않는다.

사용자가 PostHog 수집까지 없애길 원하면 별도 전환 범위로 확정한다. 그때는 Supabase에 최소한의 사이트 이벤트 수집 경로를 추가하고, 익명 브라우저·세션 식별, 수집 거부, 봇·중복 처리, 제한·보관 정책을 정의해야 한다. 기존 PostHog 방문 통계가 자동으로 Supabase에 생긴다고 가정하지 않는다. 자체 수집이 동작하는지 확인한 뒤 기존 수집을 종료한다.

Google·네이버 검색 성과는 각 검색엔진의 별도 자료다. PostHog나 실행 로그만으로 검색 노출·순위·검색어를 만들어 표시하지 않는다. 초기에는 검색 관리 화면 링크만 제공한다.

## 접근 구조

운영자 Google 로그인 → 기존 Supabase 인증 검증 → 백엔드의 운영자 계정 확인 → 전용 집계·상세 API → 운영 화면.

- 운영자 계정은 사용자에게 정확한 이메일을 확인한 뒤 실제 인증 계정의 UUID로 제한한다. 현재 브라우저의 Google 계정을 자동으로 운영자로 정하지 않는다.
- 모든 운영 API에서 서버가 권한을 확인한다. 화면의 버튼을 숨기는 것만으로 보호하지 않는다.
- DB 연결과 서비스 역할 키는 백엔드에만 둔다. 기존 로그 테이블을 일반 authenticated 역할에 공개하지 않는다.
- 관리자 경로와 응답은 검색 제외·개인 캐시 금지로 처리한다. 비로그인 접근과 다른 회원의 접근을 각각 확인한다.
- 질문·답변 상세는 필요한 목록을 선택할 때만 제공한다. 통계 목록은 본문을 포함하지 않는다. 검토 수정에는 운영자 식별자와 시각을 기록하고 기존 검토·승인 규칙을 지킨다.

## 구현 순서

1. 사용자 우선 기능과 PostHog 수집 유지/전환 범위를 확인한다. 운영자 계정이 정해지기 전에는 접근을 기본 차단한다.
2. 로그 담당 작업의 스키마·조회 규격과 운영 반영 상태를 확인한다. 그 작업 파일을 덮어쓰지 않고 별도 작업에서 진행한다.
3. 운영자 인증, 서버 집계·목록·상세 API와 읽기 중심 화면부터 만든다. 기존 자료만으로 확인 가능한 항목을 우선 제공한다.
4. 검토 기록 저장과 평가 사례 승인·내보내기를 기존 경로에 연결한다. 자동 학습이나 자동 배포는 추가하지 않는다.
5. 권한·기간·집계 중복·비회원 누락·자료 없음·조회 실패를 검사하고, 대표 데이터로 대시보드 수치와 DB 조회 결과를 대조한다.
6. 배포 전 확인한 운영자 계정만 허용하고, 일반 상담과 새 홈페이지 사전 렌더링에 영향이 없는지 확인한다.
