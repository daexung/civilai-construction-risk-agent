2026-10-10 추가 조사 반영: [실무 사례 조사](structural-chunking-practice-research.md)에 따라 공종 목록·규칙·표의 검색 표현을 구분한다. 짧은 절은 전체 부모 문맥을 우선 비교하고, 근거 조회 도구의 응답 형식을 데이터 설계와 함께 정한다.

## 목표와 현재 판단

표를 제대로 읽는 것에서 한 단계 더 나아가, 질문에 답할 때 숫자·단위·조건·주석·참조 절을 함께 확인할 수 있게 한다. 그 위에서 목록·설명·품·견적·여러 공종 견적의 대화 흐름을 개선한다.

ODL + 기존 후처리를 데이터 개선의 우선 후보로 둔다. 185쪽에서 보았던 값 누락과 작은 표 연결은 개선되었다. 다른 형태의 표와 전체 품셈에 대한 검증이 끝난 것은 아니다.

먼저 데이터 보관과 근거 검색을 정비한다. 이후 에이전트의 질문·조건 반영·계산 행동을 정비한다. 파서 이름만 바꾸거나 청크 크기만 바꾸는 작업으로 보지 않는다.

## 전체 흐름

원문 PDF → ODL 표 추출과 후처리 → 원문 구조 보관 → 검색용 조각 → 필요한 근거 조립 → 에이전트 → 계산기 → 견적·Excel

원문 구조 보관과 검색용 조각은 분리한다. 검색하기 좋게 반복한 숫자나 제목이 원문의 독립 값으로 오인되지 않게 한다. 계산기는 근거가 확인된 계산 명세와 입력을 사용하며, 검색된 문장만으로 산식을 새로 만들어 실행하지 않는다.

## 1단계: 적재 스키마의 초안을 정한다

적재 스키마는 복원된 자료를 저장하는 약속이다. 이번에는 데이터베이스 제품 선택보다 무엇을 보존해야 하는지를 먼저 정한다.

### 보관 대상

| 대상 | 필요한 정보 |
|---|---|
| 문서 | 연도·부문·문서 버전·원본 해시 |
| 절과 소제목 | 식별자·제목·상위 소속·원문 위치 |
| 표와 셀 | 행·열·병합 범위·값·단위·산출 기준·원문 좌표 |
| 공동 값 | 원문 셀 하나와 그 값이 적용되는 행 묶음 |
| 주석 | 원문 문장·위치·적용 대상·연결 확정 여부 |
| 참조 | 출발 문장·대상 절·조건 원문·연결 종류·확정 여부 |
| 처리 상태 | 추출 도구·변환 버전·불확실 사유·추적 가능한 원문 |
| 검색 표현 | 공종 목록·규칙 문장·표 또는 작업 조건별 묶음과 원문 식별자의 연결 |

63/55는 세 행에 각각 생긴 독립 값 세 개가 아니라, 세 행에 걸친 원문 셀과 적용 범위로 보관한다. 같은 문장이 다른 표에서 반복되면 원문 위치와 연결을 각각 남긴다.

표의 병합 범위는 추출 결과로 보관할 수 있지만, 그것만으로 계산상 의미까지 전부 확정되지는 않는다. 주석의 적용 범위나 참조 조건이 모호하면 미확정 상태를 유지한다.

**산출물:** 저장 형식 설명과 실제 185쪽 데이터를 넣은 예시. 기존 스키마와 달라지는 필드 목록.

**완료 기준:** 63/55의 원문과 적용 행, 작은 표의 유형과 설명, 주석 위치를 추적할 수 있다. 빠진 정보는 정상값으로 표시하지 않는다.

## 2단계: 같은 데이터로 청킹 후보를 만든다

다음 세 가지를 우선 비교한다.

| 후보 | 검색 대상으로 만드는 내용 | 검색 후 가져오는 내용 |
|---|---|---|
| 가 | 표 전체 또는 작업 조건별 행 묶음 | 검색된 조각 |
| 나 | 가와 같은 검색 조각 | 해당 표의 머리글·단위·산출 기준·필수 주석 |
| 다 | 나와 같은 검색 조각 | 나의 근거 + 필요한 참조 절 |

작은 표는 통째로 보존하고 큰 표는 작업 조건과 공동 값이 완결되는 행 묶음으로 나누는 안을 검토한다. 반복되는 직종명 하나를 기준으로 서로 다른 공종을 합치지 않는다.

짧은 절은 표와 주석을 포함한 절 전체를 부모 문맥으로 먼저 비교한다. 모든 표를 처음부터 작게 나누지는 않는다. 공종 목록은 제목·적용 범위에서 자동 생성하고, 규칙 질문이 공종 선택 없이도 해당 주석을 찾을 수 있도록 별도 검색 표현을 둔다.

부모·자식 방식은 작은 조각을 찾은 뒤 더 큰 근거를 가져오는 기능이다. 다 조합의 참조 연결은 다른 절을 가져오는 기능이다. 두 기능의 추가 효과를 구분해서 비교한다.

**산출물:** 원문 → 저장 구조 → 검색 조각 → 전달 근거를 나란히 볼 수 있는 비교 문서.

**완료 기준:** 조각을 나누어도 머리글·단위·공동 값·필수 주석의 의미가 유지된다. 긴 근거를 전달할 때 조건 문장을 중간에서 잘라 정상 답변을 이어가지 않는다.

## 3단계: 검색 후 근거를 모으는 기능을 확인한다

우선 기존 키워드·벡터 결합 검색을 유지하는 안으로 설계한다. 청킹과 새 임베딩 모델의 효과를 동시에 비교하지 않는다.

표를 찾으면 연결된 주석과 필요한 참조를 식별자로 가져온다. 참조는 연도·부문·절을 함께 구분하고 순환·대상 누락·모호함을 검사한다. 그래프 전용 데이터베이스 도입은 이 단계의 필수 조건이 아니다.

6-1-1의 표면 마무리 참조는 조건 문장과 대상 근거를 가져오는 대상으로 삼는다. 해당 작업이 필요하다는 확인 없이 비용을 자동 추가하지 않는다.

목록 질문은 절 제목과 적용 범위를 우선 조회하고, 기준 설명은 규칙 문장과 적용 대상을 우선 조회하도록 설계한다. 계산 명세가 없는 절도 목록과 설명의 검색 대상이 될 수 있어야 한다.

**산출물:** 가져온 근거, 원문 위치, 가져온 이유, 아직 확인하지 못한 관계를 보여주는 조회 결과.

에이전트에 전달할 공통 조회 도구의 응답 형식도 이 단계까지 정한다. 에이전트 전체 행동 변경은 5단계에서 진행하지만, 표·주석·참조·불확실 상태를 어떤 형태로 받을지는 지금 설계한다. 검색용 설명은 원문 값과 계산 명세를 대체하지 않는다.

**완료 기준:** 관련 주석과 참조를 누락하지 않으면서 무관한 규칙을 붙이지 않는지 사례별로 확인한다. 여러 공종은 항목별 근거를 구분한다.

현재 API 금지 조건에서는 고정된 검색 시작점과 오프라인 키워드 검색으로 검증한다. 고정 시작점 검사는 근거 조립 검사이며 실제 벡터 검색 평가가 아니다.

## 4단계: 작은 범위에서 검증하고 데이터 전환 여부를 결정한다

185쪽은 개선을 눈으로 확인하는 개발 사례로 사용한다. 555쪽은 잘못된 라벨 연결을 정상 데이터로 받아들이지 않는지 확인하는 실패 사례로 사용한다. 어느 쪽도 다음 수정의 새로운 평가 사례라고 부르지 않는다.

기존 질문 초안 중 약 20개를 골라 목록·설명·품·단일 견적·여러 공종 요청을 포함한다. 답변 전체보다 먼저 질문에 필요한 원문 근거의 묶음과 적용하면 안 되는 근거를 정한다.

방법을 고정한 뒤, 가능한 기존 출력 중 수정에 사용하지 않은 표를 최대 5개 확인한다. 적합한 별도 표본이 없으면 새로 확인할 범위를 먼저 정하고 부족한 검증을 명시한다. 공종별 설정을 늘려 표본만 통과시키는 방식은 쓰지 않는다.

### 핵심 검사

- 숫자와 행·열 조건의 연결
- 공동 값과 단위·산출 기준의 유지
- 필수 주석과 참조 근거의 누락
- 무관한 주석·조건부 규칙의 잘못된 연결
- 불확실한 자료를 계산 가능 상태로 오인하는 문제
- 원문 위치와 변환 과정을 재현할 수 있는지
- 근거 길이·중복·처리 시간

기준 코드의 현재 결과를 보관하고 같은 입력·같은 평가 기준으로 비교한다. 원문 구조 보관, 청킹, 반복 문장 보존의 효과를 분리한다. LLM이 만든 정답 초안의 검토 상태도 유지한다.

**산출물:** 기존 방식과 후보 방식의 비교 결과, 실패 목록, 적용 가능한 범위와 보류 범위.

**완료 기준:** 알려진 중요한 오류를 숨기지 않고, 별도 표본에서의 결과를 개발 사례와 구분해 보여준다. 표본 점수를 전체 품셈 정확도로 주장하지 않는다.

전체 문서 재파싱·재청킹·재임베딩·운영 적재는 이 결과로 범위를 결정하는 후속 실행이다. 지금 실행할 작업에 포함하지 않는다. 특히 재임베딩과 실제 LLM 평가에는 현재의 API 금지 조건이 그대로 적용된다.

## 5단계: 근거를 사용하는 에이전트를 정비한다

데이터와 검색 개선이 계산 명세의 정확성을 자동으로 보장하지 않는다. 검증된 계산 명세를 준비하는 절차와 사용자의 조건을 안전하게 반영하는 절차를 함께 갖춘다.

| 순서 | 에이전트에서 정비할 행동 | 확인할 결과 |
|---|---|---|
| 1 | 목록·설명·품·견적의 행동을 구분 | 목록 질문에 계산 명세 오류로 답하지 않는다 |
| 2 | 사용자 조건과 변경 대상을 구조화하고 서버가 검증 | 부정·단위·수정 대상 오류가 견적 상태를 오염시키지 않는다 |
| 3 | 질문과 가정의 일반 정책을 적용 | 필수 구분은 묻고 허용된 가정은 표시한다. 데이터 오류를 가정으로 덮지 않는다 |
| 4 | 계산 명세의 생성·검증·사용 가능 상태를 구분 | 원문과 단위·산식·조건이 확인되지 않은 명세로 금액을 확정하지 않는다 |
| 5 | 여러 공종의 상태·계산·합산을 관리하고 Excel로 출력 | 항목별 근거와 가정을 유지하며 견적서 하나와 통합 Excel을 만든다 |

계산 명세는 공종마다 사람이 새로 작성하는 방식보다 원문 구조에서 자동 생성하고 검증하는 방향을 유지한다. 검증은 필드 형식뿐 아니라 단위·산식·조건 범위·원문 값·대표 계산 사례까지 확인해야 한다. 형식 검사 통과와 실무 해석 확인을 같은 상태로 표시하지 않는다.

LLM은 문장 이해·조건 추출·근거 선택 제안·설명에 사용하고, 최종 숫자는 서버 계산기가 산출한다. 원문에서 자동 추출한 참조 조건을 계산에 적용하기 전에는 서버에서 처리 가능한 규칙과 근거로 검증한다.

처음부터 모든 대화 흐름을 동시에 교체하지 않고 목록·설명부터 확인한 뒤 품·견적·여러 공종으로 넓힌다. 질문별 검색 근거·입력 변경·가정·명세 버전·단가 기준·계산 결과를 기록할 구조는 초기 설계부터 준비한다.

**완료 기준:** 질문 유형별로 올바른 행동을 하고, 금액과 Excel의 숫자를 입력·명세·근거·단가 버전으로 재현할 수 있다. 사용자가 고칠 가정과 단가를 확인할 수 있다.

## 이번에 착수할 가장 작은 작업

**1단계 스키마 초안과 2단계의 185쪽 근거 묶음 시제품**을 먼저 만든다. 기존 ODL 출력으로 진행하고, 사용자가 원문과 직접 비교할 수 있게 보여준다. 555쪽의 실패 표시도 같은 형식으로 포함한다.

데이터베이스 제품 교체, 새 임베딩 모델 선정, 전면 재파싱, 에이전트 변경은 이 첫 결과물에 섞지 않는다. 비교가 끝나면 3·4단계로 이어간다.

## 실행 조건

여기서는 기획과 검토를 맡고, 구현은 사용자가 소넷에 전달하는 지시서로 진행한다. 다른 세션에 자동으로 메시지를 보내거나 구현을 시작하지 않는다.

현재 허용 범위는 저장소 읽기, 오프라인 검사, 기획·비교 문서 작성이다. 저장소 코드·설정·기존 데이터·루트 가상환경 변경, 비밀값 파일 읽기, 운영 접속, API 호출, 커밋·푸시·PR·배포를 하지 않는다.
