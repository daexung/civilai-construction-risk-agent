## 확인된 문제

1. 원문 릴리스 `rk-complete-82c206c61e21-37f81b5cfb1b`의 `verification.json`, `example_queries.json`, `manifest.json`이 청킹 후 원문 검사 재실행으로 덮어써졌다. 새 검사 결과에는 이전의 트랜잭션 검사 두 항목이 없다. 이전 결과 전체가 어디에 보존돼 있는지 실제 확인한다. 보고서나 실행 기록만으로 원래 JSON을 재현했다고 주장하지 않는다.
2. 청킹 묶음 `cs-37f81b5cfb1b-46f4f035c0fa`의 `manifest.json`에 기록된 `verification.json` 해시가 실제 파일과 다르다. 검토 시 `chunks.jsonl`, `input_usage.jsonl`, `stats.json`, `import_manifest.json` 해시는 일치했다. `checks/verify_chunks.py`가 재적재 검사 후 검사 결과를 저장하면서 해시 목록을 갱신하지 않는 경로를 조사한다.

## 작업 순서

1. 수정 전에 해당 결과 파일·해시·코드와 보존된 실행 기록을 별도로 보관한다. 원문과 청킹 데이터의 현재 해시와 DB 내용 비교 기준을 고정한다. 이전 정상 원문 릴리스도 보존한다.
2. 원문 검사 기록은 실제 보존 사본이 있으면 원래 파일과 해시를 확인해 복구한다. 사본이 없거나 내용이 불완전하면 원래 결과를 만들어내지 말고 복구 불가 범위를 기록한다. 필요한 검사를 다시 실행해 **새 실행 기록**으로 보관한다.
3. 기존 원문 릴리스 재적재는 청킹 외래 키 때문에 청킹 삭제가 필요할 수 있다. 청킹 묶음이나 기존 자료를 삭제해 검사하지 않는다. 필요한 트랜잭션 검사는 별도의 격리된 로컬 검증 공간에서 수행한다. 검사 범위와 생략 항목을 명시한다. 이전 51개 통과 주장과 이번 실행 결과를 섞지 않는다.
4. 검사 결과를 먼저 저장하고 그 뒤 최종 파일 해시 목록을 생성하도록 공통 저장 경로를 고친다. 목록 자체를 자기 해시에 포함하지 않는다. 재적재가 출력 파일을 다시 쓰는 경우도 마지막 저장 후 해시를 갱신한다. 중간 실패를 성공 상태로 표시하지 않게 한다.
5. 재검사는 기본적으로 별도 실행 기록 위치에 저장하도록 한다. 기존 완료 릴리스의 과거 검사 기록을 조용히 덮어쓰지 않는다. 원문·청킹의 완료 목록이 어떤 검사 실행을 가리키는지 명확히 연결한다. 과거와 새 실행을 구별하되 필요 이상으로 새 시스템을 만들지 않는다.
6. 청킹 검사를 재실행하고 최종 목록의 모든 파일 해시를 독립적으로 확인한다. 두 번 실행해도 이전 실행 기록이 남고 현재 실행 목록이 맞는지 확인한다. 검사 실패·결과 저장 실패 시 정상 완료로 표시되지 않는지도 최소한의 의미 있는 검사로 확인한다.

- 파싱 원본, 교정 자료, 원문·청킹 데이터와 참조 상태는 그대로다.
- 청크 5,764개와 `chunks.jsonl`의 내용·식별자·원문·연결은 수정 전과 같다.
- 원문 레코드 23,481개, 검색 입력 23,484개, 표 2,328개, 참조 241개의 내용과 상태는 같다.
- 기존 정상 릴리스와 청킹 묶음을 삭제하지 않는다. 운영 활성화와 원격 Supabase 연결은 하지 않는다.
- 검사 코드 수정으로 코드 해시가 바뀌는 경우, 현재 버전 산정 규칙을 확인해 변경을 기록한다. 기존 식별자와 해시를 억지로 맞추지 않는다. 내용이 같은 새 묶음이 필요하면 이유와 대응을 명시하고 이전 묶음을 보존한다.
