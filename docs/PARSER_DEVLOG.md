# 파서 개발일지

표준품셈 PDF 표 파서의 비교·평가·수정 기록이다. 결정의 이유는 `DECISIONS.md`, 전환 단계와 합격 기준(G1~G8)은 `ODL_MIGRATION_PLAN.md`, 평가 원본 판정은 `P5_HOLDOUT_REPORT.md`·`HOLDOUT_V2_REPORT.md`에 있다. 이 문서는 그 기록들을 날짜순으로 잇고, 각 항목을 **문제 · 근거 · 조치 · 검사 결과 · 남은 위험**으로 나눈다.

작성 규칙

- 평가 점수는 원래 기록을 그대로 옮긴다. 평가 뒤에 고친 결과는 "개발 검사"로 따로 적고 합격 점수로 쓰지 않는다.
- 정답은 모두 **잠정**이다(Claude가 원문 이미지로 작성, 실무 검토 미완료). 정답 쪽 원인은 "정답 오류", 파서·조립 쪽 원인은 "실제 파서 오류"로 구분한다.
- 원인 조사에서는 **사실**(원시 JSON·코드 추적으로 확인)과 **추정**(확인하지 않은 해석)을 나눠 적는다.

2. **어댑터의 첫 열 규칙이 분리를 거부한다.** 첫 열 줄 수 = 숫자 기준선 수이고 첫 열이 상위 조건 열로 판정되지 않으면, 행 라벨인지 줄바꿈된 조건인지 좌표로 구분할 수 없다며 나누지 않는다(`odl_tables.py:203`). 802_t2(11줄 = 기준선 11)에서 실제로 이 분기로 멈췄다. 876_t1도 목록을 문단으로 펼친다고 가정하면 같은 분기(5줄 = 기준선 5)에서 멈춘다(스크래치 가정 실험).
3. **조립 단계는 좌표 없이 줄 글자만 본다.** 행을 못 나눈 칸은 `assemble.unstack`이 줄 수로만 풀기 때문에 아래 표별 오류가 생긴다.

### 876_t1 (공정별 직종·수량 5행)

- 사실: ODL 본문은 1행이다. 공정·직종 칸은 5줄 문단, 수량 칸은 문단+목록 혼합이다(공통 원인 1).
- 사실: 조립에서 수량 칸이 숫자 칸이므로 깊이는 5다. `직종` 칸이 "줄마다 다르고 숫자 없는 5줄"이라 `is_row_label_lines`가 참이 되고, 첫 열을 여러 행에 걸친 **상위 조건**으로 본다(`assemble.py:176-186`). 그래서 공정 5개를 이어 붙인 `용접 교정 조작 소운반 보조(기능)`이 5개 레코드 모두에 붙는다. 직종·수량 짝은 맞다.
- 추정: 이 규칙은 185쪽처럼 "첫 열 = 작업 조건, 둘째 열 = 직종"인 표를 위해 만든 것이다. 첫 열도 행마다 다른 표(공정별 1:1)를 구분할 근거가 글자만으로는 없다.

### 876_t2 (소모자재 11행)

- 사실: 수량 칸이 중첩 목록이라 어댑터가 나누지 않는다. 목록을 펼친다고 가정해도 값이 `1.805병`처럼 단위가 붙어 `VALUE_RE`에 맞지 않아 숫자 칸이 없다(가정 실험). 조립도 숫자 칸·공유 깊이·첫 열 같은 줄 수 조건 셋 다 해당하지 않아 모든 줄을 한 레코드로 잇는다.

- 추정: 이 표는 ODL 문단 좌표만으로는 행을 복원하기 어렵다. PDF 글자 좌표(PyMuPDF `get_text("words")`)처럼 줄마다 실제 위치가 필요할 가능성이 크다.

### 802_t2 (SCH별 용접봉, 드문 칸)

  - 행 합침: 한 레코드의 라벨 칸에 다른 행 식별 글자가 함께 있는지, 값 칸에 숫자가 쌓였는지, 같은 레코드가 중복되는지 봤다. 행 식별 글자는 정답의 행 라벨만 썼다.
  - 자동 표시된 항목은 모두 원문 이미지나 격자와 대조해 오탐을 걸렀다.
