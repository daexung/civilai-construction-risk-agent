# P3 대각선 머리칸 표 대책·선 기반 누락 감시 결과

기록일: 2026-09-24 · 코드: `pipeline/table_guard.py`, `pipeline/odl_tables.py`(`run_odl(table_method=...)`) · 평가: `p3_eval.py`
정답은 모두 잠정 정답이다. 396·500쪽 정답(`validation/ground_truth_failures.json`)은 새로 만들었다. 두 표는 전에 PyMuPDF 결과를 본 적이 있어 **맹검이 아니다**.

## D1 원인 조사

ODL은 396쪽 8×10 표와 500쪽 10×6 표를 표 노드 없이 **문단 여러 개**로 냈다. 오류나 경고는 없었다.
- 줄 단위 글자는 남는다(예: `0.8 1.0 1.1 1.2 1.3 1.4 1.5`가 한 문단).
- 칸 구분은 사라진다.

두 표 모두 가로·세로 괘선이 다 있는 표이고, 머리칸에 사선 2개가 있다.

## D2 ODL 옵션

`--table-method cluster`도 두 표를 찾지 못했다. 결과가 `default`와 같았고, 시간도 26.5초로 같다. 채택하지 않았다.

## D3 선 기반 누락 감시

적용 범위는 계획서 3절과 `table_guard.py` 머리말에 적었다. 수치는 계획 초안값 그대로다: 가로선 ≥ 본문 폭 50%, 높이 ≥ 20pt, 덮임 80% 미만이면 누락 의심.

**개발 세트 39쪽 판정**: blind20 20쪽, 검증 10쪽, 기존 23건 범위, 5표 쪽이다.

| 판정 | 영역 수 |
|---|---|
| 덮임 (≥ 80%) | 95 |
| 부분 누락 의심 (50~80%) | 0 |
| 누락 의심 (< 80%) | 2 — 396쪽 표, 500쪽 표 (둘 다 실제 표) |

- **오탐률**: 누락 의심 2건이 모두 실제 표다. 오탐 0/2이다. 덮인 영역 95개는 모두 ODL 표와 대응한다.
- **감시 범위 밖 정답 표**: blind20 0/43, 실패 사례 0/2, 5표 0/5. 모든 정답 표가 선 표 후보 영역 안에 있다. 다만 개발 세트 기준이다. 가로선만 있거나 선이 없는 표는 이 표본에 없었고, 보류 표본에서 다시 확인해야 한다.
- **감시 시간**: 39쪽 0.72초 (ODL 실행 33초와 별도).

**대체 추출** (누락 의심 영역만, PyMuPDF)
- 처음에는 `find_tables(clip=영역)`으로 뽑았다. 그런데 잘린 영역에서 격자를 다르게 잡아 500쪽 첫 열 병합 라벨이 빈 칸이 됐다(파서 층 0/7).
- 쪽 전체 `find_tables()`에서 영역과 IoU 0.5 이상인 표를 고르도록 고쳤다. 병합 범위는 칸 좌표로 복원한다(실험 추출기와 같은 방식).

## D4 396·500쪽 사실 검증

| 경로 | 396쪽 (사실 5) 파서 층 / 최종 레코드 | 500쪽 (사실 7) 파서 층 / 최종 레코드 |
|---|---|---|
| ODL (감시 없음) | 0 / 0 | 0 / 0 |
| ODL + 감시·대체 추출 | **5 / 0** | **7 / 1** |
| 참고: PyMuPDF 실험 추출기 | 5 / 0 | 7 / 1 |

- **파서 층은 두 표 모두 전부 복원**됐다. 값과 행·열의 짝이 맞다.
- **최종 레코드는 아직 실패**한다. 원인은 현행 조립의 머리글 판정이다(P4).
  - 396쪽: 머리글 3행을 1행으로 세서 열 이름이 `연암 0.8`이 아니라 `연암`이 된다.
  - 500쪽: 값이 순수 숫자가 아니라서(`5만㎡`, `100m×30m`) 머리글을 5행으로 과다 계산하고, 데이터 행이 머리글에 흡수된다.
- 계획의 D4 합격 조건("모든 값이 올바른 행·열로 레코드에 들어간다")은 **P4 이후에 판정**한다.
